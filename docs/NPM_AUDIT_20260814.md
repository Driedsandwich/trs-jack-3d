## 到達性

**このプロジェクトの使い方では踏まない。**

```
配布する検算ツールが nanoid を呼ぶか   0 件（対照: node: の import は 6 件ある）
build 成果物に nanoid が入るか          0 / 7 ファイル（対照: THREE を含むファイルは 1 件ある）
```

`nanoid` を呼ぶのは `postcss` の内部だけで、**`postcss` が動くのは開発機と CI の build 時**である。
脆弱性の条件は「custom generator に size 0 を渡す」ことで、
**そこへ外部からの入力が流れる経路は無い**（build するのは、このリポジトリの中の CSS だけ）。

**「踏まない」と書いた根拠は上の 2 つの実測だけである。**
`postcss` の内部実装を読んで確かめたわけではない。

## 直したときの壊れやすさ

`3.3.16 → 3.3.18` は patch であり、`postcss@8.5.25` が要求する範囲の中に収まる。
**壊れる見込みは小さい**が、**このリポジトリでは実行していない**——
依存を動かすと `package-lock.json` が変わり、`profileId` が動く（v0.6.14 で実測済み）。
**release の直前に依存を動かさない。**

## 方針

- **次の版の頭で** `nanoid` だけを上げ、その版の staging で `profileId` の変化を実測する。
- SECURITY.md に書いたとおり、依存の脆弱性は**踏む経路を添えて**報告してほしい。
  `npm audit` の出力だけだと、この使い方では到達しないものが大半になる
  ——**現に、今回の 1 件がそれである。**
