# v0.6.12 — **前の版の誤りを 3 件訂正します。うち 1 件は配布物そのものの誤りです**

## ⚠ 先に読むところ — **v0.6.11 の訂正 3 件**

**公開した release 本文は編集しません。**代わりに正誤表を作りました
——同梱の `ERRATA.md` はありませんが、リポジトリの
[`docs/ERRATA.md`](https://github.com/Driedsandwich/trs-jack-3d/blob/v0.6.12/docs/ERRATA.md)
に、**気づいた方法と再現手順つき**で載せています。

### 1. **`VERIFICATION_INCOMPLETE` になる tag の範囲が違いました**（配布物ではなく文章の誤り）

```
誤  「v0.3.0 より前の tag を検算すると、これに当たります」
正  「v0.4.0 より前の tag を検算すると、これに当たります」
```

**`v0.3.0` 自身も対象です。**範囲定義（`manifest.inputScope`）が入ったのは v0.4.0 から。
21 tag すべてを、その tag の source に対して実際に走らせて確かめました。

```
v0.1.0 / v0.1.1   manifest 自体が無い
v0.2.0            VERIFICATION_INCOMPLETE
v0.3.0            VERIFICATION_INCOMPLETE   ← 前の版は「これは大丈夫」と読める書き方だった
v0.4.0 / v0.4.1   OK
```

**境界を実際に走らせずに書いたのが原因です。**

### 2. **「通す材料 66 件」は、誰も検査していない旗の数でした**（文章の誤り）

**実際に通る材料は 72 件です。**

corpus が**同じ境界を 2 つの一覧**で持っていました——材料ごとの `ok` 旗と、期待値表です。
**検査されていたのは期待値表だけ**で、旗は 1 か所から `!ok` としてしか読まれず、
**`ok: true` が本当に通ることは一度も確かめられていませんでした。**10 件でずれていました。

そのうち 2 件（`pax-zero-length-mtime` / `pax-zero-length-uid`）は、
外部監査で「過剰拒否では」と挙がって一度こちらが通すと判断し、
CI の ubuntu が `Malformed extended header: invalid mtime=` を出したので拒否に戻したものです。
**そのとき旗のほうを戻し忘れて、以後ずっと数に混ざっていました。**

### 3. **同梱の artifact が status を 5 種類と書いていました**（**配布物そのものの誤り**）

```
v0.6.11 の source-verification-result.json → howToVerifyYourself
  「status は OK(0) / MISMATCH(1) / SOURCE_UNAVAILABLE(2)
       / MANIFEST_UNAVAILABLE(2) / NOTHING_TO_VERIFY(2)」        ← 5 種類

同じ配布物の verifyReleaseSourceInputs.mjs                        ← 8 種類を返す
```

足りない 3 つは v0.6.10 と v0.6.11 で足したものそのもので、
**`VERIFICATION_INCOMPLETE` は v0.6.11 の目玉なのに、受け手に伝わっていませんでした。**

**v0.6.11 の配布物を使っている場合は、この行を読まないでください。**
`schemas/source-verifier-cli-result.v1.schema.json` の `status.enum`（同じ配布物に入っています）
が正本です。v0.6.12 では**道具の定数から生成**しています。

v0.6.12 の手順書はこの 1 行です（**折り返さずにそのまま載せます**——
折って書くと、配布物と機械で突き合わせられなくなります）。

```
# status は OK(0) / MISMATCH(1) / VERIFICATION_INCOMPLETE(1) / ARCHIVE_INVALID(2) / ARCHIVE_UNSUPPORTED(2) / SOURCE_UNAVAILABLE(2) / MANIFEST_UNAVAILABLE(2) / NOTHING_TO_VERIFY(2)。
```

## この版でやったこと — **一覧を 1 本にする**

3 件とも同じ形の欠陥でした。**同じ境界を、検査されない一覧がもう 1 つ持っている。**

**直す前に「嘘の一覧でも緑のままか」を実測**してから直しています。

| 直す前の変異 | 落ちた試験 | 直したあとの同じ変異 |
|---|---:|---:|
| corpus の `ok` 旗を 1 件反転 | **0 件** | 期待値を嘘にすると **2 件** ／ 種類の既定を消すと **5 件** |
| 手順書の一覧に偽の `TOTALLY_FAKE(9)` を足す | **0 件** | **2 件** |
| 手順書から新しい status を 1 つ落とす | — | **2 件** |
| 手順書の終了コードだけ嘘にする | — | **2 件** |

```
corpus の ok 旗        消した。判定は test/_tarExpectations.mjs 1 本から引く
                       引けない材料は例外にする（黙って「通る」側へ落とさない）
status と終了コード     verifyReleaseSourceInputs.mjs の CLI_STATUS_EXIT が正本
                       CLI_STATUSES も配布物の手順書もそこから導出する
自己申告の表現範囲      scripts/selfReportStatus.mjs へ切り出し、schema の enum を正本に
                       関門を投げる関数にしたので、試験が実際に踏める
```

**受け手向けの出力は 1 バイトも変わりません。**v0.6.11 の道具と v0.6.12 の道具に
同じ入力を与えると**出力の差は 0 行**でした（対照: 引数を変えると 102 行差）。
判定が変わっていないので **`toolVersion` は 16 のまま**です。
