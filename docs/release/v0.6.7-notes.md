# v0.6.7 — **schema は 1 本も上げていません。下流はどこでも止まりません**

## ⚠ 先に読むところ

### 1. **v0.6.6 は、誰も展開できない木を「合っている」と言っていました**

**受け手に直接影響するのはこちらです。**

```
regular root/src ／ regular root/src/model/a.ts
  検算 v11  READ（files に src と src/model/a.ts の両方）／ status OK
  bsdtar    exit 1 — Not a directory
  python    exit 2 — NotADirectoryError
  GNU tar   exit 2 — Cannot open: Not a directory

symlink root/src -> elsewhere ／ regular root/src/model/a.ts
  検算 v11  READ
  4 実装すべて tree を作れない
```

**祖先が通常ファイルや symlink でも、その下の entry を受理していました。**
v0.6.5 で「先頭 1 階層が directory か」を塞ぎましたが、
**それは途中の階層でも同じことが起きるという一般形の、特殊な場合でした。**

### **お願い: v0.6.6 以前で出た `status OK` のうち、リンクを含む source は取り直してください**

**そちらが v0.6.6 以前の道具で別の archive を検算していた場合、
`OK` が出ていても「その木が作れる」ことは示せていません。**
`v0.6.7` の道具で取り直してください。

### 2. linkname の上書きに状態機械がありませんでした

```
global の linkpath（g ヘッダ）
  検算 v11  READ（受け取って黙って無視）
  bsdtar    root/ln -> root/t1   ／ python    root/ln -> root/t2   **別の木**

linkpath を 2 回          bsdtar は exit 1 ／ python は 1 つ目を採る
上書きのあとに entry 無し   bsdtar は Damaged tar archive ／ python は ReadError
```

名前の上書きには v0.6.4 から状態機械があるのに、**指す先の側には無かった**ということです。
`inventory` に記録する指す先も、**上書きが効いたあとの値**に直しました
（v0.6.6 はヘッダの 100 byte 欄をそのまま記録していたので、記録と展開結果が別物でした）。

### 3. **こちらの過剰拒否が、これで 3 版続けてです**

```
負の時刻 mtime=-1（GNU tar がふつうに書く）    4 実装とも展開できるのに拒んでいた
hardlink の連鎖 A → B→A → C→B                 同上（nlink=3 の 3 本ができる）
指す先の別の綴り root/./A ・ ./root/A ・ root//A  同上
```

v0.6.7 は通します。**`..` と末尾スラッシュは通しません**——実測でそこは実装間で割れます。

### 4. **監査に無い false-OK を 1 件、こちらの実測で見つけました**

```
hardlink の指す先が / で終わる（root/B -> root/A/）
  検算 v11  READ            ← 受理していた
  bsdtar    exit 1 — Can't create 'root/B': Not a directory
```

v0.6.6 は末尾スラッシュを剥がしてから照合していたので、
**剥がした結果は存在するので通り、実際には展開できません。**

### 5. `ARCHIVE_UNSUPPORTED` を新設しました

v0.6.6 まで、止める理由は全部 `ARCHIVE_INVALID` でした。
だが実測で、**ふつうの tar が何事もなく展開する archive**をいくつも「壊れている」と言っていました
（base-256 の size 欄・typeflag 7 / S / D / M / N・長いパス・未知の vendor 鍵）。

| | 意味 |
|---|---|
| `ARCHIVE_INVALID` | 矛盾・破損・曖昧、または展開できない |
| `ARCHIVE_UNSUPPORTED` | ふつうの tar なら展開できるが、**この道具が扱うと決めた範囲の外** |

**exit code は両方 2 のままで、`OK` にはなりません。**
`status !== 'OK'` で分岐しているなら影響はありません。
**自己申告の schema には入れていません**（あちらの経路では出ないためです）。

### 6. **必須 oracle を 2 実装同時に効かせるようにしました**

v0.6.6 まで CI は ubuntu 1 本、開発は macOS でした。
**つまり GNU tar と bsdtar が、同じ変更に対して同時に効いたことが一度もありません。**

```
ubuntu-latest   tar (GNU tar) 1.35 / Python 3.12.3
macos-latest    bsdtar 3.5.3 - libarchive 3.7.4 / Python 3.14
```

**入れた最初の run で 2 つ見つかりました。**

```
① 止める理由の表が、片方の platform しか見ていなかった（8 件失敗）
② 木を歩く試験の道具が、名前を UTF-8 文字列で読んでいた（1 件失敗）
   Linux は不正 UTF-8 のファイル名を作れるので lstat が ENOENT になる
   macOS の APFS は作れないので、**この欠陥は macOS では出ない**
```

**どちらも archive の扱いではなく、確かめる側の欠陥でした。**

### 7. `profileId` が変わりました。**lock を作り直してください**

```
v0.6.6  trs-jack-3d:TRS|JACK-TRS:4874b63082e9
v0.6.7  trs-jack-3d:TRS|JACK-TRS:c4bf51e169e3

v0.6.6  trs-jack-3d:TRS|JACK-TRRS:4998389a40e4
v0.6.7  trs-jack-3d:TRS|JACK-TRRS:f8599fafc8a9
```

**この文書から転記せず、同梱の `trs-jack-3d-release-index.v1.json` から引いてください。**

**動いた原因は版数上げ（`package-lock.json`）です。**検算ツールは配布物ですが
**入力ではない**ので、v11 → v12 にしても digest を動かしません。

**モデルの数値は変わっていません。**葉ノードまで平坦化した実測です。

```
TRS   葉 2267 件 → 由来まわりの差 10 件 / モデル数値の差 0 件
TRRS  葉 3130 件 → 由来まわりの差 10 件 / モデル数値の差 0 件
```

この比較が「全部を由来に寄せているだけ」ではないことも確かめてあります——
`fullInsertionDepthMm` を 14 → 14.001 に変えると **「モデル数値の差 1 件」**になります。

### 8. **契約は変わっていません**

## 止める理由の半分は、片方の実装だけでは見えません

止めているもののうち、**その run の 2 実装がそろって通し、同じ木を作るもの**が 20 件あります。

```
GNU tar 側でだけ根拠が取れる   9 件
bsdtar 側でだけ根拠が取れる    8 件
どちらでも取れていない         3 件
```

**監査が報告した GNU tar の挙動は、メッセージまでそのとおりでした**
（`Extended header gid=4294967296 is out of range 0..4294967295`）。
一覧は `test/tarExtractionOracle.test.ts` の `EVIDENCE_ELSEWHERE` にあり、
**どこで根拠が取れるかを毎 run 両方向で照合します。**

GNU tar でも 24 件すべて通ることを CI で確かめています。
