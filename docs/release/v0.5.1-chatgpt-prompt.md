## 4. P0 — `oneOf` の誤判定を直した

**指摘は実在した。**ajv で裏を取ってから直した。

```
旧  oneOf: [{integer}, {number, minimum: 0}]
新  oneOf: [{integer}, {number, minimum: 1}]

値 0    旧 invalid（2 枝が一致するので oneOf は落ちる）→ 新 valid   **広がっている**
値 0.5  旧 valid                                    → 新 invalid  狭まっている
```

どちらも他方を包含しないので正しい判定は `BUMP`。
**v0.5.0 までの実装は `HOLD_RECORD`（据え置き可）を返していた。危険な向きの誤りである。**

原因も指摘のとおり、`oneOf` の枝を index 同士で再帰比較していたこと。
`oneOf` は「ちょうど 1 枝が一致」なので**枝の言語について単調でない。**

**`oneOf` は変更があれば無条件で `UNDEC`（→ `BUMP`）へ倒す。**

### `anyOf` / `allOf` は触っていない

そちらの推奨は「`anyOf` / `allOf` も包含を証明できる限定ケース以外は `UNDEC`」だったが、**採らなかった。**

`anyOf` は和、`allOf` は積なので、**枝ごとの言語が狭まれば全体も狭まる（単調）。**
枝ごとの再帰比較で健全である。ここまで倒すと、狭めただけの変更まで版上げになり、
**条文の判別力（据え置き可を据え置き可と言える能力）が落ちる。**
枝が混在した場合は WIDEN と NARROW が両方立ち、verdict は `BUMP` になる（安全側）。

「`anyOf` / `allOf` は `HOLD_RECORD` のまま」もテストに入れた。

### 回帰試験は 5 件

| | 内容 |
|---|---|
| ① | ajv で値 `0` と `0.5` の valid / invalid が反転すること（＝どちらも他方を包含しない） |
| ② | **`v0.5.0` tag の実物を `git show` で読み込んで** `HOLD_RECORD` を返すこと |
| ③ | 現在の実装が `BUMP` を返し、**その経路が鳴ったこと**（別の理由で BUMP でも意味がない） |
| ④ | `anyOf` / `allOf` は `HOLD_RECORD` のまま（倒しすぎていない） |
| ⑤ | live な schema で `oneOf` が実際に使われていること（**4 本・計 8 か所**） |

②が無いと「昔からそうだった」のか「直した」のかを、記録でしか主張できない。
②は「昔の実装が枝を index 同士で比べていた」ことも同じテストで確認するので、
反例が的外れになったら落ちる。

**v0.5.0 の 6 本の判定は汚染されていなかった**（`oneOf` 由来の差分 0 件・すべて他の理由で `BUMP`）。
そちらの評価と一致する。

## 7. 実装中に見つけたもの／v0.6.0 へ回したもの

### macOS の `tar` で作った archive は `--source` で壊れる

```
tar czf src.tar.gz -C dir .        ← macOS
→ AppleDouble（._*）が混ざる
→ stripTopLevel が「共通の親が 1 枚」と判定できなくなる
→ **30 件すべてが missingInSource**
```

**GitHub の tarball では起きない**（`._*` を含まない）。
release notes が案内している経路は動く（下の手順で 30/30 一致を実測済み）。

```bash
curl -sL -o src.tar.gz \
  https://github.com/Driedsandwich/trs-jack-3d/archive/refs/tags/v0.5.1.tar.gz
node verifyReleaseSourceInputs.mjs --manifest source-input-manifest.json \
  --source src.tar.gz --scope source-input-scope.v1.json
```

自分で `tar` を作って渡す場合は `COPYFILE_DISABLE=1` を付けること。
