# v0.6.17 — 監査スレッドへ渡す作業指示

添付は公開物から取得したものです。**まず `shasum -c SHA256SUMS` を通してから読んでください。**
以下の数値は、すべて添付のファイルから機械照合できます。報告文からの転記ではありません。

## 1. P0 を実データで再現しました。**指摘より影響が広かった**

指摘は「`stableReasonCode` へ 2 値を足しながら v1 のままだった」でした。
両 tag の実物へ repo 自身の判定器を当てて確かめました。

```
diffSchemaObjects(v0.6.15 の v1, v0.6.16 の v1) = **BUMP**
  WIDEN  /properties/stableReasonCode/enum
           + CLI_ARGUMENTS_MISSING, SOURCE_FETCH_TIMEOUT
  WIDEN  /properties/archivePolicy/properties/coverage/properties/reasonCodeFamilies/items/enum   + usage
  WIDEN  /properties/archivePolicy/properties/reasonCodeFamilies/items/enum                        + usage
対照  同じ schema どうしなら HOLD（常に BUMP と言う判定器ではない）

schema の sha256（実測）
  v0.6.15  59b765499cc7b3070ecb6cedbcf54770e35fcbdbd9f505efb92d9310ea928eee  18073 B
  v0.6.16  77a32f714d2a11833d6c59f6cac76f82033cafacdd3cd96bc5c359cd1661713e  18188 B
```

**指摘は 2 か所ですが、実際は 3 か所です。**そして `usage` 族は `archivePolicy` に載るので
**全出力に出ます。**ajv で当てた結果:

```
v0.6.15 の v1 schema に、v0.6.16 の道具の出力を当てる
  引数不足の出力（CLI_ARGUMENTS_MISSING）  → 不適合 3 か所
  **`OK` の正常な出力**                     → **不適合 2 か所**
```

つまり「新しい 2 つの code を返す結果だけが不適合」ではなく、
**v0.6.16 の出力は 1 つも v0.6.15 の schema を通りません。**
ここは指摘を鵜呑みにせず、実際に走らせて測った結果です。

## 2. 根本原因も再現しました。**母集団が 11 版のあいだ止まっていました**

指摘どおり `LATEST_TAG = 'v0.5.1'` が原因でした。実測:

```
v0.5.1 の schemas/      21 本
現在の schemas/         23 本
差（一度も検査に入っていない）
  schemas/measurement-record.v1.schema.json
  schemas/source-verifier-cli-result.v1.schema.json
```

**「いまの検査は嘘でも緑か」を先に測りました。**

```
BUMP が実在する状態で v0.6.16 の schemaVersioningPolicy を回す → **57/57 全緑**
```

その検査には「比較した本数 === 母集団の本数」という空振り検査が付いていました。
**数えていたのが古いほうの一覧**なので、新しい契約が抜けても鳴りません。

**直した形。**直前 release は `package.json` の版数より小さい最大 tag をその場で選び、
母集団は現行の `schemas/*.schema.json` 全部にしました。
**`git add` していないものも数えます**——add 忘れのあいだ検査から消えるのは、同じ形だからです。

**回帰試験を入れました。**v0.6.15 → v0.6.16 の実物を当てて、
**いまの判定がこの反例を違反として鳴らす**ことを固定しています。
対照として、変えていない組み合わせでは鳴らないことも見ます。

## 3. **`HOLD_RECORD` の想定は、判定器の実測と違いました**

指示書 §3 は「Schema を狭める変更のため、policy に従い `HOLD_RECORD` を記録する」でした。
入れてから測ると `BUMP` でした。

```
diffSchemaObjects(v0.6.16 の validation-results.v2, 狭めた版) = **BUMP**
  UNDEC  /properties/testEvidence/oneOf
         「ちょうど 1 枝」は枝の言語について単調でないので、枝ごとの比較では決められない
```

`testEvidence` は `oneOf: [null, object]` で、狭めるのは object 枝の中です。
判定器は `oneOf` の中の変更を**判定不能**として `BUMP` を返します（条文どおり）。

**判定器を緩めませんでした。**この判定は v0.5.0 の外部監査（`oneOf` の反例）で
入れたもので、緩めるとその反例が戻ります。**代わりに `validation-results` を v3 へ上げました。**

変異対照（7 種類）:

```
                                  v2（旧）   v3（新）
基準（無変更）                       適合       適合
testCountsSha256 を消す              適合     **不適合**
testCountsGeneratedFromCommit を消す 適合     **不適合**
testCountsGeneratedAt を消す         適合     **不適合**
SHA を 63 桁にする                   適合     **不適合**
commit を短縮する                    適合     **不適合**
日付を壊す                           適合     **不適合**
未知項目を足す                       適合     **不適合**
```

## 4. cross-binding は**関門を切り出してから**測りました

指示書 §4 の変異 5 種を、最初は `npm run release:stage` を丸ごと回して測りました。
**全件 exit 1 になりましたが、止めた理由は全件同じ**でした——手前の鮮度検査です。

```
基準（無変更）           exit 1  「test_counts.json が実測と違う」
test_counts だけ更新     exit 1  同じ
validation だけ更新      exit 1  同じ
SHA だけ偽装             exit 1  同じ
```

**これは「この関門が効いた」の証拠になりません。**落ちた理由が別だからです。
関門を `crossBindTestEvidence()` に切り出し、そこへ直接当て直しました。

```
基準（無変更）              通す
test_counts だけ更新        **止める**（testCountsSha256 が指す先と違う）
validation だけ更新         **止める**（total が食い違う）
SHA だけ偽装                **止める**
commit だけ偽装             **止める**
date だけ偽装               **止める**
testEvidence ごと消す       **止める**
```

**それぞれ固有の理由で止まっています。**関門が `release:stage` から呼ばれていること自体は、
別の試験がソースを読んで確かめます（書いただけで配線し忘れる形を防ぐため）。

## 5. §8 は「語彙が無い」ことのほうが問題でした

`SOURCE_ARCHIVE_MISSING` は指摘どおり `race-defensive` へ移しました。
ただし、移そうとして分かったことがあります。

```
v0.6.16 の両方向照合
  const shouldReach = entries.filter(([, m]) => m.reachability !== 'defensive-invariant')
  const shouldNot   = entries.filter(([, m]) => m.reachability === 'defensive-invariant')
```

**文字列の否定で 2 群に分けていました。**新しい種類を足すと、
**黙って「到達するはず」側へ入ります**（実際、`race-defensive` を足した瞬間に落ちました）。
逆に言えば、宣言を書き換えるだけで検査から外せます。

語彙表 `REACHABILITY_KINDS` を作り、`reachedInRun`（この repo の試験一式で決定的に踏めるか）
を明示しました。知らない値があればその場で投げます。

```
catalog 82 種類 = corpus 45 / cli-route 33 / defensive-invariant 3 / race-defensive 1
```

## 7. §10 は「名前だけを持つ」形にしました

値の正本は `assets[]` の filename と sha256 のままです。
`REQUIRED_CONSUMER_PINS` は**どれを固定すべきかの名前**だけを持ち、
**`RELEASE_ASSETS` から role で導出**します（手で並べると配布名が変わったときに古くなるため）。
索引の `notes` はその名前を載せますが、**`notes` 自身は機械契約ではない**と `notes` に書いています。

## 8. attestation は索引の外に置きました

指示書 §5 の 11 項目をすべて入れました。**索引に入れなかった理由**は指摘どおりの循環です。

```
索引        release:evidence が作る。その時点で全 asset の sha256 を持つ
attestation 索引を読んでから作る
→ 索引が自分の digest を持つと、1 回の実行で収束しない
```

**SHA256SUMS が attestation の sha256 を持ちます**（staging の最後に作られるので循環しません）。
`exactTestEvidenceMatched` などは**門が通ったときにだけ立てた値**で、定数の `true` ではありません
（試験がソースを読んで確かめます）。

## 次の版で着手すること — **計画を書きました**

**core / CLI 分離。**v0.6.16 の notes で「次の版で着手します」と書きましたが、
**この版でも着手していません。**監査も「先に契約の versioning を閉じ、
その次の独立版で着手するのが妥当」としており、その判断に従いました。

**約束を文にするだけにしないため、着手手順と検証手順を先に書きました**
（`docs/CORE_CLI_SEPARATION_PLAN_20260815.md`）。要点:

```
やる     main(args, io) の抽出だけ。**1 コミット**
やらない ファイル分割・API 設計変更・判定ロジックへの変更（1 行も触らない）
触る場所 8 か所だけ（実測。うち 2 か所は入口の判定なので CLI 側に残る）
```

**検証は「分離前の出力を先に固定する」形にしました。**

```
段 0  分離前に、全経路の stdout / stderr / 終了コードの sha256 を取る
      経路の母集団は test/_cliRoutes.mjs（引数なし・OK・fetch 失敗・timeout・
      503・body・git archive・manifest 欠落）
段 5  分離後に同じものを取り、**byte で**比べる
      対照  基準を 1 バイト変えると不一致として検出されること
```

**stdout を JSON として比べません。**キーの順序が変われば受け手の差分も変わるためです。
`toolVersion` は上げません——**上げたくなったら、それは分離ではありません。**

分離が済んで初めて `SOURCE_ARCHIVE_MISSING` を実経路として踏めます
（`io.existsSync` を通したあと `io.readFileSync` が ENOENT を返す形を注入する）。
そのときに `race-defensive` から `cli-route` へ移します。

## 12. **公開した直後に、自分で欠陥を 1 件見つけました**

attestation が名乗る 3 つの digest を、添付の実物と突き合わせたところ **2/3 しか一致しません**でした。

```
testCountsSha256         15add2c4d070e050…  一致
validationResultsSha256  4e1c6aa91064c2b2…  一致
releaseIndexSha256       e9c72e2412fa6e21…  **不一致**
                         a014768129b56e18…  ← 配布した索引の実測値
```

原因: attestation を書く工程が **repo 側の索引**を測っていました。
`test_counts.json` と `validation-results.json` は配布時にそのまま写すので同じ値になりますが、
**索引だけは配布時に `releaseTag` と `releaseCommit` を書き込む**ので別物になります。

```
repo 側   releaseTag = null      / releaseCommit = null
配布物    releaseTag = v0.6.17 / releaseCommit = cc3452a517ac
```

**「検証した物と出荷した物を別にしない」の再発です。**
公開済みの asset は上書きしません。`docs/ERRATA.md` §23 に記録し、コードは直しました
（測る先を `OUT` へ）。**この欠陥を捕まえる検査**も入れ、変異対照で確かめています
——`resolve(ROOT, …)` へ戻すと**その検査だけが落ちます**（他 8 件は緑のまま）。

**受け手への影響は 1 欄だけです。**`SHA256SUMS` は配布物から作っているので正しく、
索引の検算はそちらで行えます。
