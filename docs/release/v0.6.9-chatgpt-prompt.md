# trs-jack-3d v0.6.9 — 前回の指摘への回答と、次にお願いしたいこと

**6 群すべて、こちらで archive を組み立て直して再現してから直しています。**

## 1. 前回の指摘をどう直したか

### P0-A ヘッダ形式を確かめずに 345..499 を prefix として読んでいた

```
magic が old GNU（ustar␠␠\0）／ V7（全 NUL）／ 未知 で、345..499 が非空
  検算 v13  status OK ／ 32 of 32（src/model/types.ts が「ある」と言う）
  bsdtar    exit 0 — types.ts を root に作る       ← prefix を使わない
  python    exit 0 — src/model/types.ts を作る     ← prefix を使う
```

**そちらは「GNU tar だけが違う」と書いていましたが、実測ではもっと広いです。**
**bsdtar でも同じ差が出ます**——つまり手元の 2 実装だけで根拠が取れました。

magic を形式判別子として読み、**prefix を使うのは POSIX ustar のときだけ**にしました。

### P0-B typeflag が除外表だった

```
typeflag Z ／ 空白（本体 5 バイト）を、範囲の外（docs/ の下）に置く
  検算 v13  status OK ／ 32 of 32 ／ files 85・inventory 86
  bsdtar    exit 0 — 5 バイトの通常ファイルを作る
  python    同じ
```

**除外表は、知らない物を通す側へ倒れます。**許可表にしました
（`NUL`/`0`・`1`・`2`・`5`・`x`・`g`・`L`・`K` だけ）。

### P0-C 長さ 0 の PAX 値

`path=` は member を丸ごと一覧から落としていました（`files` 0 件・bsdtar は展開する）。
`path`/`linkpath` は止めます（理由は §3-c）。

### P1-A 同一 PAX ヘッダ内の重複鍵 → 後勝ちへ

`path` / `linkpath` / `mtime` / `uid` / `size` / `comment` の **6 鍵とも
2 実装が一致して後の値を採る**ことを実測しました。**こちらの過剰拒否でした。**

### P1-B symlink・hardlink の名前の末尾スラッシュ → 受理へ

2 実装とも同じ木を作ります。末尾スラッシュを 1 回だけ剥がして、
剥がした名前で衝突・祖先の検査をやり直します。
**通常ファイル（type 0）は拒否のまま**——実測で
**bsdtar は directory を作り、python は通常ファイルを作る**ので割れます。

### P1-C 試験の穴

生ヘッダの `uname`/`gname` の不正 UTF-8 材料を足し、**両 matrix で実行**しました
（結果は §5）。あわせて `stableReasonCode` を付けています。

## 3. **勧告のうち 3 点は採っていません**

前回、**そちらが勧めた正規表現（`^-?(0|[1-9][0-9]*)…`）をそのまま採ったことが
過剰拒否になりました**（`uid=0001` が落ちた）。
今回は**勧告どおりに書いたものを corpus の「通す」側へ当ててから**決めています。

### (a)「V7・old GNU を実装しないなら `ArchiveUnsupported`」→ 採らない

実測で、**345..499 が空なら old GNU も V7 も未知 magic も 2 実装が同じ木**を作ります。
そして **old GNU は GNU tar 自身の既定の出力形式**です。
形式で拒むと、**ふつうに GNU tar で作った tar.gz が読めなくなります。**

止めるのは「**形式が POSIX ustar でないのに 345..499 が非空**」——実装が割れる形だけです。

### (b)「prefix は `ustar\0` + `00` のときだけ」→ version を見ない

実測で、magic が `ustar\0` なら version が **`00` / NUL NUL / 空白 2 個**のどれでも
**2 実装とも prefix を使います。**version まで見ると、この 2 つを落とします。

### (c)「長さ 0 の `path=` は POSIX の削除意味を実装する」→ 止める

```
x: path=（長さ 0）＋ 生ヘッダ root/raw.txt
  bsdtar    exit 0 — root/raw.txt を作る（POSIX の削除意味）
  python    exit 2 — IsADirectoryError（空の名前として扱う）
```

削除意味を実装すると **bsdtar とは一致しますが python とは一致しません。**
この道具の約束は「ここに挙げた物が、展開して出てくる物と同じ」なので、
**読み手によって出てくる物が違う archive では、その約束を果たせません。**

## 4. **こちらが 1 つ間違えました。CI が落として分かりました**

長さ 0 の `mtime=` / `uid=` も「過剰拒否」と判断して**通すように直したのですが、誤りでした。**

```
x: mtime=（長さ 0）／ uid=（長さ 0）
  GNU tar 1.35  Malformed extended header: invalid mtime= — **archive ごと拒む**
  bsdtar        exit 0 — 削除として無視して展開する
  python        同じ
```

**開発機に GNU tar が無く、手元の 2 実装がそろって通したのを「割れていない」と読みました。**
割れていたのは**3 つ目の実装**です。受理すると、GNU tar の受け手は何も手に入らないのに
検算器だけが「そのファイルはある」と言うことになります。**v0.6.8 の拒否が正しかった。**

**2 実装で足りるかどうかは、2 実装では決められません。**
v0.6.7 で CI を 2 platform の matrix にした理由がそのまま働いた形です。

## 5. 止める理由が、どちらの実装で裏を取れるか

```
GNU tar 側でだけ根拠が取れる   11 件（v0.6.8 は 9 件）
bsdtar 側でだけ根拠が取れる     9 件
どちらでも取れていない          2 件（v0.6.8 は 3 件）
```

増えた 2 件が §4 の長さ 0 の `mtime=` / `uid=`、
減った 1 件が `pax-symlink-trailing-slash` で、**過剰拒否だったので受理側へ直しました。**
残る 2 件は、名前・指す先の上書きが 2 つ効く形の**片方の順序**です。

> **BusyBox は開発機にも CI にもありません。**
> そちらが BusyBox で裏を取ったと報告している結果は、**こちらでは追試していません。**
> `none` の 2 件がそれに当たります。

`raw-uname` / `raw-gname` の不正 UTF-8 は、**両 platform とも割れませんでした**
（GNU tar と python が同じ木を作り、検算器の見え方とも一致）。
**PAX 側は libarchive が locale 変換で落ちるのに、生ヘッダ側は落ちません。**

## 8. 次に確かめてほしいこと

1. **生ヘッダで、まだ読んでいない欄。** 数値欄（v13）と magic/version（v14）は見るようになりましたが、
   **`typeflag` 以外の固定長欄**——`linkname` の綴り・`uname`/`gname` の長さ・`prefix` の内容——は
   まだ形式ごとの読み分けをしていません。ここに同じ形の穴が残っていないか。
2. **`headerFormat` の判別そのもの。** magic 257..262 が `ustar\0` かだけを見ています。
   `ustar` のあとが NUL でない実装（star など）や、magic を書かないのに
   prefix を使う実装があれば、こちらの判別は間違っています。
3. **許可表から落とした型の扱い。** `3`/`4`/`6` を `ARCHIVE_UNSUPPORTED` にしました。
   実測では device は 2 実装とも作れず、FIFO は 2 実装とも作ります。
   **これを「範囲の外」と呼ぶのが妥当か**（`ARCHIVE_INVALID` にすべきか、受理すべきか）。
4. **長さ 0 の値の線引き。** いま「解釈する鍵は止める／それ以外は無視」です。
   GNU tar がどの鍵まで検査するのかを、こちらは 2 鍵でしか測れていません。
   **`size=` や `linkpath=` を含む網羅的な表**があれば知りたいです。
5. **BusyBox の結果。** `none` の 2 件（名前・指す先の上書きが 2 つ効く形の片方の順序）に加え、
   §1 の新しい材料を BusyBox で通すとどうなるか。
6. **`stableReasonCode` の粒度。** family 名は勧告どおりにしましたが、
   こちらの判断で `HEADER_FORMAT_PREFIX_CONFLICT` /
   `PAX_ZERO_LENGTH_NAME_AMBIGUOUS` / `PATH_TRAILING_SLASH_TYPE_CONFLICT` を足しています。
   **受け手が機械で分岐するのに、この粒度で足りるか。**
7. **受け手向けの `source-verifier-cli-result.v1` schema。** まだ作っていません
   （草案はいただいています）。**新しい公開契約なので、次の release で出すべきか**の判断。
