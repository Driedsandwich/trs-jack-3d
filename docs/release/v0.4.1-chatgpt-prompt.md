## 2. `test_counts.json` の `allPassed: false` を直した

v0.4.1 の値:

```
total 476 / skipped 0 / failed 0 / failedSuites 0 / exitCode 0 / allPassed true
runner vitest 4.1.10 / nodeVersion v22.22.3
generatedFromCommit 162f4cd7d93689a21b7d63260571926fee2b377b
testCommand "npx vitest run --reporter=json"
```

### なぜ生成側で止めなかったか

**「テストが落ちている間は件数を更新できない」という循環に戻したくないからである。**

件数の照合（`docs/TEST_RESULTS.md` ↔ `test_counts.json`）が落ちているとき、
件数を直すには `test:count` を回す必要がある。生成を止めると、その回せない状態から抜けられない。
**この循環が起きるのは生成側だけ**なので、生成は許して**配布を止める**。

| | 挙動 |
|---|---|
| `npm run test:count` | テストが落ちても件数を書く。**ただし `failed` / `exitCode` も同じ実行から記録する** |
| `npm run release:evidence` | `NOT_READY` でも evidence を書く（判定を残すため）。生成は止めない |
| `npm run release:stage` | **`allPassed !== true` を拒否する**（`--allow-not-ready` で回避できるが配布してはいけない） |

v0.4.0 の欠陥は「2 件落ちている時点で件数を取り、直したあと取り直さなかった」ことだった。
件数は変わらなかったので `total` を突き合わせる検査は通った。**`failed` と `exitCode` を
同じ実行から取るようにしたので、同じ形の見逃しは起きない。**

### `validation-results.json` の判定が 2 つに分かれた

```
artifactValidationStatus   PASS      ← artifact の形と意味が正しいか
releaseReadinessStatus     READY     ← release として配ってよいか
releaseReadinessReasons    []        ← NOT_READY のときは理由が入る
testEvidence               { total: 476, failed: 0, skipped: 0, exitCode: 0, allPassed: true }
```

**v0.4.0 は前者が PASS で後者が NOT_READY にあたる状態だった。**両者を突き合わせていなかった。
`releaseReadinessStatus` を見れば、形の検証だけで配布可と読む誤りが起きない。

そちらの release verifier では、**`artifactValidationStatus` ではなく
`releaseReadinessStatus` を配布可否の判定に使うこと。**

## 4. 検証ツールが `gh` を要求しなくなった

v0.4.0 では `--fetch github` が `gh api` を呼んでいた。
そちらの環境に `gh` が無く `spawnSync gh ENOENT` で `SOURCE_UNAVAILABLE` になった。
**判定は正しかったが、配った道具の network 経路が使えないままだった。**

Node 18 以降は `fetch` が組み込みなので外部コマンドは要らない。**同梱の道具はそのまま動く。**

```bash
node verifyReleaseSourceInputs.mjs --manifest source-input-manifest.json \
  --tag v0.4.1 --fetch github --scope source-input-scope.v1.json
```

実際に使う外部コマンドは 2 つだけになった。

```
git archive
git rev-parse
```

`gh` があってもなくても結果が同一であることを実測してある（PATH から `gh` を外して 29/29 一致）。
通信させたくなければ release ページの "Source code (tar.gz)" を展開して `--source` に渡す
（かぶる 1 階層は `--source` が剥がす）。

### `toolVersion` が全ての出口に入る

v0.4.0 では成功・不一致の出口にしか入っておらず、
そちらが保存した `SOURCE_UNAVAILABLE` の記録に版が無かった。
出力の通り道で入れるようにしたので、**4 経路すべてに入る。**

```
OK / MISMATCH / SOURCE_UNAVAILABLE / MANIFEST_UNAVAILABLE / NOTHING_TO_VERIFY
```

`TOOL_VERSION` は 2 → **3**。
`source-verification-result.json` の `tool.sha256` が同梱の script と一致することを確かめてから読むこと。

## 5. 次は v0.5.0 で schema versioning を是正する

**指摘のとおり、v0.3.0 → v0.4.0 で同じ `schemaId` / version のまま schema ファイルを変えた。**

```
half-plug-topology-profile.v2   6b13f5… → ecc48e…
event-sensitivity.v1            8d4b87… → b859a1…
topology-robustness.v2          9c2e3c… → 13a30e…
source-input-manifest.v1        b5b1ab… → 15a905…
```

こちらは「追加のみだから沈黙して壊れない」と書いたが、
**旧 schema を pin した consumer が拒否する時点で実質的に破壊変更**という読みのほうが正確である。
fail-closed である点は安全だが、同じ version が互換性を表していない。

v0.5.0 で次を上げる。

```
half-plug-topology-profile.v3
event-sensitivity.v2
topology-robustness.v3
source-input-manifest.v2
```

`contractMigration` へ旧版からの変更を記録し、versioning policy も文書化する。
**v0.4.1 では上げていない**（互換 patch に破壊変更を混ぜない）。

そちらは v0.5.0 で**必ず一度停止する**。`schemaVersion` の分岐を先に入れておくこと。

1. `SHA256SUMS` で exact byte 検証（23 件）
2. `trs-jack-3d-release-index.v1.json` から `release-lock-v0.4.1.json` を作る。
   **`artifactGenerationCommit` を単一値で照合しないこと**——この版でも 3 種ある
3. profile を取り込み直す。**`profileId` が変わっただけ**で、契約は 1 つも変わっていない
4. 配布可否の判定を `releaseReadinessStatus` へ切り替える（→ §2）
5. `verify:release-source-inputs` で入力 29 件を自分で検算する。**今度は `gh` が無くても動く**
6. production byte import を回し、結果を返す
