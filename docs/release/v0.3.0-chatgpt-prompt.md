## 1. **profile の取り込み経路は止まらない**（前回と違う）

破壊的変更は `topology-robustness` の 1 件だけである。

| artifact | schemaVersion | 前回からの変化 |
|---|---:|---|
| `half_plug_topology_profile.v2.*` | **2** | **変わらない** |
| `event-sensitivity` | 1 | 変わらない |
| `topology-robustness` | **2** | **1 → 2（破壊的変更）** |

**v0.2.0 のときは `schemaVersion` を見て必ず停止したが、今回はしない。**
profile を読む経路は前回のまま動く。止まるとすれば頑健性 artifact を読む側だけである。

そちらの現行コードは頑健性の窓の項目（`fromMm` / `toMm`）を読んでいないことを、
配布物の `topology-adapter.mjs` / `import-profile.mjs` で確認した（要約項目だけ使っている）。
**そのままでも動くはずだが、`schemaVersion` の分岐は入れておくこと。**
入れておかないと、次に窓を読み始めたときに黙って `undefined` を掴む。

## 2. 窓の端点を 3 つに分けた

| 旧（v1） | 新（v2） |
|---|---|
| `fromMm` | **`startMm`** |
| `toMm` | **`lastSampleMm`** |
| （無し） | **`endExclusiveMm`** |

**旧 `toMm` は「最後に当たった標本の位置」で、区間の終端ではなかった。**
同じ「終わり」という語で 2 つの違う量を指していた。

```
startMm        13.30   ← profile の nominalStartMm と一致
lastSampleMm   13.50   ← 観測の最後の点。**区間の終端ではない**
endExclusiveMm 13.52   ← **profile の nominalEndMm と一致する**
widthMm         0.22   ← endExclusiveMm − startMm
```

`windowEndConvention: "EXCLUSIVE"` を持たせた。
**`endExclusiveMm` と profile の `nominalEndMm` が一致することは、こちらの意味規則で機械的に守っている。**
UI で最後の標本と区間境界を混同しないこと。

対応表は `topology-robustness` の `contractMigration` にある。
`renamedFields[].from` を自分のコードに grep すれば、直す箇所が出る。

## 3. lock は索引から作る（**手で転記しない**）

`trs-jack-3d-release-index.v1.json` を同梱した。v0.2.0 では報告文から手で転記していた。

```
releaseTag              v0.3.0
releaseCommit           4c5fce8b23147dc03cd5b18ac855cc51e4c7b179
evidenceBuiltAtCommit   索引を作った時点の HEAD
artifactGenerationCommit 3966dc6cf693…   ← **profile の**生成 commit
```

```
TRS|JACK-TRS   trs-jack-3d:TRS|JACK-TRS:abca1dfb5b5f
               sha256 d18f91cd091a…   生成 commit 3966dc6cf693

TRS|JACK-TRRS  trs-jack-3d:TRS|JACK-TRRS:01ac02bdcb7b
               sha256 cf8507d3de48…   生成 commit 3966dc6cf693
```

**索引から引くこと。**上はその写しで、表に貼り直す過程で誤りが入りうる。

### ⚠ `artifactGenerationCommit` は 1 つではない

**この版では 3 種ある。**

```
3966dc6cf693  2 件
5900015f1b5f  2 件
b66a3017c650  3 件
```

release 工程が 2 段階だからである。profile の入力に感度 artifact が含まれるので、
**感度を作り直すとその入力が dirty になり `--release` が拒否する。**
先に感度・頑健性を確定してコミットし、そのうえで profile を生成する。
evidence はさらにその後に作られるので、また別の commit になる。

`artifactGenerationCommits[]` が完全な事実で、`assets[].generatedFromCommit` に個別の値もある。
**単一の値だけを見て照合すると、必ずどれかが食い違う。**

`releaseCommit` との一致も要求しないこと。artifact をコミットしてから tag を打つので、
artifact は必ず tag より前の commit から作られる。

## 4. 検証対象 9 件のうち 2 件は bundle に無い

`validation-results.json` の各対象に `distribution` を付けた。

```
RELEASE_ASSET   7 件
SOURCE_ONLY     2 件  ← bundle に入っていない
```

入っていないのはこの 2 つで、どちらも runtime 入力ではない。

```
artifacts/topology_search_difference_signal.json
artifacts/real_jack_comparison.json
```

**「9 件すべてを bundle だけで独立再検証できる」と読まないこと。**
できるのは `RELEASE_ASSET` の 7 件である。

## 5. 入力 28 件は自分で検算できる

`npm run verify:release-source-inputs` を新設した。
**こちらの自己申告を信じずに確かめるための道具である。**

```bash
# 通信しない。展開済みの source を渡す
node scripts/verifyReleaseSourceInputs.mjs --manifest source-input-manifest.json --source <dir>

# 手元に tag があるなら（これも通信しない）
node scripts/verifyReleaseSourceInputs.mjs --manifest source-input-manifest.json --tag v0.3.0

# 明示したときだけ GitHub から取る
node scripts/verifyReleaseSourceInputs.mjs --manifest source-input-manifest.json --tag v0.3.0 --fetch github
```

**「取れなかった」と「合わなかった」を潰していない。**

| status | exit | 意味 |
|---|---:|---|
| `OK` | 0 | 全件一致 |
| `MISMATCH` | 1 | 不一致・欠落・**記録漏れの入力** |
| `SOURCE_UNAVAILABLE` | 2 | source を取れなかった。**検証していないだけで、不一致ではない** |
| `MANIFEST_UNAVAILABLE` | 2 | manifest を読めなかった |
| `NOTHING_TO_VERIFY` | 2 | 入力 0 件。**何も見ていないのに OK と言わない** |

出力は `selfReported`（manifest がそう名乗っているだけ）と
`independentVerification`（その実行で計算し直した結果）を**別項目に分けてある**。

**read-only である。**書き込み API を 1 つも使わず、tar は展開せずメモリ上で読む。
外部コマンドは `git archive` / `git rev-parse` / `gh api` だけ。

こちらで v0.3.0 tag に対して実行し、**28/28 一致**した。同じことをそちらでも回せる。

## やること

1. `SHA256SUMS` で exact byte 検証（18 件）
2. `trs-jack-3d-release-index.v1.json` から `release-lock-v0.3.0.json` を作る。
   **`artifactGenerationCommit` を単一値で照合しないこと**（→ §3）
3. `topology-robustness` の `schemaVersion` 分岐を入れる。窓を読むなら
   `endExclusiveMm`（区間の終端）と `lastSampleMm`（観測の最後の点）を取り違えないこと
4. `verify:release-source-inputs` で入力 28 件を自分で検算する
5. production byte import を回し、結果を返す
