# trs-jack-3d v0.6.10 — 前回の指摘への回答と、次にお願いしたいこと

前回（v0.6.9 監査）の **P0 2 件・P1 3 件**に対応して v0.6.10 を公開しました。

この版では**こちらの誤りが 2 つ**あったので、先に書きます。
ひとつは**穴を開けたのがこちらの前回の変更**だったこと、
もうひとつは**「根拠が無い」と報告したものに実は根拠があった**ことです。

> **次回は控えを付けていただけると、こちらで照合できます。**

添付は公開物そのものです（28 ファイル・`shasum -c` が exit 0）。

## 1. 前回の指摘をどう直したか

### P0-A 長さ 0 の PAX 鍵が、鍵の分類を丸ごと迂回していた

```
同じ鍵で、値の長さだけを変える
  size=12            ARCHIVE_INVALID   ／ size=（長さ 0）        READ  ← 素通り
  SUN.holesdata=X    ARCHIVE_INVALID   ／ SUN.holesdata=        READ  ← 素通り
  ACME.weird=X       ARCHIVE_UNSUPPORTED ／ ACME.weird=          READ  ← 素通り
```

`SUN.holesdata=` は **bsdtar が exit 1 で拒む**のに受理していました。
32 入力の source に混ぜると `status OK / 32 of 32`。

**分類は値の長さで変わりません。**先に鍵で分類し、そのあとで値の長さを見ます。
`hdrcharset=` も同じ形で素通りしていました（そちらの fixture にあったもの）。

### P0-B 終端 zero block のあとを、一度も見ていなかった

zero block を 1 個置いた後ろに member を隠せました
（`OK 32/32`・未記録候補 0 件で、`sneaky.ts` はファイルの中に入っている）。
終端の印は zero block 2 個なので、そのあとに非 zero block があれば止めます。

### P1 過剰拒否 3 件

```
正当な old GNU sparse   typeflag S・345..499 は sparse map。型より先に形式を見ていたので
                        ARCHIVE_UNSUPPORTED ではなく ARCHIVE_INVALID になっていた
mtime=1.                小数点のあとに数字が無い形。2 実装とも受理するのに拒んでいた
冪等な directory の重複  2 実装とも同じ木を作るのに拒んでいた
```

directory は中身を持たないので「どちらが本物か」という問いが立ちません。
**通常ファイルの重複は今までどおり止めます。**

## 3. **長さ 0 の鍵の穴は、こちらが前回の版で開けたものです**

指摘された P0-A は、**そちらの前回の指摘に対応したときにこちらが作り込んだ**ものです。

v0.6.9 で「長さ 0 の値を早く返す」ようにしたとき、`path`/`linkpath` と数値鍵しか
記録しなくなりました。ところが**そのあとの allowlist と known-dangerous 検査は、
記録された鍵しか見ません。**結果として、**前の版では止まっていた鍵が素通りするようになりました。**

**直した箇所の下流に、同じ検査を通らない経路ができていないか**——
これが今回いちばん効いた観点だと思っています。

## 4. **「根拠が無い」と報告した 3 件に、実は GNU tar の警告がありました**

止める理由のうち根拠が取れないものを、こちらは一度 **8 件**と書きました。
**CI（ubuntu）が落として、3 件は GNU tar が警告を出していると分かりました。**

```
eoa-lone-zero-then-member   tar: A lone zero block at 3
eoa-lone-zero-then-junk     同上
zero-hdrcharset             tar: Ignoring unknown extended header keyword 'hdrcharset'
```

`A lone zero block at 3` は**この形をちょうど名指ししています**
（材料の並びとも一致: 0 起点で block 2 が zero block）。

**開発機の 2 実装だけを見て「根拠が無い」と書くと、根拠を過小に報告します。**
過大に報告するのと同じくらい、受け手の判断を誤らせます。

## 5. 止める理由 29 件の内訳

```
GNU tar 側でだけ根拠が取れる   15 件（v0.6.9 は 11 件）
bsdtar 側でだけ根拠が取れる     9 件
どちらでも取れていない          5 件（v0.6.9 は 2 件）
```

**残る 5 件のうち 3 件は、実装が割れているのではなく方針で止めています。**

| id | なぜ止めるか |
|---|---|
| `nonzero-size` | `size` は entry の見え方を変えるので解釈しない方針（v0.6.3〜） |
| `dup-regular-same-content` | 同じパスの通常ファイルが 2 回。どちらを検算したか言えなくなる（v0.6.1〜） |
| `dup-regular-different-content` | 同上 |
| `pax-path-then-gnu-longname` | 名前の上書きが 2 つ効く形の片方の順序。**BusyBox が要る** |
| `pax-linkpath-then-gnu-K` | 同上 |

**「実装が割れているから止めた」と書けないものは、方針で止めていると書きます。**
前の 3 件は、そちらが「これは過剰拒否では」と見るなら、こちらは反論材料を持ちません。

> **BusyBox は開発機にも CI にもありません。**下 2 件はそちらの報告に頼っています。

## 6. 止め方 65 か所すべてに、変わらない名前が付きました

`stableReasonCode` を全 throw 地点に付け、
**corpus の材料が `*_OTHER` を返したら試験が落ちる**ようにしました。

```
止まる材料 105 件 / *_OTHER 0 件
```

そちらの family 名に加えて、こちらの判断で
`END_OF_ARCHIVE_LONE_ZERO_BLOCK` / `PAX_KEY_DANGEROUS` / `PAX_KEY_UNSUPPORTED` /
`PAX_ZERO_LENGTH_VALUE_INVALID` / `DUPLICATE_PATH_CONFLICT` などを足しています。

> 一括で付けたとき **2 か所を第 3 引数として書いてしまい**、
> `ArchiveInvalid(reason, detail)` は 2 引数なので**黙って無視されていました。**
> corpus を全件流す検査が `*_OTHER` として拾って気づきました。

## 8. `profileId` は変わりますが、モデルの数値は同じです

```
v0.6.9   trs-jack-3d:TRS|JACK-TRS:6209fa3bd888
v0.6.10  trs-jack-3d:TRS|JACK-TRS:e3a230f2c600

v0.6.9   trs-jack-3d:TRS|JACK-TRRS:76904bf4730a
v0.6.10  trs-jack-3d:TRS|JACK-TRRS:8d64e23c190d
```

**動いた原因は版数上げ（`package-lock.json`）です。**
検算ツールは配布物ですが**入力ではない**ので、v14 → v15 にしても digest を動かしません。

**モデルの数値は変わっていません。**葉ノードまで平坦化した実測です。

```
TRS   葉 2267 件 → 由来まわりの差 8 件 / モデル数値の差 0 件
TRRS  葉 3130 件 → 由来まわりの差 8 件 / モデル数値の差 0 件
```

対照として `jack.fullInsertionDepth` を 14.0 → 14.001 に変えると、
**モデル数値の差が TRS 80 件**出ます。

`profileId` は**この文書から転記せず、同梱の
`trs-jack-3d-release-index.v1.json` から引いてください。**

## 9. 次に確かめてほしいこと

1. **直した箇所の下流。** §3 のとおり、前回の修正が次の穴を作りました。
   今回の修正（鍵の分類を先に・終端のあとを見る・型を先に）でも同じことが起きていないか——
   **「早く返す」経路が、後段の検査を飛ばしていないか**を見てほしいです。
2. **終端の扱いの境界。** いま「終端 zero block のあとに非 zero block があれば止める」です。
   終端が 1 個だけで物理 EOF・zero block が 3 個以上・詰め物が blocking factor を超える、
   といった**正当な形を落としていないか**（npm の実 tarball 600 本では 0 件でしたが、
   母集団が npm に偏っています）。
3. **長さ 0 の値の線引き。** `uname` / `gname` / `comment` / xattr は長さ 0 でも通しています。
   **これらが見え方を変えないという前提が本当か**（`hdrcharset` は変えるので止めました）。
4. **`stableReasonCode` の粒度。** 65 か所を 30 種類ほどに畳んでいます。
   受け手が機械で分岐するのに、**粗すぎる／細かすぎる**ところがないか。
5. **BusyBox の結果。** `none` 5 件のうち 2 件と、§1 の新しい材料。
6. **こちらの方針 3 件が過剰拒否でないか**（§5 の表の上 3 行）。
   実装が割れないのに止めているので、**そちらの目で見て妥当か**を聞きたいです。
7. **受け手向けの `source-verifier-cli-result.v1` schema。** まだ作っていません
   （草案はいただいています）。**次の release で出すべきか**の判断。
