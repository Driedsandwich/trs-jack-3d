# trs-jack-3d v0.6.6 — 前回の指摘 4 件を直した版の確認

前回の監査（v0.6.5・2026-08-08）で出た **P0 3 件と P1 を、こちらで確かめてから直した**版です。
添付は公開した release asset **28 ファイル**そのものです。

**今回のパケットは checksum が合いました。**前回は `.sha256` が別ビルドの値でしたが、
今回は `shasum -c` が exit 0 で通っています。

## 1. 添付をどう扱うか

```
28 ファイル / 1.8 MB
SHA256SUMS      27 件ぶんの checksum（自分自身は含まない）
```

**まず `shasum -a 256 -c SHA256SUMS` を通してください。**
こちらでは公開物を取り直して 27/27 OK でした。合わなければ、そこから先は読まなくて構いません。

## 2. **v0.6.5 は、正当な archive を 2 種類拒んでいました**

**受け手に直接影響するのはこちらです。先に書きます。**

```
再現（v0.6.5 実測）
  GNU の長い linkname（K ヘッダ）
    検算 v10  ARCHIVE_INVALID — 「. を含む entry がある」
    GNU tar / bsdtar / BusyBox / python   4 実装すべて展開できる

  PAX の linkpath
    検算 v10  ARCHIVE_INVALID — 「受け入れていない鍵がある: linkpath」
    4 実装すべて展開できる

直したあと
  どちらも通る
```

`K` は**分岐そのものが無く**、`K` ヘッダ自身の名前 `././@LongLink` が
正規化検査に当たって落ちていました。`linkpath` は allowlist に入れ忘れです。

### **お願い: v0.6.5 で出た `ARCHIVE_INVALID` を取り直してください**

**そちらが v0.6.5 の道具で別の archive を検算していた場合、
`ARCHIVE_INVALID` が出ていても archive の欠陥ではなく、こちらの誤検知だった可能性があります。**

該当するのは、**長いシンボリックリンクの指す先を持つ archive**です
（GNU tar の `K` ヘッダ、または PAX の `linkpath` を使うもの）。
`v0.6.6` の道具で取り直してください。

> **正当な archive を拒む欠陥は、これで 2 版続けてです**（v0.6.4 は独立した 2 つの member が
> それぞれ長い名前を使うだけで拒んでいました）。**「実物が通る」確認では見つかりません**——
> この repo の実物は最長パス 95 文字で、これらの機構を使わないためです。
> **corpus に「通す」材料を 3 つ足しました。**止める材料しか無ければ、次も同じ形で見落とします。

## 3. 誰も展開できない archive を、まだ受理していました

```
再現（v0.6.5 実測）
  自分自身を指す hardlink（root/self -> root/self）
    検算 v10  status OK / 32 件中 32 件一致 / 未記録 0
    bsdtar    exit 1 — Skipping hardlink pointing to itself
    python    KeyError: linkname 'root/self' not found

  ディレクトリを指す hardlink（root/hdir -> root）
    検算 v10  status OK
    bsdtar    exit 1 — Can't create 'root/hdir': Operation not permitted

直したあと
  どちらも ARCHIVE_INVALID
```

1 つ目は **この entry の名前を先に控えていた**ため、自分を指すリンクが
「指す先が在る」と判定されていました。2 つ目は「名前が在るか」しか見ていませんでした。
**hardlink は通常ファイルにしか張れません。**

`linkpath` を解釈するようにしたので、**`linkpath` で hardlink の指す先を
存在しない場所へ上書きする形**も止まります。

## 4. **手元では確かめられなかった 2 件を、構造の理屈で直しました**

```
PAX の値が読めない（uid=abc / mtime=abc / atime=nan / ctime=1e999）
  検算 v10  status OK      bsdtar exit 0    python exit 0    ← こちらの 2 実装は通す
  （そちらの GNU tar は exit 2 — Malformed extended header）

中身を持てない型に本体がある（type 5 で size≠0）
  検算 v10  status OK      bsdtar exit 0    python exit 0    ← こちらの 2 実装は通す
  （そちらの GNU tar は exit 2、BusyBox は exit 1、libarchive は exit 1）
```

**この 2 件は、こちらの 2 実装が検算器と同じ答えを返します。**
GNU tar と BusyBox はこの環境に無いので、**そちらの結果は確かめられていません。**

**それでも直したのは、構造として理屈が立つからです。**

- 値が読めない PAX は、**「view を変えない鍵だから通す」という v0.6.5 の理屈を崩します。**
  その理屈は値が読める前提に乗っていて、読めなければ読み手の挙動は決まりません。
- 中身を持てない型に本体があると、**読み手がその本体を読み飛ばすかどうかで、
  その先の解釈が丸ごとずれます。**1 個の entry の問題では済みません。

**「監査がそう言ったから直した」ではありません。**確かめられなかったことは
`docs/release/verify-tool-v11-notes.md` の §4 に節として分けてあります。

> **`type 5 with body` について、こちらの実測はそちらと 1 点違いました。**
> そちらは libarchive exit 1 と報告していますが、**こちらの bsdtar 3.5.3
> （libarchive 3.7.4）は exit 0 で通します。**版の違いか、材料の作り方の違いだと思います。
> 結論（accepted subset へ入れない）は同じです。

## 7. `profileId` は変わります。**原因は版数上げです**

```
v0.6.5  trs-jack-3d:TRS|JACK-TRS:df6244796ab5
v0.6.6  trs-jack-3d:TRS|JACK-TRS:4874b63082e9

v0.6.5  trs-jack-3d:TRS|JACK-TRRS:e5dd0a0a92a4
v0.6.6  trs-jack-3d:TRS|JACK-TRRS:4998389a40e4
```

**この文書から転記せず、添付の `trs-jack-3d-release-index.v1.json` から引いてください。**

**動いたのは `package-lock.json`（入力）が版数上げで変わったからです。**
検算ツールは配布物ですが**入力ではない**ので、そちらは digest を動かしません。

**モデルの数値は変わっていません。**葉ノードまで平坦化した実測です。

```
TRS   葉 2267 件 → 由来まわりの差 10 件 / モデル数値の差 0 件
TRRS  葉 3130 件 → 由来まわりの差 10 件 / モデル数値の差 0 件
```

この比較が「全部を由来に寄せているだけ」ではないことも確かめてあります——
`fullInsertionDepthMm` を 14 → 14.001 に変えると **「モデル数値の差 1 件」**になります。

区間・event の数も同じです（TRS 23/32・TRRS 30/36）。`IV028` も `ASSUMPTION` のままです。

同梱の検算ツールは `toolVersion: 11` です。
壊れた tar の材料は **50 個 9 種類 → 63 個 10 種類**。

## 8. 次に確かめてほしいこと

優先順に並べます。**指摘は反例（再現手順・期待した結果・実際の結果）を添えてください。**
こちらで再現できたものだけ直します。**再現できなかったものは、そう書いて判断を分けます。**

1. **v0.6.6 も、正当な archive を拒んでいないか。**
   **2 版続けて過剰拒否を出しているので、ここが最優先です。**
   corpus に「通す」材料を 3 つ足しましたが、まだ足りないはずです。
   **ふつうの tar が作る archive で、v0.6.6 が拒むものを探してください。**
   star・古い GNU tar・古い bsdtar・非 ASCII のパス・sparse file・
   大きな uid/gid・`SCHILY.*` 系の他の鍵などが候補です。

2. **hardlink の検査が厳しすぎないか。**
   「指す先がここまでの entry に在る通常ファイルであること」を要求しています。
   **正当な tar がこれを満たさない hardlink を書く場面**はありますか
   （例: 先に書かれた hardlink を指す hardlink の連鎖）。

3. **PAX の値の文法が厳しすぎないか。**
   `uid`/`gid` は `[0-9]+`、時刻は `[0-9]+(\.[0-9]+)?` にしています。
   **負の時刻**（1970 年より前）や、**GNU tar が書く base-256 形式**を
   拒んでしまわないか見てください。

4. **oracle をまだ増やせていません。**bsdtar と python の 2 実装のままです。
   **上の 4（確かめられなかった 2 件）は、そのために確かめられませんでした。**
   GNU tar を必須 oracle に足すべきという指摘は受け入れています。
   **こちらの環境に入れずに済む方法**（例: 判定を Docker で回す・CI で回す）で
   現実的な案はありますか。

5. **`source-verifier-cli-result.v1` の項目を詰めたい。**
   そちらの案（tool / status / exitCode / stableReasonCode / origin / counts /
   unrecordedInputCandidates / scopeDefinition / appliedResourceLimits / oracles）を
   ほぼそのまま採る方向です。**受け手として実際に使う立場から、
   足りない項目・要らない項目**を指摘してください。

6. **意図した挙動として残した 2 つ**（9 MB 超の entry・scope 配下の正当な hardlink）は、
   この判断で問題ありませんか。**下流が困る形になっていませんか。**

**この版の弱点として、こちらが自覚しているもの:**

- **oracle が 2 実装まで**（GNU tar・BusyBox は入っていない）。
  **確かめられない指摘が実際に出た**
- **正当な archive を拒む欠陥が 2 版続けて出た**。corpus の「通す」側がまだ薄い
- PAX は allowlist にしたが、**通す鍵と値の文法はこちらの理屈**であって外部の検証を受けていない
- 検査の側にも版ごとに穴があった（v8 は片方向、v9 は oracle 1 実装）
- `verifiedPhysical` は **実測記録 0 件のまま**で、`ASSUMPTION` が 54 件ある
- 導通・音響の実測はしていない
