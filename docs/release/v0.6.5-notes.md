# v0.6.5 — **schema は 1 本も上げていません。下流はどこでも止まりません**

## ⚠ 先に読むところ

### 1. **v0.6.4 の検算ツールには、受け手を誤らせる欠陥が 4 つありました**

外部監査（2026-08-08）が反例を出し、こちらで全件再現してから直しています。
GNU tar が手元に無いので、**bsdtar 3.5.3（libarchive 3.7.4）と Python 3.14 の `tarfile`**
の 2 実装で測りました。

**先頭 1 階層を、ディレクトリか確かめずに剥がしていた**

GitHub の tarball は `<repo>-<sha>/` を頭に付けるので、検算器はそれを剥がします。
v0.6.4 は「全部が同じ頭で始まる」だけを見ており、**その頭が通常ファイルでも剥がしていました。**

```
regular root = ROOTFILE ／ regular root/... が 2 件
  検算 v9  status OK・files に**空文字の key** が残る
  bsdtar   exit 1（root は directory ではない）
  python   NotADirectoryError
```

**どの展開器でも作れない木を「source として受理」していました。**

**受理するのに、誰も展開できない archive があった**

```
正常なファイル 2 件 ＋ 指す先の無い hardlink
  検算 v9  status OK / 2 件中 2 件一致 / 未記録 0
  bsdtar   exit 1 — Hard-link target not found
  python   KeyError: linkname not found
```

**これは差分試験の足場になります。**「展開できない archive は比べようがない＝合格」と
数えていたので、ここを通すと**見えないファイルを混ぜられます。**

**PAX の `path` に入れた NUL を切り捨てていた**

PAX のレコードは長さで区切るので、NUL は詰め物ではなく値の一部です。
v0.6.4 は固定長ヘッダ欄と同じ関数で読んでいたため、NUL 以降を黙って捨てていました。
bsdtar も切り捨て、python は展開に失敗します——**実装ごとに結末が割れます。**

**PAX の denylist が閉じていなかった**

```
PAX x: SUN.holesdata=…（Solaris の sparse map）
  検算 v9  status OK（未知の鍵として無視）
  bsdtar   exit 1 — Parse error で archive ごと拒否
  python   展開できる
```

数え上げでは閉じないので、**通す鍵を並べる形（allowlist）へ変えました。**
通す鍵は実物を数えてから決めています（GitHub の tarball は `g:comment` だけ、
macOS の `tar` は `x:mtime` と `x:LIBARCHIVE.xattr.*` / `x:SCHILY.xattr.*`）。

### 2. **v0.6.4 は、正当な archive を拒んでもいました**

v0.6.4 で入れた「同じ member に上書きが 2 つ効いたら止める」に、戻し忘れがありました。

```
独立した 2 つの member が、それぞれ長い名前を 1 回ずつ使う
  検算 v9  ARCHIVE_INVALID（二重の上書きだと誤認）
  bsdtar   2 件とも展開する
  python   2 件とも展開する
```

**この repo の実物では踏みません**——最長パスが 95 文字で、long name 機構を使わないためです。
**「実物が通る」だけでは、過剰拒否は見つかりません。**

v0.6.4 を使って**他の repo の archive**を検算していた場合、
`ARCHIVE_INVALID` が出ていても**それは archive の問題ではなかった**可能性があります。

### 3. 差分試験そのものを直しました

v0.6.4 の差分試験は `tar` **1 実装だけ**を機械で強制していました。
**oracle が持つ癖と同じ癖を検算器が持っていると、差分は出ません。**実測:

```
PAX path の NUL 切り捨てを v0.6.4 の形へ戻す変異
  差分試験（bsdtar のみ）  0 件が落ちる  ← bsdtar も同じく切り捨てるため
  差分試験（+ python）     1 件が落ちる  ← 2 実装目で初めて割れる
```

v0.6.5 からは **bsdtar と python tarfile の両方**を必須にし、
**2 つが違う木を作る archive は受理しません。**（GNU tar・BusyBox はまだ入っていません。）

あわせて 3 つ直しました——展開失敗を「合格」と数えていた／中身を UTF-8 文字列で比べていた
（不正バイトが U+FFFD に潰れて一致して見える）／剥がした頭を `endsWith` で推測していた。

**強化した試験が、監査の指摘外でもう 1 件見つけました** —
GNU long name のあとに entry が無いまま終わる archive を v0.6.4 は受理していましたが、
`tar` は `Damaged tar archive` で拒みます。

### 4. `profileId` が変わりました。**lock を作り直してください**

```
v0.6.4  trs-jack-3d:TRS|JACK-TRS:104e6a87aa90
v0.6.5  trs-jack-3d:TRS|JACK-TRS:df6244796ab5

v0.6.4  trs-jack-3d:TRS|JACK-TRRS:d8d7a2930de1
v0.6.5  trs-jack-3d:TRS|JACK-TRRS:e5dd0a0a92a4
```

**この文書から転記せず、同梱の `trs-jack-3d-release-index.v1.json` から引いてください。**

**動いた原因は版数上げ（`package-lock.json`）です。**検算ツールは配布物ですが
**入力ではない**ので、そちらは digest を動かしません。

**モデルの数値は変わっていません。**葉ノードまで平坦化した実測です。

```
TRS   葉 2267 件 → 由来まわりの差 10 件 / モデル数値の差 0 件
TRRS  葉 3130 件 → 由来まわりの差 10 件 / モデル数値の差 0 件
```

この比較が「全部を由来に寄せているだけ」ではないことも確かめてあります——
`fullInsertionDepthMm` を 14 → 14.001 に変えて同じ比較をすると
**「モデル数値の差 1 件」**になります。


v0.6.4 の過剰拒否は corpus では見つかりませんでした。

## 変わっていないもの

- **モデルの数値**。接点位置も走査結果も同じです（上の葉ノード比較）。
- **`verifiedPhysical` は `false`**。実測記録は依然 **0 件**で、それが正しい状態です。
- 過去 release の asset。**v0.1.0 以降の 321 件すべて byte 一致**であることを、
  再生成の段ごとに対照つきで実測しています。
- `ARCHIVE_INVALID` は v1 の自己申告 schema では表現できないままです。
  **受け手向けの CLI 結果 schema は、まだ作っていません。**

## まだやっていないこと

- **実測が 1 件も来ていません。**ジャック内部の接点位置は全部仮定のままです。
- **導通測定も音響測定もしていません。**
- 受け手向けの `source-verifier-cli-result` schema の新設。
- annotated tag への署名。
- **`tar` の oracle が 2 実装まで**です。GNU tar・BusyBox では確かめていません。
- 入力の閉包検査は `import` グラフと文字列リテラルの静的走査の 2 本立てで、
  動的 `import()`・変数で組み立てたパス・環境変数経由は見えません。
- 検算ツールの強化は **試験した範囲まで**です。**すべての細工に耐えることは示していません**
  ——v5 で 3 つ、v6 で 2 つ、v7 で 3 つ、v8 で 3 つ、v9 で 4 つ見落としていました。
  **v8 と v9 では、検査の側（差分試験）にも穴がありました。**
