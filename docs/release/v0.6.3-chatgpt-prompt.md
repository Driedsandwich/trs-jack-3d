## 1. 前回の指摘 4 件をどう直したか

**捏造・誤検知は 0 件でした。指摘は全件実在しました。**

指摘 1〜3 はどれも同じ形の欠陥です——**「検算が見た source の中身」と
「ふつうに `tar` で展開してできる中身」が食い違う。**
`shasum` を通しても意味がなくなるので、どれも P0 として扱いました。

### P0-1 — PAX の上書き指示に「従わない」だけで、止めてもいなかった

v0.6.2（`toolVersion` 7）は PAX（`x` / `g`）entry を「中身をファイルとして拾わない」ように
していました。**しかし PAX は後続 entry の意味を変えられます。**

```
再現（v0.6.2 実測）
  ヘッダの名前 root/file.txt ／ PAX path=root/other.txt ／ 中身 EXPECTED
    検算 : file.txt = EXPECTED を「source にあった」と言う     status OK
    展開 : root/other.txt ができる。root/file.txt は存在しない

  ヘッダの size 8 ／ PAX size=4 ／ 中身 ABCDEFGH
    検算 : file.txt = ABCDEFGH（8 バイト）                     status OK
    展開 : root/file.txt = ABCD（4 バイト）

直したあと
  path=      → 解釈する（展開と同じ view になる）
  size=      → ARCHIVE_INVALID
```

**拾わないことと、無かったことにするのは別でした。**

v0.6.3 は PAX のレコードを読みます。**`path=` は拒まずに解釈します**——
GNU tar が長いパスに使う正当な機能なので、拒むと実物が通らなくなるためです。

```
止める鍵   size / linkpath / hdrcharset / SCHILY.realsize / GNU.sparse.*
通す鍵     path（解釈する）／ comment・mtime・SCHILY.xattr.* など見え方を変えないもの
```

読めない形式（長さ欄が無い・改行で終わらない・`=` が無い）も止めます。
**読めないものを黙って飛ばすと、そこに何が書いてあっても通ってしまう**ためです。

> **PAX を完全に実装する道は採っていません。**sparse や `linkpath` まで正しく扱う面積は、
> この道具が引き受けるべき量を超えます。**意味を変える鍵があったら止める**ほうを選びました。

### P0-2 — 読み飛ばす entry に、正規化の検査をかけていなかった

v0.6.2 は「リンクやディレクトリの**名前も覚える**」ようにしましたが、
正規化の検査（`.` を含む・空のパス要素）は**通常ファイルにしかかけていませんでした。**

```
再現（v0.6.2 実測）
  regular root/file.txt        = FIRST          ← 検算はこちらを見る
  symlink root/./file.txt -> target.txt         ← 別の綴りなので衝突しない扱いだった
  regular root/target.txt      = SECOND
    検算 : file.txt = FIRST   status OK
    展開 : root/file.txt は symlink になり、辿ると SECOND

直したあと
  ARCHIVE_INVALID
```

v0.6.3 は**すべての entry 型に、同じパス検査を先にかけます。**
ディレクトリの末尾スラッシュだけは tar の表記なので剥がしてから見ます。

### P0-3 — パスの前後の空白が消えていた

v0.6.2 はヘッダの文字列を、数値欄と同じく `.trim()` していました。

```
再現（v0.6.2 実測）
  ヘッダの名前 "root/file.txt␠"（末尾に空白）
    検算 : root/file.txt を検証            status OK
    展開 : "root/file.txt␠" という別のファイルができる

直したあと
  ARCHIVE_INVALID
```

数値欄（実装によって空白で詰められるので `trim` が要る）とパス欄（NUL 終端を落とすだけ）を
分けました。パス要素の前後に空白があれば止めます。
**途中の空白は許します**——`my file.txt` は正当な名前です。

### P0-4 — 生成器が、入力に宣言していないファイルを読んでいた

**これは v0.6.2 でこちらが入れた依存です。**前回の指摘「空の予測での読み替え」を直すために
`artifacts/real_jack_comparison.json` を読むようにしたのですが、
このファイルは入力の範囲（`source-input-scope.v1.json`）に入っていません。

```
再現（v0.6.2 実測）
  real_jack_comparison.json の中身を変える
    → 判定に使う予測が変わる
    → inputDigest は動かない
    → 受け手の検算は status OK / 32 of 32 / 未記録 0 件 のまま
```

直し方は「読む先を入力に足す」ではなく「**読まなくて済むようにする**」を採りました。
`artifacts/` は生成物なので、入力にすると自己参照になります（scope の `excludedOutputs`）。

**判定に使った予測そのものを、配布物へ記録します。**添付の profile で確認できます。

```
modelLimitations.physicalVerificationRef の末尾
  TRS   predicted=RING_BREAK_OPEN_DEPTH_MM:8.06,TIP_BREAK_OPEN_DEPTH_MM:12.02
  TRRS  predicted=L_FIRST_CONTACT_SHOULDER_GAP_MM:2.14,RING_BREAK_OPEN_DEPTH_MM:8.48,TIP_BREAK_OPEN_DEPTH_MM:11.92
```

検証側は、記録された値と profile の `events` から再計算した値が **1e-6 を超えてずれたら error** です。
`real_jack_comparison.json` は「あれば追加で見る第二の意見」に降格しました——
**無くても通り、あって食い違えば error を足します。**

`import` を辿る閉包検査だけでは、この依存は見えませんでした
（`readFileSync` でパスを直書きする経路は import グラフに現れません）。
**直接のファイル読み込みも静的に走査して照合する**テストを足しています。

## 2. 期待値を手で書くのをやめ、実際の展開を oracle にしました

**指摘 P0-1 の反例は、材料が前から手元にありました。**

`pax-x-path` という壊れた tar は **v0.6.0 から corpus に置いてあり**、それでも落ちませんでした。
期待値が「PAX ヘッダをファイルとして拾っていないか」だったからです。

**材料は正しく、判定基準がコードと同じ思い違いを共有していました。**
期待値を人が書く限り、この形の見落としは何度でも起こります。

そこで、同じ tar を `tar` コマンドで実際に展開し、できた木と比べる形にしました。

```
要件はひとつだけ
  検算器が読めたなら、その各キーは、展開してできた通常ファイルとして
  同じ中身で存在しなければならない。
  止まった（ARCHIVE_INVALID）なら、食い違いは起こりえないので合格。
```

**何を拒むべきかを人が決めなくてよい**のが要点です。参照実装との差分がそのまま欠陥になります。

```
食い違いが起きた件数   0（正常な tar・26 個 6 種類の壊れた tar のすべてで）
変異試験              PAX 検査を外すと 4 件、パス欄の trim を戻すと 1 件、
                     正規化検査を通常ファイル限定に戻すと 1 件が落ちる
```

**塞ぎすぎていないことも実測しています。**最初の PAX 実装は、実物の macOS `tar` が作った
tar.gz を弾きました（レコード長をバイトでなく文字で数えていた・`SCHILY.` を一括で拒んでいた）。
どちらも直したうえで、実物の GitHub tarball が通ることを確かめています。

```
v0.5.2 の tarball   246 ファイル（pax_global_header 1 件を含む）
v0.6.2 の tarball   284 ファイル（同上）
```

## 5. 検算ツールが v8 になりました

添付の `verifyReleaseSourceInputs.mjs` の出力は `toolVersion: 8` です。

```
使い方（network 不要）
  node verifyReleaseSourceInputs.mjs --manifest source-input-manifest.json --source <source archive か展開済みディレクトリ>

こちらでの実測
  正常な source    status OK       32 件中 32 件一致 / 未記録 0
  入力を1つ改竄     status MISMATCH 31 件一致 / scripts/measurementGate.mjs を名指し
```

**この道具が保証するのは「配布物に記録された入力の sha256 が、tag の source と一致するか」だけです。**
こちらの自己申告が正しいことも、モデルが正しいことも証明しません。

**塞いだつもりで残っていた穴を、版ごとに数えておきます。**

```
v5 → v6   3 つ（同名 entry の後勝ち・ディレクトリ入力の symlink ループ・圧縮入力の上限なし）

v7 → v8   3 つ（PAX の上書き・読み飛ばす entry の正規化漏れ・パス末尾の空白）
```

**どれも外部監査の指摘です。**「すべての細工に耐える」ことは示していません。

## 6. 次に確かめてほしいこと

優先順に並べます。**指摘は反例（再現手順・期待した結果・実際の結果）を添えてください。**
こちらで再現できたものだけ直します。

1. **実展開との差分試験そのものに穴がないか。**
   `tar` コマンドを oracle にしていますが、`tar` の実装差（GNU / bsdtar / busybox）で
   結論が変わる細工はありますか。oracle が 1 つしかないことが弱点になっていませんか。

2. **PAX の「止める鍵」の一覧に漏れがないか。**
   `size` / `linkpath` / `hdrcharset` / `SCHILY.realsize` / `GNU.sparse.*` を止め、
   `path` は解釈しています。**この分け方で view が変わる鍵が他にありませんか。**
   `path` を解釈する実装自体に、長さ・エンコーディング・NUL の扱いで穴はありませんか。

   **両方を同時に書き換えれば一致してしまいます。**この経路をどう塞ぐべきですか
   （台帳は意図して入力から外しています——記録が増えても過去の artifact の digest を
   動かさないため）。

4. **入力の閉包検査に、まだ見えない経路がないか。**
   `import` グラフと、相対パスの文字列リテラルの静的走査の 2 本立てです。
   動的な `import()`・変数で組み立てたパス・環境変数経由は見えません。
   **実際に危ないものが残っていますか。**

5. **`verifiedPhysical` の条文（`docs/VERIFIED_PHYSICAL_GATE.md` v2・全 10 条）に
   抜け道がないか。**現在 `false`・記録 0 件です。
