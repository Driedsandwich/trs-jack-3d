# trs-jack-3d v0.6.16 — 監査の P0 2 件と P1 5 件への対応

**いただいた指摘は全件実在しました。**とくに P0-1 は、こちらの release 工程の
根幹が抜けていたもので、**指摘されるまで 3 つの門が全部「整合している」と言っていました。**

添付は公開物そのものです（29 ファイル・`shasum -c` が exit 0）。

## 1. P0-1 — **v0.6.15 は v0.6.14 のテスト証拠で `READY` を名乗っていました**

そちらの指摘どおりです。公開物を開いて確かめました。

```
v0.6.15 が配った test_counts.json    total 1236 / generatedAt 2026-08-12
                                     generatedFromCommit 1c79e059…
                                     ↑ **v0.6.14 の第2段のコミット**
v0.6.15 が配った validation-results  testEvidence.total 1236 / READY
v0.6.15 の tag 時点の CI             1304 件 / 32 ファイル / 失敗 0
v0.6.15 の release notes             1304 件
```

**なぜ 3 つの門が全部通したかまで測りました。**

```
check:vacuity      byFile を「これ以上減ってはいけない下限」として使う
                   → 1304 ≥ 1236 なので通る（**空振り検査としては正しい**）
check:doc-numbers  docs/TEST_RESULTS.md と test_counts.json を突き合わせる
                   → **どちらも古いので一致する**
release:evidence   allPassed / failed / exitCode しか見ない
                   → 古いかどうかは一度も見ていない
```

**一致は現在性の証拠になりません。古いもの同士は仲良く一致します。**
そちらの「`check:vacuity` は floor semantics のまま維持し、freshness 根拠には使わない」
という切り分けは、そのまま採りました。

### 変異対照（v0.6.15 が実際に配った 1236 件の証拠を戻して実測）

```
                             v0.6.15 の門    v0.6.16 の門
check:vacuity                   exit 0          exit 0（下限のまま。これは正しい）
check:test-evidence-current     （無い）        **exit 1**
release:evidence                READY           **NOT_READY**
release:stage                   exit 0          **exit 1**
```

**旧実装は 3 経路とも素通りしました。**これが v0.6.15 の出荷経路そのものです。

公開済みの asset は上書きせず、
[`docs/ERRATA.md`](https://github.com/Driedsandwich/trs-jack-3d/blob/v0.6.16/docs/ERRATA.md) §13 で
**`NOT_READY` へ再分類**しました。受け手への影響は限定されます——profile の数値・区間・event・
`profileId` は変わらず、**使えないのは `test_counts.json` と `validation-results.testEvidence` だけ**です。

## 2. 門を 2 つに分けました。**役割が違います**

そちらの指示は「`release:evidence` と `release:stage` の両方がこの check を必ず実行」でした。
**実行はさせましたが、同じことをさせていません。**理由があります。

```
release:stage     **実測**して total / byFile / skipped / failed / failedSuites /
                  exitCode / allPassed を完全一致で突き合わせる
                  （byFile も下限にしない——増えたときも止める）
release:evidence  **由来**を見る。その証拠を取ってから、テストに効くファイルが
                  commit 間で動いていないか／未コミットで触っていないか
```

**`release:evidence` でテストを回すと、二度と `READY` にできなくなります。**
この工程は `test_counts.json` が指す成果物（索引・検証結果）を**これから書くところ**なので、
いま測ると「まだ書いていない索引と食い違う」失敗を数えます。実測で確認しました。

由来だけでも v0.6.15 は止まりました——`test/` が 4 コミットぶん動いていたためです。
**実測の門は配布側に置けば足ります。**

`validation-results` へ `testCountsSha256` / `testCountsGeneratedFromCommit` /
`testCountsGeneratedAt` を記録しました。v0.6.15 まで件数しか写しておらず、
**その件数がどの版の実行かは記録に無かった**ためです。

## 3. P0-2 — 道具が、自分の配った schema に反していました

```
実測（公開した v0.6.15 の道具そのもの）
  --source も --tag も渡さない   SOURCE_UNAVAILABLE / SOURCE_UNAVAILABLE_OTHER
  GitHub 取得中に fetch が失敗    同じ
```

どちらも同梱 schema の 80 種類の enum に**無い値**です。
**v0.6.15 で enum へ狭めたときに、名前を付け忘れた経路が受け皿へ落ち続けていました。**

配線しました（`SOURCE_FETCH_FAILED` / `SOURCE_FETCH_TIMEOUT` / `CLI_ARGUMENTS_MISSING`）。
そのうえで**出口に関門**を置き、契約を破る出力は**そもそも出しません**。

```
JSON を出さず、終了コード 3 で止まる
  status が CLI_STATUS_META に無い／exitCode が表と食い違う／
  OK なのに理由が付いている／非 OK なのに catalog の名前が無い／
  catalog の status と実際の status が違う
```

**終了コードを 3 にした理由。**例外のまま落とすと Node は 1 で終わり、
**`MISMATCH` と見分けが付きません**——stdout が空なのに終了コードだけ「不一致」に見えるのが、
いちばん悪い読まれ方です。3 はどの status の終了コードとも重なりません。

**個々の経路を直しても、次に足す経路でまた同じことが起きます。出口は 1 つなので、そこで見ます。**

`toolVersion` は **19**。止め方の名前は 80 → **82 種類**。

> **配布 schema のうち道具から決まる部分は、生成するようにしました。**
> v0.6.15 は enum を手で貼った箇所が残っており、**`usage` 族を 1 つ足しただけで
> 正常な `OK` の出力まで自分の schema に落ちました**（7 経路すべてで実測）。

## 4. **「到達しない」と宣言した 8 件のうち 4 件は、実経路でした**

そちらの再分類をそのまま採りました。4 件とも依存注入で踏めることを確かめています。

```
SOURCE_GIT_ARCHIVE_FAILED   PATH の先頭に偽 git を置き、rev-parse は通して archive だけ失敗させる
SOURCE_FETCH_FAILED         fetch の reject（v0.6.15 では未配線でもあった）
SOURCE_HTTP_ERROR           HTTP 503
SOURCE_BODY_UNREADABLE      応答本文の reader が失敗
```

### **v0.6.15 の両方向照合が、なぜこれを通したか**

**route の母集団を試験が手で持っていたからです。**
そこに書かなかった経路は当然「出なかった」ので、
「出なかった」を「出ない」の証拠として使っていました。

**そちらの「現在の reachability 試験は宣言した有限個の route を実行しているだけで、
依存関数の失敗を注入して全経路を探索しているわけではない」という指摘が正確です。**

route の表を 1 つ（`test/_cliRoutes.mjs`）にし、**契約の検査と到達性の照合が同じ表**を使います。
別々に持てば、また同じ形の穴になります。

```
catalog 82 種類 = corpus 45 / cli-route 33 / defensive-invariant 4
この run で実際に出た 78 種類
到達しないと宣言した 4 種類（**出ていないことも実測**）:
  ROOT_STRIP_NOT_A_DIRECTORY / HEADER_NUMERIC_FIELD_RANGE /
  HARDLINK_CHAIN_UNRESOLVED / SOURCE_ARCHIVE_MISSING
```

そちらの期待計数は corpus 45 / cli-route 31 / defensive 4 でしたが、
**cli-route は 33 になりました**——`SOURCE_FETCH_TIMEOUT` と `CLI_ARGUMENTS_MISSING` を
新設したためです。

注入は `node --import` で `globalThis.fetch` を差し替えます。**道具は 1 バイトも変えません。**

## 6. schema は v2 にしませんでした。**理由を実測で示します**

そちらの推奨は「`source-verifier-cli-result.v2` を新設し、toolVersion 19 から v2 を名乗る」でした。
**採りませんでした。**代替案（release-pinned historical schema）のほうを採っています。

- **v2 にしても、次に狭めたときに同じことが起きます。軸の問題は版数では解けません。**
- 下流は既に `schemaId` で分岐しており、v2 はその分岐を増やすだけです。
- **必要なのは「保存した結果をどの schema で読むか」を結果ごとに固定すること**で、
  **その digest は既に `assets` に在りました。名指ししていなかっただけです。**

`docs/SCHEMA_VERSIONING_POLICY.md` に第7条を足し、2 軸を条文にしました。

```
producer-forward     新しい出力が古い schema を通るか       → 通る
historical-instance  保存した古い結果が新しい schema を通るか → **通らない**

実測: v0.6.14 の出力 → v0.6.14 の schema  適合
      v0.6.14 の出力 → v0.6.16 の schema  **不適合**（policyId が必須になった）
```

試験（条文⑦）が**過去の出力が最新 schema を通らないこと**を実測で固定します。
通るようになったら前提が変わったということなので、黙って通さず条文を書き直します。

### **索引へ欄を足す案は、測ってから撤回しました**

そちらの「`policyId/policyVersion/policySha256` を release index へ追加」を最初に実装し、
`verifierContract` という欄を作りました。**版数判定器に掛けたら `BUMP` でした。**

```
diffSchemaObjects(旧 index schema, 新 index schema) → BUMP
対照（同じもの同士）                                 → HOLD
```

`additionalProperties: false` の schema へ欄を足すのは**言語の拡大**で、
**索引を v2 にすることになり、下流に版追従を強います。**
pin となる digest は既に `assets` に在るので、**欄を増やさず既存の `notes` で名指しする**
形にしました（添付の索引に 3 行入っています）。

> **`policySha256` は信頼の起点にしていません。**そちらの評価どおり、
> 自己整合の識別子として扱っています。起点は**道具そのものの sha256**
> （`f8596510e24537f0…`）です。

## 8. core / CLI 分離 — **次の版の最初に着手します**

そちらの「P0 訂正版と混ぜない」という判断を支持いただいた点、そのとおりにしました。
次の独立版で、この順に進めます。

```
1. main(args, io) の抽出
2. process.argv / process.exit を wrapper へ限定
3. pure core の route 試験
4. single-file 配布の制約は維持（試験が強制している）
5. source と bundle の byte 一致、または semantic 一致の試験
```

**他の変更を混ぜません。**`main(args, io)` の抽出だけを 1 コミットにし、
**正規の名前での出力が byte 一致であること**を先に示してから先へ進みます。

CI へ `npm run build` も足しました（両 platform で実行を確認）。
model の再生成は足していません——重く、配布可能性の確認とは別物です。

## 9. 反例のいただき方と、次に見てほしいこと

**実データで再現できる形だと助かります。**今回はとくに、
**公開物を開いて `test_counts.json` の中身を見た**という指摘の形が効きました
——こちらは「CI が 1304 件で通っている」を根拠にしていて、
**配った機械可読の証拠を一度も読み返していませんでした。**

そのうえで、次を見ていただきたいです。

1. **`defensive-invariant` と宣言した 4 件。**本当に外部入力から到達しないか。
   **こちらは「出ないこと」しか確かめていません**——到達経路の不在は証明していません。
2. **門を 2 つに分けた設計**（§2）。`release:evidence` を由来だけにした判断が甘くないか。
3. **終了コード 3**（§3）。JSON を出さずに止めるのが、受け手にとって本当に安全か。
   `INTERNAL_ERROR` status を作って JSON で返すほうがよいという判断であれば、次版で変えます。
4. **索引へ欄を足さなかった判断**（§6）。`notes` の宣言では機械可読性が足りないか。
5. **同じ形の穴が、ほかにも無いか。**——**いちばん見てほしいのはここです。**
   同じ境界を 2 つ以上の一覧で持っていて、片方しか検査していない箇所。
   **直近 5 版で 10 個出ました。**今回も「全面へ当てる」と書いた検査自体がそれでした。
6. **BusyBox 列は今も未再現です。**開発機にも CI にもありません。
   そちらの外部再現（BusyBox 1.37.0）は根拠として採りました。
