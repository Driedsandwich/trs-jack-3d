## 版を据え置いた根拠

条文（`docs/SCHEMA_VERSIONING_POLICY.md`）どおり、**新旧 2 つの schema だけ**で判定しました。

```
v0.5.0 の schema 20 本 → 現在
  HOLD 20 / HOLD_RECORD 0 / **BUMP 0**
新設 1 本  contract-migration.v1.schema.json（比較対象なし）
```

この判定はテストにも入れました（`v0.5.0 の全 schema が、現在も言語が変わっていない`）。
**次に据え置いたまま契約を変えたら、そこで落ちます。**

## 直した 2 件（どちらも外部監査の指摘）

### 1. 条文の判定器が `oneOf` を誤判定していた — **危険な向き**

```
旧  oneOf: [{integer}, {number, minimum: 0}]
新  oneOf: [{integer}, {number, minimum: 1}]

値 0    旧 invalid（2 枝が一致するので oneOf は落ちる）→ 新 valid   **広がっている**
値 0.5  旧 valid                                    → 新 invalid  狭まっている
```

どちらも他方を包含しないので正しい判定は `BUMP` ですが、
**v0.5.0 までの実装は `HOLD_RECORD`（据え置き可）を返していました。**

原因は `oneOf` の枝を index 同士で再帰比較していたことです。
`oneOf` は「ちょうど 1 枝が一致」なので、**枝の言語について単調ではありません。**
枝を狭めた結果、それまで 2 枝に一致して弾かれていた値が 1 枝だけに一致して通るようになります。

**v0.5.0 の判定器と設計文書には「逆（上げるべきなのに据え置く）は起きない」と書いていました。
これは嘘でした。**該当箇所を実測に合わせて書き換え、条文の「限界」にも節を足しました。

`oneOf` は変更があれば無条件で `UNDEC`（→ `BUMP`）へ倒します。
**`anyOf` / `allOf` は和と積なので枝ごとに単調で、健全なので触っていません**（過剰に倒すと条文の判別力が落ちます）。

`oneOf` は live な 4 本（`source-input-manifest` / `trs-jack-3d-release-index` / `validation-results`）で
**計 8 か所**使われており、机上の話ではありませんでした。
ただし **v0.5.0 の 6 本の判定は汚染されていません**（`oneOf` 由来の差分 0 件・すべて他の理由で `BUMP`）。

回帰試験は 3 つを同じテストで見ます。

| | 内容 |
|---|---|
| ① | ajv で値 `0` と `0.5` の valid / invalid が反転すること（＝包含していない事実） |
| ② | **`v0.5.0` tag の実物を読み込んで** `HOLD_RECORD` を返すこと（修正前の実測） |
| ③ | 現在の実装が `BUMP` を返し、**その経路が鳴ったこと** |

②が無いと「昔からそうだった」のか「直した」のかを、記録でしか主張できません。

### 2. 配布した profile の中で `normalized` の説明が矛盾していた

```
coordinateSystem.normalizedScope        PROFILE_LOCAL
coordinateSystem.crossProfileComparable false
coordinateSystem.normalizedNote         同じ normalized 値が別 profile で同じ状態を意味する保証はない

modelLimitations.notes[4]  「…機種横断では normalized を使うこと。」   ← 真逆
```

**全 tag を走査したところ、この一文は v0.1.0 から v0.5.0 まで 7 版すべてに入っていました。**
`crossProfileComparable: false` を足した v0.2.0 の時点で矛盾になっています。

生成器のコメントには「v0.1.1 で文章としては弱めた」と書いてありました。**弱まっていませんでした。**
機械可読フィールドを足したときに、元の文言を消し忘れています。コメントも実態へ直しました。

差し替え後:

> `nominalStartMm` は 1 機種の実寸であり、一般的な「挿入深度」ではない。
> **profile を跨いで対応づけるときは `topologyClass` と event の同一性を主キーにすること。**
> `normalized` は分母（`fullInsertionDepthMm`）が profile ごとに違うので主キーにできない
> （近傍を選ぶ補助にだけ使う）。

**この artifact を UI へそのまま出していた場合、表示が変わります。**
