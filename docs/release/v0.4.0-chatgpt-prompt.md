## 0. 先に訂正 — `test_counts.json` の `allPassed` は誤り

**`allPassed: false` が入っているが、実際は 467 件すべて通っている。**

```
公開した値   total 467  skipped 0  allPassed false   ← false が誤り
実際         467 passed (19 files)  失敗 0
回し直した値 total 467  skipped 0  allPassed true    ← byFile も total も同一
```

原因は生成の順序である。テストが 2 件落ちている時点で `npm run test:count` を回し、
そのあと 2 件を直したが**件数を取り直さなかった**。件数は変わらなかったので、
`total` を突き合わせる既存の検査は通ってしまった。

**この artifact を上書きはしない**（公開済み asset は不変にする方針）。次の版で直す。
`total` と `byFile` と `skipped` は正しいので、件数として使う分には問題ない。
**`allPassed` だけを信じないこと。**

## 1. `profileId` が変わった。**lock を作り直すこと**

```
TRS   trs-jack-3d:TRS|JACK-TRS:abca1dfb5b5f  → trs-jack-3d:TRS|JACK-TRS:f925561fead8
TRRS  trs-jack-3d:TRS|JACK-TRRS:01ac02bdcb7b → trs-jack-3d:TRS|JACK-TRRS:4923277389e6
```

**索引から引くこと。**上はその写しで、貼り直す過程で誤りが入りうる。

### 中身は変わっていない

| | v0.3.0 | v0.4.0 |
|---|---:|---:|
| profile の `schemaVersion` | 2 | **2**（変わらず） |
| 頑健性の `schemaVersion` | 2 | **2**（変わらず） |
| TRS intervals / events | 23 / 32 | **23 / 32** |
| TRRS intervals / events | 30 / 36 | **30 / 36** |
| `ground-open-differential` | TRS 0 / TRRS 1 | **TRS 0 / TRRS 1** |
| `IV028` | 13.30–13.52 mm | **13.30–13.52 mm** |

**変わったのは入力の集合だけである。**`profileId` は `inputDigest` の先頭 12 桁なので、
入力が変われば ID も変わる。区間・event・topology 列を読む経路は止まらない。

### `profileId` は local ビルドから予測できない

この版の作業中に実証した。profile の入力には**感度 artifact が含まれる**ので、
感度を `--release` で作り直すと `artifactKind` が `local` → `release` に変わって bytes が動き、
profile の digest も動く。

```
入力 24 件のうち変わったもの  2 件
  package-lock.json             （採番による）
  sensitivity.trs_jack_trs.json （local → release）
残り                          22 件は不変
```

感度と頑健性は入力に他 artifact を含まないので予測できる。**profile だけができない。**

## 2. `source-input-manifest.json` に `inputScope` が必須で入った

**v0.3.0 の schema を pin して v0.4.0 の manifest を検証すると落ちる。**
沈黙ではなく `required` 違反として明示的に落ちる。

なぜ足したか。**件数と sha256 だけでは記録漏れを見つけられない**——
落ちている入力があっても、残った分は全部一致するからである。
範囲を一緒に渡せば、受け手は自分の source を歩いて「載っていない入力」を自分で探せる。

```
inputScope.file                    source-input-scope.v1.json
inputScope.recursiveDirectories    ["src/data", "src/model"]
inputScope.requiredExactFiles      9 件
inputScope.allowedGeneratedInputs  3 件
inputScope.excludedOutputs         ["artifacts"]
inputScope.notCovered              5 件
```

`notCovered` は **`inputDigest` が覆えないもの**（Node のバージョン・ロケール・環境変数・
`src/` のうち UI 側・`test/`）。**「digest が一致した」は「これらも同じだった」を意味しない。**

## 3. `role` の enum に `input-scope` が増えた

**改名ではなく追加である。**旧語彙は消えていないので、`role` で絞り込む実装が沈黙して壊れることはない。
ただし v0.3.0 の schema を pin して新しい artifact を検証すると enum で落ちる（**明示的に落ちる**）。

```
["schema", "generator", "model-data", "model-code", "lockfile", "sensitivity-input", "input-scope"]
```

現役の 3 schema（profile v2 / event-sensitivity v1 / topology-robustness v2）に入れた。
**v1 schema（過去の release の契約）には触れていない。**
両 artifact の `contractMigration.addedFields` に記録してある。

入力は **28 件 → 29 件**（範囲定義自身が入力に加わった）。

## 4. 入力 29 件を自分で検算できる。**道具は bundle に入っている**

v0.3.0 では「入力 28 件を自分で検算せよ」と書いておきながら、
**その script も tag source も bundle に入っていなかった。**
返ってきた `SOURCE_UNAVAILABLE` は正しい報告で、欠陥はこちらの指示にあった。

- `verifyReleaseSourceInputs.mjs` を**同梱した**（node 標準しか使っていないので単体で動く）
- tag source は**この release ページの "Source code (tar.gz)" がそのまま使える**

```bash
# release ページから bundle と Source code (tar.gz) の両方を取る
tar xzf trs-jack-3d-0.4.0.tar.gz     # → Driedsandwich-trs-jack-3d-<sha>/ ができる

node verifyReleaseSourceInputs.mjs \
  --manifest source-input-manifest.json \
  --source <展開先> \
  --scope source-input-scope.v1.json
```

**展開すると `<repo>-<sha>/` が 1 枚かぶる。**剥がし忘れると 29 件すべてが
`MISSING_IN_SOURCE` になり「壊れている」と読めてしまうので、`--source` がその 1 階層を剥がす。
展開先を親ディレクトリのまま渡してよい。

通信して取りに行かせることもできる。

```bash
node verifyReleaseSourceInputs.mjs --manifest source-input-manifest.json \
  --tag v0.4.0 --fetch github --scope source-input-scope.v1.json
```

| status | exit | 意味 |
|---|---:|---|
| `OK` | 0 | 全件一致 |
| `MISMATCH` | 1 | 不一致・欠落・**記録漏れの入力**・**出力の自己参照** |
| `SOURCE_UNAVAILABLE` | 2 | source を取れなかった。**検証していないだけで、不一致ではない** |
| `MANIFEST_UNAVAILABLE` | 2 | manifest を読めなかった |
| `NOTHING_TO_VERIFY` | 2 | 入力 0 件。**何も見ていないのに OK と言わない** |

**`unrecordedInputDetection.performed` を先に見ること。**`false` なら
「候補 0 件」ではなく「**探していない**」である（範囲定義が無い source ではそうなる）。
古い tag を検証するときは `--scope` を明示すれば探索できる。

こちらで v0.4.0 tag に対して実行し、**29/29 一致**した（GitHub tarball 経由・記録漏れ 0・自己参照 0）。

## 5. `source-verification-result.json` は**自己申告**である

同梱してあるが、**そちらの独立検証を置き換えない。**artifact 自身がそう名乗っている。

```
isSelfReport                   true    ← schema で const 固定
replacesRecipientVerification  false   ← 同上
sourceOrigin                   directory:.   ← **tag の source ではない。生成時の作業ツリー**
releaseCommit                  null
status / exitCode              OK / 0
counts.checked                 29
unrecordedInputDetection.performed  true
```

`releaseCommit` が `null` なのは正しい。**artifact は自分を含む commit の hash を持てない。**
tag は evidence をコミットしてから打つので、生成時点では存在せず、原理的にここでは検証できない。

配る理由は自慢のためではなく、**判定の境界を実物で見せるため**である。
「取れなかった」「合わなかった」「そもそも探していない」が別物だということは、
出力を 1 つ見るのがいちばん早い。

`tool.sha256` が同梱の script と一致することを確かめてから読むこと
（違っていたら、この記録は今の道具の出力ではない）。

## やること

1. `SHA256SUMS` で exact byte 検証（23 件）
2. `trs-jack-3d-release-index.v1.json` から `release-lock-v0.4.0.json` を作る。
   **`artifactGenerationCommit` を単一値で照合しないこと**——この版でも 3 種ある
3. profile を取り込み直す。**`profileId` が変わっただけで、区間・event・topology 列は同じ**
4. `verify:release-source-inputs` で入力 29 件を自分で検算する（→ §4）
5. production byte import を回し、結果を返す

`artifactGenerationCommits[]` が完全な事実で、**3 種ある**。


release 工程が 3 段階だからである。profile の入力に感度 artifact が含まれるので、
**感度を作り直すとその入力が dirty になり `--release` が拒否する。**
先に感度・頑健性を確定してコミットし、そのうえで profile を生成し、evidence はさらにその後になる。

`releaseCommit` との一致も要求しないこと。artifact をコミットしてから tag を打つので、
artifact は必ず tag より前の commit から作られる。
