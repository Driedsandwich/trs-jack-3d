**これは patch ではない。schema を 6 本まとめて上げた。**

## 1. 下流は **6 か所**で止まる。直す順序がある

```
half-plug-topology-profile   2 → 3    止まる artifact 2
event-sensitivity            1 → 2    止まる artifact 2
topology-robustness          2 → 3    止まる artifact 1
source-input-manifest        1 → 2    止まる artifact 1
validation-results           1 → 2    止まる artifact 1
test-counts                  1 → 2    止まる artifact 1
```

**索引（`trs-jack-3d-release-index.v1`）は版を上げていない。**入口は動く。
まず索引を読んで「今回どれが何版になったか」を引くこと。

止まり方は **8 件すべて `schemaVersion` の不一致**である。
「不明な項目がある」で潰れるのではなく、**版が違うと読める形で止まる。**

### 直す順序

**信じてよいものが確定する順**に直す。

| 順 | pin | 理由 |
|---:|---|---|
| 0 | 索引 | 上げていない。ここから今回の版を引く |
| 1 | `source-input-manifest` | 配布物を信じてよいかを決める検証の入口。ここが通らないと他を直す意味がない |
| 2 | `half-plug-topology-profile` | 本体。**ファイル名も変わる**ので lock の書き換えを伴う |
| 3 | `event-sensitivity` | profile の `sensitivitySummary` が指す先 |
| 4 | `topology-robustness` | profile とは独立に読める |
| 5 | `validation-results` | producer の自己申告。読まなくても profile の取り込みは動く |
| 6 | `test-counts` | 同上 |

**profile しか読まないなら 2 か所で済む**（`source-input-manifest` と profile）。
5 と 6 は、こちらの検証結果を読んでいなければ何もしなくてよい。

## 2. profile は**ファイル名も変わる**。`profileId` も変わる

```
half_plug_topology_profile.v2.trs_jack_trs.json   →  half_plug_topology_profile.v3.trs_jack_trs.json
half_plug_topology_profile.v2.trs_jack_trrs.json  →  half_plug_topology_profile.v3.trs_jack_trrs.json
```

**名前で引いている lock は、schema 検査に届く前に「ファイルが無い」で止まる。**
これは schema の言語に現れない変更なので、ajv では検出できない。
対応表は各 artifact の `contractMigration.renamedAssets` にある（機械可読）。

schema ファイル名も 6 本変わる（`event-sensitivity.v1.schema.json` → `.v2.schema.json` など）。
**artifact 側の名前が変わるのは profile だけ**で、`sensitivity.*` / `topology-robustness.*` /
`source-input-manifest.json` / `validation-results.json` / `test_counts.json` は変わらない。

`profileId`:

```
TRS   trs-jack-3d:TRS|JACK-TRS:796498ebba63  → trs-jack-3d:TRS|JACK-TRS:89fa4eea1173
TRRS  trs-jack-3d:TRS|JACK-TRRS:b61bce36516c → trs-jack-3d:TRS|JACK-TRRS:821cc14c605d
```

**索引から引くこと。**上はその写しで、貼り直す過程で誤りが入りうる。

### オーダーに無い 2 本を足した理由

v0.4.1 のフォローアップオーダー §1 は 4 本を挙げていた
（profile / event-sensitivity / topology-robustness / source-input-manifest）。
**`validation-results` と `test-counts` は挙がっていない。**

こちらで洗ったところ、**この 2 本も v0.4.1 で同じ性質の変更をしていた**——
項目を追加して必須にしており、旧 schema を pin した consumer は拒否する。
条文に照らして違反なので足した。**オーダーの一覧は不完全だった。**

記録はすべて `contract-migration.v1.json` と各 artifact の `contractMigration.history`（全 17 項目）にある。
据え置いた回は次を持つ。

```
versionWasHeld: true
schemaVersionShouldHaveBeen: <本来あるべきだった版>
recordedRetroactivelyIn: "v0.5.0"     ← 当時の判断記録ではないことを隠していない
```

## 5. 条文は「言語の包含」で判定する。**artifact の中身は見ない**

`docs/SCHEMA_VERSIONING_POLICY.md`（tag source にある）。

> 新 schema が受け入れる値の集合が、旧 schema のそれに**収まらないなら版を上げる。**
> 判定は**新旧 2 つの schema だけ**で行う。

最初は「旧 schema を pin した consumer が**今の artifact**を拒むか」で書いた。**これは使えなかった。**

```
v0.3.0 schema × 現物（role に input-scope を使う）            → 拒む   → 「上げる」
v0.3.0 schema × role を input-scope から戻した同じ artifact   → 受ける → 「据え置き可」
                                              （書き換えたのは 1 項目だけ）
```

**同じ schema 変更でも、その版の artifact が新しい値を使っているかで答えが反転する。**
enum に値を足しても、まだ使っていなければ据え置きが許され、**使い始めた版で突然止まる。**
破壊的変更の記録が「いつ壊したか」ではなく「いつ使い始めたか」にずれる。

### 判別力を確かめた

「常に上げる」と言うだけの壊れた判定器でも、過去 9 件には 9/9 で当たる。
**それだけでは何も確かめたことにならない。**

| 検査 | 結果 |
|---|---|
| 答えが分かっている合成 16 件 | **16/16 一致・うち 7 件は BUMP 以外** |
| 過去へ当てる | **9/9 で「上げるべきだった」** |
| 対照（中身が変わらない schema 7 件） | **7 件すべて HOLD**（何にでも鳴らない） |

合成の途中で 1 件、`pattern` の変異が **BUMP は出たが意図した経路では鳴っていなかった**
（同じ変異で enum も消していた）。作り直して 16/16 にした。

### `additionalProperties: false` は維持する

schema 20 本すべてが `additionalProperties: false` である。この書き方では
**optional な項目の追加も、pin した consumer は拒む。**
so 条文には「**項目の追加はすべて版を上げる**」と書いた。
「optional なら据え置き可」とは書いていない（この project では成り立たないため）。

### 記録が実物とずれないようにした

`contractMigration` は手で書くと腐る。実際に腐っていた。

```
"field": "provenance.inputFiles[].role に \"input-scope\" を追加"   ← 項目名の欄に日本語の文
"introducedIn": "v0.1.2 (追加のみ)"                                 ← 存在しない tag
```

記録に **schema への JSON Pointer** と **判定器が出した効果**を持たせ、4 つの機械検査で突き合わせる。

```
① pointer 実在   changes[].schemaPointer が新旧いずれかの schema に実在する
② 判定の一致     その 2 つの schema へ判定器を当て、policyVerdict と effect が一致する
③ 網羅           判定器が出した差分のうち記録に無いものがあれば落ちる
                 ＋ 全 tag 対を走査して据え置き違反の取りこぼしも見る
④ 据置きゼロ     v0.5.0 以降に versionWasHeld: true が現れたら落ちる
```

変異 8 件すべてで落ちることを実測した。うち 4 件は記録側ではなく
**schema を書き換えて記録が追随しないこと**を見る変異である。

## 6. オフライン向けの写しを同梱した。**独立検証は置き換えない**

v0.4.1 でそちらはネットワークが無く `SOURCE_UNAVAILABLE` になった。
判定としては正しい（取れなかったことを不一致に潰していない）が、
**完全にオフラインだと独立検算に着手できなかった。**

`source-snapshot.v1.json`（**77 ファイル・1.05 MB**）を同梱した。
入力 30 件・生成器・schema が入っている。

**これは producer の申告であって、受け手の独立検証を置き換えない。**
artifact 自身に書いてある。

```
isSelfConsistencyOnly          true
replacesRecipientVerification  false
isSourceOfTruthForInputDigest  false
inputDigestSourceOfTruth       "artifacts/source-input-manifest.json"
```

**言えるのは「記録した hash が、記録した中身と合っているか」だけ**である。
その中身が本当に tag の source かどうかは、この写しでは確かめられない
（producer が写しと manifest を同時に偽れば一致する）。

### 通信があるなら、写しではなく tag source を使うこと

```bash
curl -sL -o src.tar.gz \
  https://github.com/Driedsandwich/trs-jack-3d/archive/refs/tags/v0.5.0.tar.gz
node verifyReleaseSourceInputs.mjs --manifest source-input-manifest.json \
  --source src.tar.gz --scope source-input-scope.v1.json
```

**v0.4.1 まで、この手順は動かなかった。**`--source` は展開済みディレクトリしか受けず、
tar.gz を渡すと `ENOTDIR` で落ちていた。**書いてある手順が動いていなかった。**
v0.5.0 で archive を受けられるようにし、ディレクトリ経路と判定が一致することを実測した
（`TOOL_VERSION` 3 → **4**）。

release ページの "Source code (tar.gz)"（GitHub が tag から自動生成）でも同じである。

### tag source をそのまま添付しない理由

| | 実サイズ |
|---|---:|
| 入力 30 件だけ | 0.49 MB |
| **入力 + `scripts/` + `schemas/`（採用）** | **1.05 MB** |
| tag source archive まるごと | **9.28 MB** |

9.28 MB の増えるぶんは `docs/screenshots/*.png`（1 枚 0.6〜0.7 MB）と
`artifacts/contact_sweep.json`（1.3 MB）で、**どれも受け手の検証には使われない。**

`tar.gz` ではなく JSON にしたのは、**tar.gz が同じ入力から作っても毎回ハッシュが変わる**
（mtime が入る。実測で不一致）ためである。asset は sha256 で固定するので再現しない形式は使えない。
