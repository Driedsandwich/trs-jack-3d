## 必要な変更（emulator 側）

### A. `release-lock` の `inputDigest` を variant 別にする

`release-verifier.mjs:43` は `lock.inputDigest`（トップレベルに 1 つ）と突き合わせる。
v0.1.1 で inputDigest を variant 別にしたので、**1 つの lock では片方しか production import できない。**

```
TRRS の digest を入れた lock で TRS を import
  → Error: provenance.inputDigest does not match release lock
```

`lock.profiles[variantId].inputDigest` へ移し、`expected?.inputDigest ?? lock.inputDigest`
で引くようにすると両 variant とも PASS する。

### B. `spreadStatus` の新しい enum 名を受ける（**こちらが重い**）

`topology-adapter.mjs:29` は `event.spreadStatus !== 'MEASURED'` で `continue` する。
v0.1.1 で `MEASURED` → `MODEL_SWEEP_EVENT_SPECIFIC` に改名したため、
**36 event すべてが弾かれ、ループ本体が 1 回も走らない。**

このループは「名目値が自分の spread の外にあるか」＝**今回直した汚染そのものを検出する箇所**。
つまり検出器が死んだまま `status: PASS` / `verificationWarnings: []` が返る。
`notEventSpecificSpreadCount` も真値 29 に対して 0 を返している（`:118` も旧名で数えているため）。

変異検査（等価変異でないことの確認）:

| | 汚染を 1 件仕込んだ profile |
|---|---|
| 現行 | `AVAILABLE_AS_MODEL_SWEEP_ONLY`（**見逃す**） |
| 新 enum 名を足した版 | `QUARANTINED`（検出する） |

`['MEASURED','MODEL_SWEEP_EVENT_SPECIFIC'].includes(...)` と
`['NOT_EVENT_SPECIFIC','MODEL_SWEEP_NOT_EVENT_SPECIFIC'].includes(...)` に置き換えれば直る。

**これは trs-jack-3d 側の設計ミスでもある。**`schemaVersion` を 1 のまま enum の値を変えたので、
値で絞り込む消費側からは「その状態のデータが 1 件も無い」と区別がつかない。失敗ではなく沈黙になる。
schema v2 で `spreadStatus` を扱うときは、**語彙が変わったことを機械可読に示す**必要がある
（`schemaVersion` を上げるか、語彙バージョンを別フィールドに持つか）。判断はそちらの都合に合わせる。

### C.（付随・profile 側の既知の限界）

TRS variant は A・B を直した後も `SENSITIVITY_PROVENANCE_NOT_VARIANT_SCOPED` で `QUARANTINED` になる。
adapter は sensitivity 入力のパス全部に variant 名を求めるが、TRS は後方互換で
`artifacts/sensitivity.json`（variant 名なし）も入力に残しているため。
adapter 側を緩めるか profile 側から外すかは、次の schema 変更とまとめて決める。

### D. `profileId` の変更への追随

`intervalId` / `eventId` の再解決が要る（新旧は下記）。

## 実装した内容（P0-1〜P0-4）

- **`scripts/sensitivityEvents.ts` を新設。**variant ごとに event spread を測り、
  `variantId` / `analysisScope` / `sweptParameters` / `generatedFromCommit` /
  `basis: MODEL_PARAMETER_SWEEP` を記録する
- **exporter は `variantId` が profile と一致しなければ取り込まない（fail-closed）。**
  一致しなければ `spreadMm: null` / `spreadStatus: NOT_ANALYZED` /
  `sensitivitySummary.available: false`
- **3極の総合解析**（プラトー間隔・Tip 橋絡しきい値・挿抜力）は 3極 variant でのみ出力。
  TRRS では `bridgeDepthJointRangeMm` 等が `null`
- `sweptParameters` を直書きせず artifact の記録から取る
- **`inputDigest` を variant 別にした**（P1-2）

## 用語の補強（オーダー §6）

- **`fully-seated` は「肩が当たった」ではない。**`reasonCode` のとおり
  `ALL_EXPECTED_FUNCTIONS_MATCH`。TRS×TRRS では 13.52 mm から始まるが、
  機械的な完全挿入は 14 mm。Schema v1 の間は名前を変えず、v2 で改名を検討
- **`normalized` の説明を弱めた。**「機種横断では normalized を使う」は強すぎた。
  profile 内の相対座標であり、**profile 横断で同じ電気状態を保証しない**

## こちらの検査が捕まえなかった件

意味規則を 45 本書いていたが、構造（一意性・連続性・存在）ばかりで、
**記録された値どうしの整合をほとんど見ていなかった。**

同種の抜けを数えたところ、**候補 12 件のうち 11 件が素通り**していた。
8 件を追加した（すべて変異させて落ちることを確認）。

とくに **`provenance.inputFiles[].sha256` が実ファイルと一致するか**を
一度も検査していなかった。provenance の話は全部これに乗っているので、
ここが嘘なら `inputDigest` も再計算も無意味になる。
