## 2. **広がっているのに「据え置き可」と答えていました**

```
旧  oneOf: [{type:'string'}, {$ref:'#/definitions/d0'}]  definitions.d0.type = 'boolean'
新  同じ oneOf                                            definitions.d0.type = ['boolean','null']

ajv   null が旧 invalid → 新 valid  ＝ **言語が広がっている**
判定  HOLD（据え置き可）             ← **上げるべきなのに上げない**
```

`oneOf` は「ちょうど 1 枝が一致」なので枝の言語について単調でなく、枝ごとの比較ができません。
そこで**変更があれば無条件で UNDEC へ倒す**設計にしてありますが、
その「変更があったか」を `JSON.stringify(o.oneOf) !== JSON.stringify(n.oneOf)` で見ていました。

**枝が `{ $ref: … }` なら、参照先が変わっても枝の文字列は同じ**です。

**受け手への影響。** 版が据え置かれると、そちらは旧 schema を pin したままになります。
新しい版が `null` を出した瞬間、**検証が落ちます。**
「壊したのはいつか」ではなく「使い始めたのはいつか」で止まる——
この判定器が最初から避けようとしていた形そのものです
（`scripts/schemaLanguageDiff.mjs` の冒頭に書いてある動機）。

**root が `$ref` の場合は前から正しく**（`deref()` が入口で辿るため）、`oneOf` の枝だけが素通りしていました。

修正は比較の前に `$ref` を展開する形です（行番号は現在の repo のもの）。

```
100:  function expandRefs(node, root, seen = new Set(), depth = 0) {
354:    if (JSON.stringify(expandRefs(o.oneOf, oroot)) !== JSON.stringify(expandRefs(n.oneOf, nroot))) {
```

循環は `$ref` のまま残します——消すと**循環している 2 つが同じ形に見えます。**

## 4. **独立生成では判別力がありませんでした**

最初は schema を独立に 2 枚生成する形にしました。実測:

```
独立生成 600 対   BUMP 589 / HOLD 9 / HOLD_RECORD 2   ← **98% が BUMP**
```

これでは「**常に BUMP と言う判定器**」も同じ点数を取ります。
危険は**小さな変更**に潜むので、1 か所だけ変異させる形へ変えました。

```
変異対 961 対     BUMP 779 / HOLD_RECORD 173 / HOLD 9   ← ここで 4 件見つかった
```

**変異が当たらなかった対は数えていません**（539 件を除外）。
当たらなかった変異と素通りした変異は出力が同じなので、混ぜると意味が消えます。

種は固定してあります（`test/schemaLanguageFuzz.test.ts:45` の `SEEDS` は 300 件）。
**テスト件数が種の数で決まる**ので、環境で変わりません。

## 5. **見ている性質は 1 つだけです。値が作れなければ見逃します**

```
ajv が「新だけが通す値」を見つけたなら、判定器は BUMP でなければならない
```

逆（BUMP なのに広がっていない）は条文が明示的に許す保守的な誤りなので見ていません。

**一番の落とし穴は値の作り方です。**「新だけが通す値」を探せなければ、
言語が広がっていても反例が出ず、**試験は緑になります。**
値はその schema 対から作りますが（enum の全値・const・境界の前後・型ごとの代表値）、
**作れない値があれば広がりを見逃します。網羅性は示していません。**

探索が働いていることは、同じファイルの対照 5 つで確かめています。

```
① 既知の広がり対で証人が出る（出なければ探索が壊れている）
② 同一 schema では証人が出ない（何にでも鳴らない）
③ 深いネスト（>=4）と $ref を実際に作れている
④ 判定が BUMP 一色でない（常に BUMP と言う判定器を弾く）
⑤ 変異が当たった対だけを数えている
```

**反例をいただけるなら、ここが一番効きます**——こちらの値生成が届かない形を 1 つ挙げてください。

## 8. release 工程で 4 回止まりました

**どれも「確かめずに次へ進んだ」形です。**

```
① package-lock.json の版数を上げ忘れ
   artifact の記録された入力なので、後から触ると記録した sha256 が古くなる
   validate:profiles が 6 件で落ちた → **約 25 分の再生成をやり直し**
   前回の第0段は両方を上げていた（git show --stat で確認できた）のに、手順を記憶で進めた

② 第1段をコミットせずに第2段を実行
   「入力に未コミットの変更がある」で拒否された。**正しい歯止め**
   葉の差が 0 件に見えたのは、再生成されていなかったから
   エラーの末尾（Node.js v22.22.3）だけ見て「成功」と読むところだった

③ check:doc-numbers が exit 1 のままコミット
   SECURITY.md の「直近の release」は docs/release/<tag>-SHA256SUMS.txt の
   最大版が真値。控えは公開物からしか作れないので、公開前は前の版が正しい

④ **失敗した実行から証拠を記録**
```

**④ が一番危なく、配る直前でした。**

```
artifacts/test_counts.json に記録されていた値
  total 1410 / **failed 27** / **failedSuites 18** / **exitCode 1** / allPassed false
```

原因は 2 つ重なっています。工程の順序（profile 再生成の直後、`release:evidence` を
回す前に全テストを走らせた。その時点では突合系が 27 件落ちる）と、
**`npm run test >/dev/null 2>&1` と出力を捨てて終了コードを見ずに記録したこと**です。

**手元の鮮度検査は「一致」と答えていました。** `.vitest-report.json` と
`test_counts.json` を比べる仕組みですが、**両方とも同じ失敗実行から来ていた**ので
食い違いようがありません。**CI は新しく走らせるので、そこで初めて落ちました。**

> 「記録と実測が一致するか」の検査は、**記録と実測が同じ壊れ方をしていると通ります。**
> 配った `test_counts.json` は `failed 0 / exitCode 0 / allPassed true` です（添付から確認できます）。

## 9. 反例のもらい方について（お願い）

**指示書が機械で実行できる形**だと速く確かめられます。

```
schemas/… を <tag> から読む
{"status":"…","stableReasonCode":"…"} を AJV で当てる
diffSchemaObjects(A, B) が BUMP になることを確認する
```

今回の欠陥は**この形そのもの**で見つかりました。ajv を正解器にして
「新だけが通す値」を実際に探し、判定器と突き合わせています。

**§5 の値生成が届かない形**を挙げていただけると、一番効きます。
「〜のはずである」ではなく、**「この 2 つの schema へこのコマンドを当てるとこうなる」**が
最も速く確かめられます。
