## 1. **`OK` の意味を狭めました**（受け手に直接効きます）

v0.6.10 まで、`status` は**不一致が無いこと**しか見ていませんでした。
そのため、**記録漏れの探索をしていなくても `OK`** になりました。
受け手には「探して見つからなかった」と読めます。**やらなかったことは、合格ではありません。**

```
できていない工程がある  → VERIFICATION_INCOMPLETE（exit 1）
```

**`OK` を期待している自動処理があれば、そこは直す必要があります。**

### **訂正: 影響する tag は「v0.3.0 より前」ではありません**

公開した notes には「**v0.3.0 より前の tag** を検算すると、これに当たります」と書きました。
**間違いです。**公開後に全 tag を実際に走らせて測り直しました（2026-08-12）。

```
tag ごとに、その tag の source に対して検算した結果
  v0.2.0    VERIFICATION_INCOMPLETE   incompletePhases=["unrecorded-input-detection"]
  v0.3.0    VERIFICATION_INCOMPLETE   同上          ← notes は「これは大丈夫」と読める書き方
  v0.4.0    OK                        incompletePhases=[]
  v0.4.1    OK
```

`manifest.inputScope` が入ったのは **v0.4.0** からです（21 tag 全件を確認）。
**v0.3.0 も対象です。**v0.1.0 / v0.1.1 は manifest 自体がありません。

**「より前」と書いたのは、境界を実際に走らせずに書いたからです。**
`inputScope` を足した版を思い違いしていました。

`--scope` を**中身も確かめずに**受け取っていました。実測:

## 6. 止める理由 30 件の内訳

```
GNU tar 側でだけ根拠が取れる   15 件
bsdtar 側でだけ根拠が取れる    10 件（v0.6.10 は 9 件）
どちらでも取れていない          5 件
```

この 3 つの数は**試験が毎 run 数え直して固定しています**（増減すると落ちます）。
増えた 1 件は `trunc-no-terminator` で、**bsdtar は exit 1 で拒み、GNU tar と python は通します**
——**切れていることに気づくのは 3 実装のうち 1 つだけ**でした。
これは CI の ubuntu 側が落として分かりました。

**残る 5 件のうち 3 件は、実装が割れているのではなく方針で止めています。**

| id | なぜ止めるか |
|---|---|
| `nonzero-size` | `size` は entry の見え方を変えるので解釈しない方針（v0.6.3〜） |
| `dup-regular-same-content` | 同じパスの通常ファイルが 2 回。どちらを検算したか言えなくなる（v0.6.1〜） |
| `dup-regular-different-content` | 同上 |
| `pax-path-then-gnu-longname` | 名前の上書きが 2 つ効く形の片方の順序。**BusyBox が要る** |
| `pax-linkpath-then-gnu-K` | 同上 |

**「実装が割れているから止めた」と書けないものは、方針で止めていると書きます。**

> **BusyBox は開発機にも CI にもありません。**下 2 件はそちらの報告に頼っています。

### **訂正: 「通す材料 66 件」は、誰も検査していない旗の数でした**

公開した notes には「うち『通す』材料が 59 → **66 件**」と書きました。
**実際に通る材料は 72 件です。**公開後に測り直して見つけました。

原因は、**同じ境界を 2 つの一覧で持っていた**ことです。

```
(A) 材料ごとの ok 旗          ok:true 66 件
(B) 期待値表（EXPECTED / EXPECTED_BY_ID）
    → 182 件すべてについて実際の結果と突き合わせ、毎 run 緑
    → 'safe' = 72 件（実測の READ 72 件と一致）
```

**検査されているのは (B) だけです。**(A) は corpus 全体で 1 か所からしか読まれておらず、
しかも `!ok`（止まる材料を選ぶ）としてしか使われていません。
**`ok: true` が本当に通ることは、どこでも確かめていませんでした。**

その結果、両者は **10 件でずれていました**。

```
ok:false なのに通る  8 件  pax-x-path, pax-g-global, pax-x-huge-record,
                          link-symlink-rel, link-symlink-escape,
                          link-symlink-absolute, link-hardlink,
                          root-is-symlink-trailing-slash-only
ok:true なのに止まる  2 件  pax-zero-length-mtime, pax-zero-length-uid
```

**後ろの 2 件は、そちらの前回の指摘で「過剰拒否では」と挙がったものです。**
こちらは一度「通す」と判断して旗を立て、**CI の ubuntu が
`Malformed extended header: invalid mtime=` を出したので拒否に戻しました。**
そのとき**旗のほうを戻し忘れて、以後ずっと数に混ざっていました。**

v0.6.10 の「59 件」も同じ旗の数です（実測で確認）。
**この数え方は v0.6.11 まで一貫して間違っていました。**

**旗を消して期待値表に一本化するのが正しい直し方**だと考えています（次の版で直します）。
2 つ持った時点で、片方しか見ない経路ができます。

### **同じ形の穴が、配布物の中にもう 1 つありました**

上を書いたあと同じ観点で添付を見て、**3 件目**が出ました。
**同梱の `source-verification-result.json` が、受け手に嘘の一覧を渡しています。**

```
公開物 source-verification-result.json → howToVerifyYourself[6]
  「status は OK(0) / MISMATCH(1) / SOURCE_UNAVAILABLE(2)
        / MANIFEST_UNAVAILABLE(2) / NOTHING_TO_VERIFY(2)。」   ← 5 種類

公開物 verifyReleaseSourceInputs.mjs → CLI_STATUSES              ← 8 種類
  OK, MISMATCH, VERIFICATION_INCOMPLETE, ARCHIVE_INVALID,
  ARCHIVE_UNSUPPORTED, SOURCE_UNAVAILABLE, MANIFEST_UNAVAILABLE, NOTHING_TO_VERIFY
```

**足りない 3 つは、v0.6.10 と v0.6.11 で足したものそのものです。**
とくに `VERIFICATION_INCOMPLETE` は**この版の目玉**なのに、
**同梱の手順書がその存在を受け手に伝えていません。**

いま同じ境界の一覧が **3 つ**あります。

```
CLI_STATUSES（道具の定数）              ← 権威
新設 schema の enum                     ← 試験が CLI_STATUSES と一致を assert（緑）
howToVerifyYourself の 1 行             ← **誰も検査していない・配布物に載る**
```

新設 schema を足したのは「受け手が記録側の説明を読むしかない」状態を直すためでしたが、
**その記録側に残った古い一覧を消し忘れました。**§7 の旗とまったく同じ形です。
**次の版で、この行も `CLI_STATUSES` から生成します。**

## 9. 次に確かめてほしいこと

**反例は、実データで再現できる形でいただけると助かります。**
具体的には次の 3 つがあると、こちらで同じものを踏めます。

1. **材料そのもの**（tar を組み立てるコード、または base64 の bytes）
2. **どの実装で何が起きるか**（`bsdtar` / GNU `tar` / `python -m tarfile` のどれで、
   exit code と stderr の 1 行）
3. **期待する挙動**（通すべきか止めるべきか。止めるなら `ARCHIVE_INVALID` と
   `ARCHIVE_UNSUPPORTED` のどちらか）

**「たぶんこう書けば通る」だけだと、こちらは再現を作るところから始めます。**
前回はいただいた 6 群すべてを再現できました。**その形が理想です。**

そのうえで、次を見ていただきたいです。

1. **`OK` を狭めた結果、正当なものまで非 OK にしていないか。**
   §1 の訂正のとおり、境界はこちらが思っていたより 1 版ぶん広いところにありました。
   **`--allow-unpinned-scope` を付けても `OK` にしない**判断が過剰でないか。
2. **`incompletePhases` の粒度。**いま 2 種類だけです
   （`unrecorded-input-detection` / `scope-not-pinned-to-manifest`）。
   受け手が機械で分岐するのに足りるか。
3. **空の名前の線引き。**`PATH_EMPTY_NAME` と `EXTENSION_NAME_EMPTY` を分けました。
   **分ける意味があるか**（受け手にとって違う対応になるか）。
4. **切れ方の判定。**`END_OF_ARCHIVE_MISSING` は
   「終端の印を見ないまま尽きた」で止めます。
   **正当な形を落としていないか**（終端が 1 個・zero block が 3 個以上・
   詰め物が blocking factor を超える、など）。
5. **§7 の形の穴が、ほかにも無いか。**——**いちばん見てほしいのはここです。**
   同じ境界を 2 つ以上の一覧で持っていて、片方しか検査していない箇所。
   1 セッションで 2 つ出たので、**まだあると思っています。**
   `SECURITY.md`・`TEST_RESULTS.md`・`README` の数、artifact の中の説明文、
   schema の `description` に書いた列挙——**どれも検査されていません。**
   **こちらの試験は、旗が嘘でも配布物が嘘でも緑のままでした。**
6. **新設 schema が受け手にとって使えるか。**`archivePolicy` の粒度、
   `stableReasonCode` の分岐しやすさ、足りない欄。
7. **BusyBox の結果。**`none` 5 件のうち 2 件。
