## 2. **schema は 1 本も上げていません。下流はどこでも止まりません**

```
v0.6.0 の schema 22 本 → v0.6.1
  HOLD 22 / HOLD_RECORD 0 / **BUMP 0**
新設 0 本
```

判定は条文（`docs/SCHEMA_VERSIONING_POLICY.md`）の判定器で全 22 本に当てた実測です。
**対照**として `required` を 1 つ外した写しを同じ判定器へ通すと `BUMP` になるので、判定器は黙っていません。

`schemaVersion` も配布ファイル名も変わりません。**adapter の分岐を足す必要はありません。**

## 3. `profileId` が変わりました。**lock を作り直してください**

```
v0.6.0  trs-jack-3d:TRS|JACK-TRS:480daac80519
v0.6.1  trs-jack-3d:TRS|JACK-TRS:38b692a12af6

v0.6.0  trs-jack-3d:TRS|JACK-TRRS:b5b1e5ff2dba
v0.6.1  trs-jack-3d:TRS|JACK-TRRS:eaccc9119c92
```

**報告文から転記せず、同梱の `trs-jack-3d-release-index.v1.json` から引いてください。**

動いた理由は 2 つで、**どちらもモデルの数値とは無関係です。**

| 動いたもの | なぜ |
|---|---|
| `physicalVerificationRef` | 判定の条文が v1 → v2 になり、書き出す項目が増えた |
| 版数 | `package.json` が 0.6.0 → 0.6.1 |

**再生成が provenance しか変えていないことを、葉ノードまで展開して数えてあります。**

```
sensitivity ×2 / robustness  葉 204 / 200 / 573 ・ 差分 4  ・ provenance 以外 **0**
profile ×2                   葉 2261 / 3124   ・ 差分 11 ・ provenance 以外 **0**
```

対照: `.sweep.divisions` を 30 → 31 に変えた写しを同じ検出器へ通すと「provenance 以外 1」で落ちます。

**区間・event の数は変わっていません**（TRS 23/32・TRRS 30/36）。`IV028` は 13.30〜13.52 mm・`ASSUMPTION` のままです。

## 4. 条文が v2 になり、`physicalVerificationRef` の中身が増えました

**型は `string` のままです。**構造を足すと言語が広がって profile v4（BUMP）になり下流が止まるので、
文字列のまま項目を増やしています。

```
v0.6.0  …@sha256:… gate=…@v1 records=0 required=… satisfied=- missing=… rejected=0

v0.6.1  …@sha256:… gate=…@v2 scope=geometry-only verdict=UNVERIFIED records=0
        required=… satisfied=- missing=… ambiguous=- conflicting=0 notCertified=0
        retracted=0 dupIds=0 decidedBy=- rejected=0
```

### 条文 v2 で直したこと

| | v2 |
|---|---|
| 相反する記録 | 全候補を評価し `recordId` で並べ直す。一致と矛盾が併存したら `AMBIGUOUS`（= `false`） |
| 分解能 | 観測点ごとに要求分解能を**許容の 1/3** から導く（`L` は 0.05 mm 以下）。生値が目盛に乗っているかも見る |
| 主張の範囲 | `claimScope: geometry-only` を出す |
| 台帳の重複 | `recordId` が重複したら判定ごと拒む（`INVALID_LEDGER`） |

**認定できないことと、矛盾を見逃すことを分けました。**
粗い測定器でも「予測より 1.45 mm ずれている」は言えます。使えない記録として捨てると
**モデルの誤りを見逃す**ので、`true` を出す資格と警報を鳴らす資格を別に置いています。
食い違いの判定にだけ測定器の不確かさ（分解能/2）を足し、認定側には足しません。

### **`scope=geometry-only` を読んでください**

`verifiedPhysical: true` が言うのは「条文が名指しした**幾何量**が、モデルの予測と許容の内側で合った」までです。

```
言わないこと
  target-topology  どの端子がどの導体と繋がるか・GND が開放か・短絡が無いか
  acoustic         音がどうなるか
  lot-variation    別個体・別ロットでも同じか
```

`TRS|JACK-TRRS` の必須観測点は 1 点だけで、しかも**別 variant（`TRRS-CTIA|JACK-TRRS`）の量**です。
これが合っても `IV028`（左右が別導体・共通帰線だけ開放）を確かめたことにはなりません。

**`verifiedPhysical` の値は `false` のままです。**実測記録は依然 **0 件**で、それが正しい状態です。

### `supersedes` は入れませんでした

新しい記録が古い記録を**黙って上書きできる仕組み**を作らないためです。
矛盾したときの決着は「モデルを直す」か「`retracted: true` と理由を付ける」の 2 つだけで、
どちらも書いた人の判断が残ります。`retracted` は既に台帳 schema にあるので、
`measurement-record.v1` の版も上がりません。

## 5. 検算ツールが `toolVersion` 6 になりました

v5（v0.6.0）で塞いだつもりだった穴が 3 つ残っていました。

| 直したこと | v6 | 実測した効果 |
|---|---|---|
| 同名 entry | `ARCHIVE_INVALID` で止める。**中身が同一でも拒む** | v5 は `dup.txt = "SECOND"` で通っていた |
| symlink | `lstat` で見て追わない。fs エラーは構造化 status へ | 生スタックトレース → **JSON が出る** |
| 圧縮入力の上限 | `maxCompressedBytes` 64 MB。ローカルは `stat` で先に見る。network は受け取りながら打ち切る | 最大 RSS **165.0 MB → 43.6 MB** |

**`status` の種類は増えていません。**`ARCHIVE_INVALID` は v5 のままです。

**塞ぎすぎていないことも同じテストで見ています。**26 個・6 種類の壊れた tar は v5 と同じ結末で、
正常な tar・gzip・実物の GitHub tarball（v0.5.2・246 ファイル）は今までどおり読めます。

## 6. `ARCHIVE_INVALID` は v1 schema では表現できないままです

**これは v0.6.0 からの既知の欠けで、v0.6.1 でも直していません。**

判定器で実測した結果、こうなるためです。

```
enum へ ARCHIVE_INVALID を足す  → BUMP（schema v2・**下流の lock が止まる**）
description にずれを書く        → HOLD
対照 何も変えない               → HOLD
対照 enum から 1 つ削る         → HOLD_RECORD
```

版を上げずに、次の 3 つで閉じました。

1. **schema 自身が**「この v1 では `ARCHIVE_INVALID` を表現できない」と名指しで書く
2. こちらの生成器が、表現できない status を**近い値へ丸めずに止まる**（`process.exit(1)`）
3. ずれが `ARCHIVE_INVALID` **1 個だけ**であることをテストで固定（7 個目が増えたら落ちる）

**丸めないことが要点です。**「archive が壊れていた」を「取れなかった」に化けさせると、
受け手が通信の問題と改竄を読み分けられなくなります。

### 受け手側でどうすればよいか

**道具を直接回したときの stdout は、この schema の対象ではありません。**
`ARCHIVE_INVALID` はそのまま出ます（`exitCode` 2）。`status` を allowlist で持っている場合は、
**`SOURCE_UNAVAILABLE` とも `MISMATCH` とも別のもの**として足してください。

```
SOURCE_UNAVAILABLE  取れなかった。**検証していない**
ARCHIVE_INVALID     取れたが archive が壊れているか敵対的。**中身を信用しない**
MISMATCH            読めたが記録と合わない
```

**v2 へ上げるかは未決**です。実際に自己申告が必要になった日に判断します。

## 7. 次に確かめてほしいこと

### 直したはずのものが本当に直っているか

前回の反例を、**そちらで組み直して**当ててください。こちらの再現を信じないでください。

```
① 一致する記録と矛盾する記録を両方入れる → verified が false になるか
② その 2 件の順序を入れ替える           → 出力が完全に同一か
③ 分解能 1.0 mm の記録を入れる          → 認定されないか。**かつ矛盾扱いにもならないか**
④ 粗い測定器（0.1 mm）で 1.45 mm ずれた値 → **矛盾として検出されるか**
⑤ recordId が重複した台帳              → INVALID_LEDGER になるか
⑥ 同名 tar entry / symlink ループ / 巨大な圧縮入力 → 止まるか・JSON が出るか
```

**③ と ④ の組み合わせが要点です。**「粗いから認定しない」と「粗いから矛盾を見逃す」は別で、
後者になっていたら直っていません。

### 塞ぎすぎていないか

**正常な入力が弾かれるようになっていないか**を見てください。
特に `maxCompressedBytes` 64 MB と、同名 entry の拒否です。
実物の source tarball は 9.76 MB なので余裕はあるはずですが、
**そちらの環境の archive で試して**ください。

### claim scope の書き方が足りているか

`scope=geometry-only` を文字列の中に置きました。**構造化されていません**（型が `string` のため）。
下流がこれを機械で読むとき、この形で足りるかを見てください。
足りないなら、profile v4（BUMP）を払う価値があるかどうかの判断材料になります。

- **実測が 1 件も来ていません。**ジャック内部の接点位置は全部仮定です。
- **導通測定も音響測定もしていません。**

  **どちらも「最初の実測記録が入る前に」という条件つきで、その条件がまだ来ていません。**
  実測しました: 台帳の記録 **0 件** / profile 中の `MR####` の出現 **0 件** /
  `evidenceSources` を足すと profile v4（**BUMP**）。**中身が空のうちに下流を止めません。**
