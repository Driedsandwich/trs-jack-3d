# v0.2.0 — Schema v2（**破壊的変更**）と release evidence の自己完結化

> **草案です。tag も公開もしていません。**
> 配布物を作るには clean checkout から `--release` 付きで artifact を作り直す必要があります
> （現在の artifact は `artifactKind: local` で、`npm run release:stage` は既定で拒みます）。

## v1 を期待している実装へ

**この版は `schemaVersion: 2` です。読み込む前に必ず版で分岐してください。**

```
schemaVersion === 1 を期待する実装は、2 を受け取ったら停止してください。
語彙の対応表は profile の contractMigration にあります。
```

**そのまま読むと沈黙して壊れます。**v0.1.0 → v0.1.1 で実際に起きました。
`spreadStatus` の enum を非互換に変えたのに `schemaVersion` を据え置いたため、
下流の adapter が `spreadStatus !== 'MEASURED'` で全 event を弾き、
**エラーも警告も出さないまま汚染検出が丸ごと素通り**しました。

## 変わったもの

| | 旧 | 新 |
|---|---|---|
| `schemaVersion` | 1 | **2** |
| `schemaId` | （無し） | **`half-plug-topology-profile.v2`** |
| `topologyClass` | `fully-seated` | **`all-expected-functions-match`** |
| profile のファイル名 | `half_plug_topology_profile.v1.*` | **`half_plug_topology_profile.v2.*`** |

ファイル名も変えたのは、**下流の release lock が `filename` で引く**ためです。
名前が同じまま中身の契約だけ変わると、lock が同じ名前で非互換な内容を指します。

### 追加された項目

| 項目 | 意味 |
|---|---|
| `contractMigration` | v1 → v2 の対応表。旧語彙で読む実装が何を直せばよいかを機械可読で持つ |
| `mechanicalInsertion` | 電気的に全機能が揃う深さと、機械的な完全挿入の**差**（TRS×TRRS で 0.48 mm） |
| `coordinateSystem.normalizedScope` | `PROFILE_LOCAL`。**profile 内の座標である** |
| `coordinateSystem.crossProfileComparable` | `false`。同じ normalized 値が別 profile で同じ電気状態を意味する保証はない |
| `sensitivitySummary.eventSpreadAvailable` / `globalSummaryAvailable` / `basis` | 感度の「有無」を 2 つに分けた |

## なぜ `fully-seated` をやめたか

「プラグ肩が当たった」と読めますが、実体は `reasonCode` のとおり
`ALL_EXPECTED_FUNCTIONS_MATCH` でしかありません。

**名前を直すだけでは同じ誤読が起きる**ので、差を数字でも出します。

```
TRS×TRRS  電気的に全機能が揃う  13.52 mm
          機械的な完全挿入      14.00 mm
          差 (gapMm)             0.48 mm
```

## 版の選び方は実測で決めました

`contractRevision` を足すだけでも良さそうに見えますが、**下流が読んでいなければ意味がありません。**
実際に両方を import させて確かめました。

| 方式 | 下流 (`half-plug-emulator` v0.4.3) の反応 |
|---|---|
| `schemaVersion` を 2 にする | `Unsupported profile schemaVersion: 2` で**停止** |
| `contractRevision` を足すだけ | **PASS**（どこも読んでいない） |

沈黙を避けるという目的に対して、答えは 1 つしかありませんでした。
この判断の根拠は profile の `contractMigration.versionSelectionEvidence` にも入れてあります。

## release asset に足したもの

v0.1.1 では**受け手が確かめられないこと**が 3 つありました。
どれも「こちらは知っているが渡していない」だけだったので、渡します。

| asset | 何が確かめられるようになるか |
|---|---|
| `validation-results.json` | こちらで意味規則が通っているか。判定は `validate:profiles` と**同一実装** |
| `source-input-manifest.json` | `provenance.inputFiles[].sha256` を tag source と独立に検算できる |
| `test_counts.json` | **tag 時点の件数** |
| `event-sensitivity.v1.schema.json` / `topology-robustness.v1.schema.json` | 感度・頑健性 artifact を受け手が検証できる（v0.1.1 では**入れ忘れ**） |

一覧は `scripts/releaseAssets.mjs` に固めました。**その場で選ぶのをやめます。**

## テスト件数（**tag と main を混ぜない**）

v0.1.1 のとき、引き継ぎ文に **260 件**と書きました。これは tag ではなく**その後の main** の値で、
v0.1.1 tag の `test_counts.json` は **258 件**でした。tag と main を混ぜて数えた誤りです。

| | 件数 |
|---|---:|
| v0.1.0 tag | 249 |
| v0.1.1 tag | 258 |
| **この版（tag 作成時に確定）** | **`artifacts/test_counts.json` の値をそのまま載せること** |

**この欄に main の値を書かないこと。**同梱の `test_counts.json` が正本です。
