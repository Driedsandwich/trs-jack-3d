# v0.6.3 — **schema は 1 本も上げていません。下流はどこでも止まりません**

## ⚠ 先に読むところ

### 1. **検算ツールがまた `OK` と言いながら別のものを渡せました**（`toolVersion` 8）

v0.6.2 で直したつもりの穴が、**3 つ残っていました。**
外部監査（2026-08-06）が反例を出し、こちらで再現してから直しています。

3 つとも同じ形です——**「検算が見た source の中身」と「ふつうに `tar` で展開してできる中身」が食い違う。**
`shasum` を通しても意味がなくなるので、どれも P0 です。

**PAX の上書き指示に「従わない」だけで、止めてもいなかった**

v7 は PAX（`x` / `g`）entry を「中身をファイルとして拾わない」ようにしていました。
しかし **PAX は後続 entry の意味を変えられます。**

```
ヘッダの名前 root/file.txt ／ PAX path=root/other.txt ／ 中身 EXPECTED
  v7 の検算 : file.txt = EXPECTED を「source にあった」と言う   status OK
  実際の展開: root/other.txt ができる。root/file.txt は存在しない

ヘッダの size 8 ／ PAX size=4 ／ 中身 ABCDEFGH
  v7 の検算 : file.txt = ABCDEFGH（8 バイト）                   status OK
  実際の展開: root/file.txt = ABCD（4 バイト）
```

**拾わないことと、無かったことにするのは別です。**

v8 は PAX のレコードを読みます。`path=` は**解釈します**（GNU tar が長いパスに使う正当な機能なので、
拒むと実物が通らなくなります）。見え方を変える鍵は止めます。

```
止める鍵   size / linkpath / hdrcharset / SCHILY.realsize / GNU.sparse.*
通す鍵     path（解釈する）／ comment・mtime・SCHILY.xattr.* など見え方を変えないもの
```

読めない形式（長さ欄が無い・改行で終わらない・`=` が無い）も止めます。
**読めないものを黙って飛ばすと、そこに何が書いてあっても通ってしまう**ためです。

**読み飛ばす entry に、正規化の検査をかけていなかった**

v7 は「リンクやディレクトリの**名前も覚える**」ようにしましたが、
正規化の検査（`.` を含む・空のパス要素）は通常ファイルにしかかけていませんでした。

```
regular root/file.txt        = FIRST          ← 検算はこちらを見る
symlink root/./file.txt -> target.txt         ← 別の綴りなので衝突しない扱いだった
regular root/target.txt      = SECOND
  v7 の検算 : file.txt = FIRST   status OK
  実際の展開: root/file.txt は symlink になり、辿ると SECOND
```

v8 は**すべての entry 型に、同じパス検査を先にかけます。**

**パスの前後の空白が消えていた**

v7 はヘッダの文字列を、数値欄と同じく `.trim()` していました。

```
ヘッダの名前 "root/file.txt␠"（末尾に空白）
  v7 の検算 : root/file.txt を検証        status OK
  実際の展開: "root/file.txt␠" という別のファイルができる
```

v8 は数値欄（実装によって空白で詰められるので `trim` が要る）とパス欄（NUL 終端を落とすだけ）を
分け、パス要素の前後に空白があれば止めます。途中の空白は許します——`my file.txt` は正当な名前です。

### 2. **反例の 1 つは、前から手元にありました**

`pax-x-path` という材料は **v0.6.0 から corpus に置いてあり**、それでも落ちませんでした。
期待値が「PAX ヘッダをファイルとして拾っていないか」だったからです。

**材料は正しく、判定基準がコードと同じ思い違いを共有していました。**
期待値を人が書く限り、この形の見落としは何度でも起こります。

そこで **期待値を手で書くのをやめました。**同じ tar を `tar` コマンドで実際に展開し、
できた木と比べます。

```
要件はひとつだけ
  検算器が読めたなら、その各キーは、展開してできた通常ファイルとして
  同じ中身で存在しなければならない。
  止まった（ARCHIVE_INVALID）なら、食い違いは起こりえないので合格。
```

**何を拒むべきかを人が決めなくてよい**のが要点です。参照実装との差分がそのまま欠陥になります。
`test/tarExtractionOracle.test.ts`（36 件）にあります。

### 3. **生成器が、宣言していないファイルを読んでいました**

**これは前の版で私が入れた依存です。**v0.6.2 で「空の予測での読み替え」を直すために
`artifacts/real_jack_comparison.json` を読むようにしたのですが、
このファイルは入力の範囲（`source-input-scope.v1.json`）に入っていません。

```
real_jack_comparison.json の中身を変える
  → 判定に使う予測が変わる
  → inputDigest は動かない
  → 受け手の検算は status OK / 32 of 32 / 未記録 0 件 のまま
```

直し方は「読む先を入力に足す」ではなく「**読まなくて済むようにする**」を採りました。
`artifacts/` は生成物なので、入力にすると自己参照になります。

判定に使った予測そのものを、配布物へ記録します。

```
modelLimitations.physicalVerificationRef の末尾に
  TRS   predicted=RING_BREAK_OPEN_DEPTH_MM:8.06,TIP_BREAK_OPEN_DEPTH_MM:12.02
  TRRS  predicted=L_FIRST_CONTACT_SHOULDER_GAP_MM:2.14,RING_BREAK_OPEN_DEPTH_MM:8.48,TIP_BREAK_OPEN_DEPTH_MM:11.92
```

検証側は、記録された値と profile の event 列から再計算した値が **1e-6 を超えてずれたら error** にします。
`real_jack_comparison.json` は「あれば追加で見る第二の意見」に降格しました——
**無くても通り、あって食い違えば error を足します。**

`import` を辿る閉包検査だけでは、この依存は見えませんでした
（`readFileSync` でパスを直書きする経路は import グラフに現れません）。
**直接のファイル読み込みも静的に走査して照合する**テストを足しました。

## 塞ぎすぎていないこと

**最初の PAX 実装は、実物の macOS `tar` が作った tar.gz を弾きました。**原因は 2 つです。

- **レコード長をバイトでなく文字で数えていた。**実物は `SCHILY.xattr.com.apple.provenance` に
  生バイナリを書きます
- **`SCHILY.` を一括で拒んでいた。**`SCHILY.xattr.*` は見え方を変えません

どちらも直したうえで、次を確かめています。

- 実物の GitHub tarball が通る（**v0.5.2 で 246 ファイル・v0.6.2 で 284 ファイル**。
  どちらも `pax_global_header` を含む）
- 26 個・6 種類の壊れた tar は、`pax-x-path` / `pax-x-size-override` の 2 件が
  `safe` → `ARCHIVE_INVALID` へ変わったほかは v7 と同じ結末
- 正常な tar・gzip・ディレクトリ entry を含む tar は今までどおり

## 変わっていないもの

- **モデルの数値**。接点位置も走査結果も同じです（上の葉ノード比較）。
- **`verifiedPhysical` は `false`**。実測記録は依然 **0 件**で、それが正しい状態です。
  `predicted=` が載ったのは「判定に何を使ったか」を記録したためで、**測ったからではありません。**
- 過去 release の asset。**v0.1.0 以降の 265 件すべて byte 一致**であることを、
  再生成の段ごとに対照つきで実測しています。
- `ARCHIVE_INVALID` は v1 の自己申告 schema では表現できないままです（→ v0.6.1 notes）。
  `status` の種類は増えていません。
