# trs-jack-3d v0.6.13 — 前の版の誤り 4 件と、その直し方

**この 2 版（v0.6.12・v0.6.13）は新機能ではなく、こちらの誤りの訂正です。**
外部監査の指摘ではなく、**別の作業の途中でこちらが見つけた**ものが 4 件あります。

添付は公開物そのものです（29 ファイル・`shasum -c` が exit 0）。

---

## 1. 誤り 4 件を `docs/ERRATA.md` にまとめました

**公開した release 本文は編集しません。**編集すると受け手が読んだ文と手元の控えがずれ、
しかも本文のほうが黙って書き換わるので、「いつ何が直ったか」が誰にも分からなくなります。
代わりに正誤表へ積み、**気づいた方法と再現手順**を付けました。

| # | 対象 | 誤 → 正 |
|---|---|---|
| 1 | v0.6.11 notes | `VERIFICATION_INCOMPLETE` になるのは「v0.3.0 より前」→ **「v0.4.0 より前」**（v0.3.0 自身も対象） |
| 2 | v0.6.11 notes | 「通す材料 66 件」→ **実際に通るのは 72 件**（旗の数だった） |
| 3 | v0.6.11 **配布物** | 同梱 artifact が status を 5 種類と書いていた → 道具は **8 種類**返す |
| 4 | v0.6.12 までの**配布物** | 検算ツールを別名で走らせると**無言で `exit 0`** |

**3 と 4 は配布物そのものの誤りです。**profile・digest・検算結果は正しく、
**受け手向けの説明と入口の判定**が間違っていました。

正誤表は
[`docs/ERRATA.md`](https://github.com/Driedsandwich/trs-jack-3d/blob/v0.6.13/docs/ERRATA.md)。

## 2. 入口の判定を直しました（誤り 4 件目）

v0.6.12 まで、入口は `/verifyReleaseSourceInputs\.mjs$/` という**ファイル名の正規表現**でした。
受け手がコピーの名前を変えたり symlink を張ったりすると、**検算せずに終了コード 0** を返します。

**公開物そのもので測った結果です。**

```
                                v0.6.12 の公開物   v0.6.13 の公開物
verifyReleaseSourceInputs.mjs      4,318 B           4,318 B
renamed.mjs                            0 B ←無言     4,318 B
link.mjs（symlink）                    0 B ←無言     4,318 B
```

**終了コードだけを見る受け手には、合格と区別が付きません。**
`if node verify.mjs ...; then echo OK; fi` のような書き方だと、**検算していないのに OK** になります。

v0.6.13 は `realpathSync` を**両側に**掛けて「起動された本体か」で判定します。
片側だけだと symlink 経由を取りこぼします——Node は既定で実 path を解決して module を読むので、
`import.meta.url` は実体を指すのに `process.argv[1]` は symlink のままだからです。

> **同梱の手順どおり（名前を変えずに）回していれば起きていません。**
> 黙る経路は JSON を 1 バイトも出さないので、**出力を読んでいたなら気づけています。**

## 3. `toolVersion` は 16 に据え置きました

規則は道具側・schema 側とも「**判定の意味を変えたら上げる**」です。
**据え置きの根拠を、公開物どうしで実測しました。**

```
① 判定が変わっていないか
   v0.6.12 と v0.6.13 の道具に同じ入力 → 出力は **byte 一致**（cmp exit 0）
   対照: 引数を変えると 83 行差
② 黙る経路は toolVersion を出すか
   v0.6.12 を別名で → 出力 0 B / toolVersion の出現 **0 件**
   v0.6.13 を別名で → 出力 4,318 B / toolVersion 1 件
③ 見分けは付くか
   tool.sha256   v0.6.12 e2925e8013596215 / v0.6.13 48e91238f483abe6
```

**②が決め手です。**黙る経路は JSON を出さないので、
**`toolVersion` を読める受け手が「16 なのに挙動が違う」に出会う場面がありません。**
版で見分ける必要が生じないので上げませんでした。

> **承知のうえの副作用**: v0.6.12 と v0.6.13 の道具は**版数では見分けられません。**
> 「別名で走らせたときに黙るか」で区別したい場合は `tool.sha256` を見てください。
> **ここは判断が分かれるところだと思っています。**そちらの見立てを聞きたいです。

## 4. 4 件のうち 3 件は、同じ形でした

**同じ境界を、検査されない一覧がもう 1 つ持っていた。**

```
境界「この材料は通るのか」   期待値表（毎 run 実測と突合・緑）
                            ／ 材料ごとの ok 旗（読み手 1 か所・`!ok` としてのみ）
                            → 10 件ずれ。公開文書の「通す材料 66 件」は旗の数

境界「status は何種類か」    CLI_STATUSES（道具の定数・権威）
                            ／ schema の enum（試験が一致を assert）
                            ／ **artifact 内の手順書の 1 行（誰も検査していない）**
                            → 5 種類と書いてあった。実際は 8 種類

境界「この artifact が       schema の status.enum
書ける status は」          ／ 生成器に手書きされた 5 値（試験がソースを正規表現で読んで比較）
                            → 書き方を変えれば拾えなくなる検査だった
```

**2 つ目が「表」の顔をしていないのが厄介でした。**旗・配布物の説明文・生成器の中の定数は、
どれも同じ境界の写しなのに、**データ構造として見えません。**
「数を文章に書く」時点で 2 つ目の一覧を作っていることになります。

直し方は全部同じで、**権威を 1 つ決めて、他は生成する**です。

```
corpus の ok 旗       消して test/_tarExpectations.mjs へ一本化
                      引けない材料は例外にする（黙って「通る」側へ落とさない）
status と終了コード    CLI_STATUS_EXIT を正本にし、配布物の手順書はそこから生成
自己申告の表現範囲     scripts/selfReportStatus.mjs へ切り出し、schema の enum を正本に
                      関門を投げる関数にしたので、試験が実際に踏める
```

## 5. 直す前に「嘘の一覧でも緑か」を実測しました

**これが今回いちばん効いた手順だと思っています。**

| 変異 | 直す前に落ちた試験 | 直したあと |
|---|---:|---:|
| corpus の `ok` 旗を 1 件反転 | **0 件** | 期待値を嘘に → 2 件 ／ 種類の既定を消す → 5 件 |
| 手順書の一覧に偽の `TOTALLY_FAKE(9)` を足す | **0 件** | 2 件 |
| 手順書から新しい status を 1 つ落とす | — | 2 件 |
| 手順書の終了コードだけ嘘にする | — | 2 件 |
| 入口を名前判定へ戻す | — | **4 件** |

最初に試した変異（手順書の 5 語を 2 語に減らす）は 2 件を落としました。
**しかし中身を見ると、どちらも一覧の正しさを見ていませんでした**——
片方は artifact の digest が変わったこと、もう片方は `SOURCE_UNAVAILABLE` という
**1 語がべた書きで残っているか**を見ていただけです。
そこで**実際の欠陥と同じ形**（5 語を残して偽の語を 1 つ足す）で取り直すと、**0 件**でした。

**「変異が捕まった」で満足すると、捕まえた理由を確かめ損ねます。**

## 9. 反例のいただき方

**実データで再現できる形だと助かります。**具体的には次の 3 つがあると、こちらで同じものを踏めます。

1. **材料そのもの**（tar を組み立てるコード、または base64 の bytes）
2. **どの実装で何が起きるか**（`bsdtar` / GNU `tar` / `python -m tarfile` のどれで、
   exit code と stderr の 1 行）
3. **期待する挙動**（通すべきか止めるべきか。止めるなら `ARCHIVE_INVALID` と
   `ARCHIVE_UNSUPPORTED` のどちらか）

そのうえで、次を見ていただきたいです。

1. **§3 の `toolVersion` 据え置きの判断。**版で見分けられないことを許容してよいか。
2. **§4 の形の穴が、ほかにも無いか。**——**いちばん見てほしいのはここです。**
   同じ境界を 2 つ以上の一覧で持っていて、片方しか検査していない箇所。
   1 セッションで 3 つ出たので、**まだあると思っています。**
3. **入口の判定が塞ぎすぎていないか。**`realpathSync` が解決できない起動のされ方
   （消えた実体・権限）では CLI として走りません。**その判断が妥当か。**
4. **`--allow-unpinned-scope` を付けても `OK` にしない**判断が過剰でないか。
5. **BusyBox の結果。**根拠が「どちらでも取れていない」5 件のうち 2 件。
