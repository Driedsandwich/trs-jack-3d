# trs-jack-3d v0.6.7 — 前回の指摘 6 群を直し、必須 oracle を 2 実装同時に効かせた版の確認

前回の監査（v0.6.6・2026-08-10）で出た **P0 3 件と P1 3 件を、こちらで確かめてから**直しました。
添付は公開した release asset **28 ファイル**そのものです。

**今回のパケットも checksum が合いました**（`shasum -a 256 -c` が exit 0）。

## 1. 添付をどう扱うか

```
28 ファイル / 1,886,571 B
SHA256SUMS      27 件ぶんの checksum（自分自身は含まない）
```

**まず `shasum -a 256 -c SHA256SUMS` を通してください。**
こちらでは公開物を取り直して 27/27 OK でした。合わなければ、そこから先は読まなくて構いません。

## 2. **v0.6.6 以前の `OK` は、「その木が作れる」ことを示していません**

**受け手に直接影響するのはこちらです。先に書きます。**

```
regular root/src ／ regular root/src/model/a.ts
  検算 v11  READ（files に src と src/model/a.ts の両方）／ status OK
  bsdtar    exit 1 — Could not stat root/src/model/a.ts: Not a directory
  python    exit 2 — NotADirectoryError
  （そちらの GNU tar / BusyBox も tree を作れない）

symlink root/src -> elsewhere ／ regular root/src/model/a.ts
  検算 v11  READ ／ 4 実装すべて tree を作れない
```

**祖先が通常ファイルや symlink でも、その下の entry を受理していました。**
v0.6.5 で「先頭 1 階層が directory か」を塞ぎましたが、
**それは途中の階層でも同じことが起きるという一般形の、特殊な場合でした。**

こちらの実測では、hardlink を祖先にする形と、順序を逆にした 2 形も同じく通っていました
——**そちらの反例は 2 個ですが、同じ穴から 5 形が作れます。**

### **お願い: v0.6.6 以前で出た `OK` のうち、リンクを含む source は取り直してください**

**`status OK` は「記録された入力の sha256 が合う」ことしか言っていません。**
v0.6.6 までは、そこに **「その木が実際に作れる」という保証が入っていませんでした。**

該当するのは、**symlink や hardlink を含む archive**、
とくに**リンクの下に entry がある形**です。`v0.6.7` の道具で取り直してください。

**v0.6.7 は祖先の型を両方向で見ます。**
（① あとから来た子の祖先が非ディレクトリ ② あとから来た非ディレクトリがすでに祖先）

## 3. 残りの指摘

### linkname の上書きに状態機械が無かった（P0-B）

```
global の linkpath   検算 v11 READ（黙って無視）
                     bsdtar は root/ln -> root/t1 ／ python は root/ln -> root/t2  **別の木**
linkpath を 2 回      bsdtar exit 1 ／ python は 1 つ目
上書きのあとに entry 無し  2 実装とも Damaged / ReadError なのに READ
```

名前の上書きには v0.6.4 から状態機械があるのに、**指す先の側には無かった**ということです。
`inventory` に記録する指す先も、**上書きが効いたあとの値**に直しました。

### PAX の値の契約（P0-C）

`uname`/`gname` を厳密 UTF-8 で読み、時刻・uid・gid に範囲を置きました。
時刻の上限は **±(2^53−1)＝この道具が誤差なく持てる整数の上限**です。

### **こちらの過剰拒否が 3 版続けて（P1-A / P1-B）**

```
負の時刻 mtime=-1（GNU tar がふつうに書く）    4 実装とも展開できるのに拒んでいた
hardlink の連鎖 A → B→A → C→B                 同上
指す先の別の綴り root/./A ・ ./root/A ・ root//A  同上
```

通すようにしました。**`..` と末尾スラッシュは通しません**——そこは実装間で割れます。

### **そちらの指摘に無い false-OK を 1 件、こちらの実測で見つけました**

```
hardlink の指す先が / で終わる（root/B -> root/A/）
  検算 v11  READ            ← 受理していた
  bsdtar    exit 1 — Can't create 'root/B': Not a directory
```

v0.6.6 は末尾スラッシュを剥がしてから照合していたので、
**剥がした結果は存在するので通り、実際には展開できません。**

### `ARCHIVE_UNSUPPORTED` を新設（P1-C）

そちらの提案どおりに分けました。

| | 意味 |
|---|---|
| `ARCHIVE_INVALID` | 矛盾・破損・曖昧、または展開できない |
| `ARCHIVE_UNSUPPORTED` | ふつうの tar なら展開できるが、**この道具の範囲の外** |

base-256 の数値欄・typeflag 7 / S / D / M / N・資源上限・未知の vendor 鍵が後者です。
**exit code は両方 2 のままで、`OK` にはなりません。**

## 4. **CI を GNU tar と bsdtar の matrix にしました。最初の run で 2 つ見つかりました**

そちらの §11 の案（Docker 不要・ubuntu と macOS の matrix）をそのまま採りました。

```
ubuntu-latest   tar (GNU tar) 1.35 / Python 3.12.3
macos-latest    bsdtar 3.5.3 - libarchive 3.7.4 / Python 3.14
fail-fast: false（どちらで割れたのかが要る）
```

**入れた最初の run は、macOS 緑・ubuntu 赤（8 件失敗）でした。**

```
① 止める理由の表が、片方の platform しか見ていなかった（8 件）
② 木を歩く試験の道具が、名前を UTF-8 文字列で読んでいた（1 件）
   Linux は不正 UTF-8 のファイル名を作れるので lstat が ENOENT になる
   macOS の APFS は作れないので、**この欠陥は macOS では出ない**
```

**どちらも archive の扱いではなく、確かめる側の欠陥でした。**
3 回目の run で両 runner とも緑になっています。

**通す材料 24 件は GNU tar でも 1 件も落ちませんでした。**
勧告に従わなかった 2 件（`comment` を strict にしない・`uname` の NUL を拒まない）は、
**2 実装ではなく 3 実装で裏が取れた**ことになります。

## 5. **止める理由 20 件が、どちらの実装で裏を取れたか**

```
GNU tar 側でだけ根拠が取れる   9 件
bsdtar 側でだけ根拠が取れる    8 件
どちらでも取れていない         3 件
```

| どこで取れるか | 中身 |
|---|---|
| **GNU tar のみ 9** | PAX の値が数値でない 4 件（`Malformed extended header`）・uid/gid が 32bit 超 2 件（`is out of range 0..4294967295`）・`mtime=+1`・名前と指す先の上書きが 2 つ効く形が各 1 件（**片方の順序だけ**木が割れる） |
| **bsdtar のみ 8** | PAX の `g` 上書き 2 件（bsdtar と python が別の木）・`uname`/`gname` の不正 UTF-8 2 件（libarchive の locale 変換）・パスの不正 UTF-8 4 件 |
| **どちらでも取れない 3** | 名前・指す先の上書きの**もう片方の順序** 2 件・`..\evil.txt`（Unix ではふつうの名前、Windows では 1 階層上） |

**そちらが報告した GNU tar の挙動は、メッセージまでそのとおりでした**
（`Extended header gid=4294967296 is out of range 0..4294967295`）。
**「POSIX の書式に無いから」という推論で止めていた `mtime=+1` も、GNU tar は拒みました**——
判断の根拠が推論から実測へ変わりました。

**逆向きも起きています。**bsdtar でだけ取れる 8 件は ubuntu では根拠が消えます。
とくにパスの不正 UTF-8 は、**受け手の OS で展開結果が変わります**——
macOS では 2 実装とも `Illegal byte sequence` で作れず、Linux では両方作れます。

> **どちらか片方の実装だけでは、止める理由の半分が見えません。**

一覧は `test/tarExtractionOracle.test.ts` の `EVIDENCE_ELSEWHERE` にあり、
**どこで根拠が取れるかを毎 run 両方向で照合します**
（自分の実装で取れると書いてあるのに取れない → 落ちる。
別の実装で取れると書いてあるのにこちらでも取れる → 表が古いとして落ちる）。

```

```

**この文書から転記せず、添付の `trs-jack-3d-release-index.v1.json` から引いてください。**

**動いたのは `package-lock.json`（入力）が版数上げで変わったからです。**
検算ツールは配布物ですが**入力ではない**ので、v11 → v12 にしても digest を動かしません。

**モデルの数値は変わっていません。**葉ノードまで平坦化した実測です。

```
TRS   葉 2267 件 → 由来まわりの差 10 件 / モデル数値の差 0 件
TRRS  葉 3130 件 → 由来まわりの差 10 件 / モデル数値の差 0 件
```

この比較が「全部を由来に寄せているだけ」ではないことも確かめてあります——
`fullInsertionDepthMm` を 14 → 14.001 に変えると **「モデル数値の差 1 件」**になります。

## 8. 次に確かめてほしいこと

優先順に並べます。**指摘は反例（再現手順・期待した結果・実際の結果）を添えてください。**
こちらで再現できたものだけ直します。**再現できなかったものは、そう書いて判断を分けます。**

1. **祖先の不変条件を、まだすり抜けられないか。**
   **今回いちばん効いた指摘なので、ここを続けて突いてください。**
   ディレクトリ entry の末尾スラッシュ・`prefix` 欄と `name` 欄の組み合わせ・
   PAX `path` で祖先を後から変える形・root を剥がす前後で祖先関係が変わる形などが候補です。

2. **v0.6.7 も、正当な archive を拒んでいないか。**
   **過剰拒否は 3 版続けて出しています。**通す材料は 24 件に増やしましたが、まだ足りないはずです。
   star・古い GNU tar・非 ASCII のパス・sparse・`SCHILY.*` 系の他の鍵などが候補です。

3. **「どちらでも根拠が取れていない 3 件」をどう扱うべきか。**
   名前・指す先の上書きが 2 つ効く形は、**片方の順序でしか割れませんでした**
   （GNU tar でも bsdtar でも、もう片方の順序は 2 実装が一致します）。
   そちらの 4 実装測定では両方割れると報告されています。
   **BusyBox で割れているのか、版の違いなのか**、分かれば教えてください。

4. **`ARCHIVE_UNSUPPORTED` の切り分けが妥当か。**
   資源上限・base-256・typeflag 7 / S / D / M / N・未知の vendor 鍵を後者にしました。
   **`SUN.holesdata` だけは `ARCHIVE_INVALID` に残しています**
   （bsdtar が `Parse error` で archive ごと拒み、python は通す＝割れるため）。
   この線引きで、下流が困る形になっていませんか。

5. **`source-verifier-cli-result.v1` の項目を詰めたい。**
   そちらの Draft をほぼそのまま採る方向です。
   `stableReasonCode` は throw 箇所ごとに付けることになるので、
   **受け手として実際に分岐に使う粒度**（どこまで細かく分けてほしいか）を教えてください。

6. **BusyBox を必須にすべきか、diagnostic のままでよいか。**
   ubuntu の runner に入れる形なら足せます。
   **3 実装目を必須にすると、accepted subset がさらに狭まります**——
   その狭さが受け手にとって困る形になるかどうかの見立てを聞きたいです。
