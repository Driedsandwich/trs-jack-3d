## 2. **v0.6.7 以前の `OK` は、ヘッダの数値欄まで見ていません**

**受け手に直接影響するのはこちらです。先に書きます。**

```
mode=abc / uid=abc / gid=abc / mtime=abc（checksum は取り直し）
  検算 v12  READ — 「a.txt が source にある」と言う
  bsdtar    exit 0 — a.txt を作る
  python    exit 0 — **黙って a.txt を作らない**（OK と表示して終わる）
  GNU tar   Archive contains 'abc\0    ' where numeric mode_t value expected

checksum 欄が「8 進の頭 + junk」
  検算 v12  READ — 同上
  bsdtar    Damaged tar archive と警告して a.txt を作らない
```

**同じ archive から別の木ができます。**受け手が python で展開すると、
検算器が「あった」と言ったファイルが手元にありません。

原因は 2 つです。**`mode` / `uid` / `gid` / `mtime` / `devmajor` / `devminor` は
読んでもいませんでした。**checksum 欄は `/^[0-7]+/` の**前方一致**でしか見ておらず、
そのあとの junk を見逃していました。

### **お願い: v0.6.7 以前で出た `OK` は取り直してください**

**`status OK` は「記録された入力の sha256 が合う」ことしか言っていません。**
v0.6.7 までは、そこに **「ヘッダが正しい」という保証が入っていませんでした。**
`v0.6.8` の道具で取り直してください。

v0.6.8 は `parseTarNumericField` に集約し、**欄まるごと**見ます。
受け入れる形は**実物を測って**決めました（2026-08-11・4 通りありました）。

```
GitHub tarball / git archive   7 桁 + NUL         size と mtime は 11 桁 + NUL
macOS tar (bsdtar)             6 桁 + 空白 + NUL  size と mtime は 11 桁 + 空白
checksum 欄                    7 桁 + NUL ／ 6 桁 + NUL + 空白
```

まとめると「**先頭の空白（任意）＋ 8 進数字 1 個以上 ＋ NUL と空白だけの詰め物**」。
base-256 はどの欄でも `ARCHIVE_UNSUPPORTED` です（v12 は `size` にしか掛けていませんでした）。

## 3. 宙に浮いた local PAX ヘッダ（P0-B）

```
全入力のあとに「x: mtime=1」だけを置き、後続 member を置かない
  検算 v12  READ ／ bsdtar exit 1（Damaged）／ python exit 2（ReadError）
```

v12 は `path` と `linkpath` にしか pending 状態がありませんでした。
**鍵に関係なく `x` は「次の member を待つ」状態を作ります。**
`L` / `K` は member ではないので消費しません（実測: `x` → `L` → member は 2 実装とも通る）。
`x` が 2 つ続く形は止めます（実測: bsdtar は `Ignoring malformed pax extended attribute`）。

## 4. **過剰拒否が 4 版続けてです。先頭ゼロは、そちらの勧告どおりの正規表現が原因でした**

```
directory の PAX path が / で終わる      2 実装とも同じ木を作るのに拒んでいた
PAX の値の先頭ゼロ（uid=0001 など）      同上
歴史的な signed checksum                 同上
backslash を含むパス                     Unix では 3 実装とも同じ木
```

**先頭ゼロは、前回そちらが勧めた `^-?(0|[1-9][0-9]*)(\.[0-9]+)?$` をそのまま採った結果です。**
POSIX pax の値は 10 進の数であって、綴りを 1 つに決めてはいません。
**範囲の検査は綴りではなく、読んだあとの値に掛けます**（`BigInt('0001')` は 1）。

> **勧告を機械的に採ると、その勧告自体が過剰拒否になりうる**——今回それが起きました。
> **次からは、勧告どおりに書いた検査も corpus の「通す」側で試してから出します。**

綴りの検査は **member の型が分かるまで遅らせ**、末尾スラッシュは directory のときだけ許します。
通常ファイルで `/` が付く形は止めます——実測で
**bsdtar は directory を作り、python は通常ファイルを作る**からです。

checksum は **unsigned と signed の両方**を計算し、どちらか合えば受けます
（どちらにも合わないヘッダは、これまでどおり落ちます）。

backslash は `ARCHIVE_UNSUPPORTED` に移しました（そちらの §7 の分類どおり）。
**壊れているのではなく、受け手の OS で意味が変わる**からです。

## 5. 差分試験を型つき木にし、python を必須にしました（そちらの §6）

- 比べるのは**パスの一覧ではなく型つきの木**（型・指す先・中身のバイト）です。
  v12 は名前だけを並べていたので、**同じ名前で片方が directory・片方が通常ファイル**でも
  差が出ませんでした。
- **python が無ければ「合格」ではなく失敗**にします。
  必須 oracle が動いていないなら、それは合格ではなく「確かめていない」です。

**確かめる側の欠陥も 1 つ見つかりました。**`mode` 欄を壊した archive を展開すると
**権限 0 のファイル**ができ、木を歩く道具が読めずに試験が止まっていました。
読めなかった事実を木に記録する形に直したら、**この件は手元でも根拠が取れました。**

## 6. 止める理由 21 件の内訳と、**生の数値欄が 0 件になったこと**

```
GNU tar 側でだけ根拠が取れる   9 件
bsdtar 側でだけ根拠が取れる    9 件
どちらでも取れていない         3 件
```

**生の数値欄（`raw-*`）の拒否は、この表に 1 件も残っていません。**
どちらかの実装で必ず根拠が取れます。

```
raw-mode-not-octal   GNU tar 1.35: Archive contains 'abc\0    ' where numeric mode_t value expected
                     bsdtar は権限 0 の読めないファイルを作り、python は mode を丸める
                     → **両 platform で根拠が取れるので、表に載せない**
```

**そちらが報告した GNU tar の挙動は、メッセージまでそのとおりでした。**

`none` の 3 件は、名前・指す先の上書きが 2 つ効く形の**片方の順序** 2 件
（そちらが BusyBox で裏を取ったと報告している 2 件です）と、
**symlink の名前が `/` で終わる形**です。最後の 1 件は手元の 2 実装が同じ木を作りますが、
**typeflag は symlink・名前は directory と、entry が自分自身と矛盾している**ので止めています。

## 9. 次に確かめてほしいこと

優先順に並べます。**指摘は反例（再現手順・期待した結果・実際の結果）を添えてください。**
こちらで再現できたものだけ直します。**再現できなかったものは、そう書いて判断を分けます。**

1. **生のヘッダに、まだ読んでいない欄が残っていないか。**
   `typeflag`・`linkname`・`magic`/`version`・`uname`/`gname`（固定長欄のほう）・`prefix` は、
   **書式そのものを見ていません。**ここが今回と同じ穴になっていないか突いてください。

2. **数値欄の受け入れ範囲が狭すぎないか。**
   「先頭の空白＋ 8 進数字 1 個以上＋ NUL と空白の詰め物」にしました。
   **star・古い GNU tar・Solaris tar が別の書き方をしていないか**を見てほしいです。
   実物 4 種類（GitHub tarball・git archive・macOS tar・自作）でしか測れていません。

3. **`x` の pending 規則が厳しすぎないか。**
   `x` が 2 つ続く形を止めています（bsdtar が拒むため）。
   **正当な tar がこれを書く場面**はありますか。

4. **`stableReasonCode` の粒度。**
   そちらの §8 の family 一覧を採る方向です。
   **受け手として実際に分岐に使う粒度**（どこまで細かく分けてほしいか）を教えてください。
   `HEADER_NUMERIC_FIELD_SYNTAX` を欄ごとに分けるべきか、1 つで足りるかも含めて。

5. **BusyBox を必須にすべきか。**
   ubuntu の runner に入れる形なら足せます。
   **3 実装目を必須にすると accepted subset がさらに狭まります**——
   その狭さが受け手にとって困る形になるかどうかの見立てを聞きたいです。

6. **`none` の 3 件のうち、symlink の末尾スラッシュ**をどう扱うべきか。
   手元の 2 実装は同じ symlink を作ります。**entry が自分自身と矛盾しているから止める**
   という理屈だけで拒んでいます。この判断で問題ありませんか。

**この版の弱点として、こちらが自覚しているもの:**

- **必須 oracle は 2 実装（GNU tar / bsdtar）まで。**BusyBox は入っていない
- **正当な archive を拒む欠陥が 4 版続けて出た。**しかも今回は**勧告どおりに書いた検査**が原因
- **止める理由 21 件のうち 3 件は、どちらの実装でも裏が取れていない**
- 検査の側にも版ごとに穴があった（v8 は片方向、v9 は oracle 1 実装、
  v12 は表と木の歩き方が片方の platform しか見ていなかった、
  **v13 では木を歩く道具が読めないファイルで落ちていた**）
- 生のヘッダの**文字列欄**（`typeflag` 以外）はまだ書式を見ていない
- `verifiedPhysical` は **実測記録 0 件のまま**で、`ASSUMPTION` が 54 件ある
- 導通・音響の実測はしていない
- annotated tag に署名していない
