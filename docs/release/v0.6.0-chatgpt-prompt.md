## 1. `verifiedPhysical` を条文と記録から機械で決めるようにした

v0.5.2 まで、この 1 行は **`scripts/exportHalfPlugProfile.ts` のリテラル `false`** だった。
schema の説明は「`true` にできるのは実測記録が伴う場合のみ」だけで、
**何を何点測れば足りるのかがどこにも無かった。**
つまり実態は「**誰かがリテラルを書き換えたら `true`**」で、検証ではなかった。

```
条文    docs/VERIFIED_PHYSICAL_GATE.md（全8条）
台帳    docs/measurements/measurement-records.v1.json（**記録 0 件**）
判定器  scripts/measurementGate.mjs
```

**記録が 0 件なので `false` のまま。それが正しい状態である。**
実測は募集しているが必須にしていない（`docs/VERIFICATION_PLAN.md` 冒頭の方針は変えていない）。

条文で効いているのは次の 4 つ。

| 条 | |
|---|---|
| 第1条 | `true` は**必須観測点が裏付けられた**ことだけを言う。全値が実測とは言わない |
| 第2条 | **必須観測点が定義されていない profile は必ず `false`**（空集合を合格にしない） |
| 第4条 | 予測は artifact から引かず、**生成器がその場で計算した値**と照合する |
| 第6条 | 台帳を `inputDigest` に入れない理由と、代わりの縛り方 |

**判定器は合成の記録で全部試験してある**（記録 0 件で `true` にできない／1 件消すと `false` へ落ちる／
揃えば `true`／変異 9 種が 1 件ずつ鳴る／予測が渡されないと満たせない）。
**実測が 1 件も来ていなくても、ここは確かめられる。**

**そちらから見て変わるのは `physicalVerificationRef` である。**`null` → 文字列。

```
docs/measurements/measurement-records.v1.json@sha256:dfe5020f9198 gate=docs/VERIFIED_PHYSICAL_GATE.md@v1 records=0 required=L_FIRST_CONTACT_SHOULDER_GAP_MM satisfied=- missing=L_FIRST_CONTACT_SHOULDER_GAP_MM rejected=0
```

**`null` を期待して分岐している実装があれば、そこだけ直すこと。**
schema は `["string","null"]` のままなので型としては壊れていない。

## 2. `evidenceGrade` は区分を増やさず、`sources` で分ける（案B）

**実測値も `FACT` に置く。**`FACT` の意味を「データシート・図面の記載寸法」から
「**一次情報**（記載寸法、および条文どおりに受け取った実測記録）」へ広げた。

```
記載寸法  sources: ["ds-1532-10"]   一次資料の ID
実測      sources: ["MR0001"]       docs/measurements/ の記録 ID
```

**両案を条文の判定器（`scripts/schemaLanguageDiff.mjs`）に当ててから決めた。**

| 案 | 変更 | 判定 | 差分 |
|---|---|---|---:|
| **B（採用）** | `grade` の `description` を広げる | **`HOLD`** | 0 件 |
| A（見送り） | `enum` へ `MEASURED` を足す | **`BUMP`**（profile v4・**下流が止まる**） | 4 件 |

対照: `enum` から 1 つ削ると `HOLD_RECORD`、同一 schema 同士は `HOLD`。**判定器は黙っていない。**

**A を見送った理由は「いま入れる値が無い」こと。**`FACT` **53 件はすべて記載寸法で、実測由来は 0 件**（実測）。
中身が空のうちに下流を止めると、**止める理由を実物で説明できない。**

### そちらでやること

**`grade` を見て「記載寸法か実測か」を区別しないこと。`sources` を見ること。**
分ける必要がある場面は実在する（第三者の再現可否／記載公差と実測ばらつきの違い／別部品への一般化）が、
**すべて `sources` で足りる。**

## 3. 信頼できない archive への防御 — **26 個・6 種類で実測した**

同梱の `verifyReleaseSourceInputs.mjs`（`toolVersion` 4 → **5**）。

**parser を直す前に、壊れた tar を作る道具のほうを先に作って試した。**
材料が空振りしていると、parser の試験は「同じ 1 個を 26 回通した」になる。

```
種類ごとに 4 個以上／id が全部ちがう／**byte 列が全部ちがう**
checksum の valid と bad が実際に違う（対照つき）
狙った細工が実際に入っている（../evil.txt・/etc/passwd など 5 件）
**正常な tar には細工が入っていない**（対照）
```

           cksum-bad-second           ARCHIVE_INVALID  files=0

           res-huge-entry             ARCHIVE_INVALID  files=0

**`READ` になる 4 種類は「止める必要が無い」ものである。**
PAX とリンクは**拾わないこと**が要件なので、止めずに読み飛ばし、
`files` に混ざっていないことをテストで固定している。

### 直した中身

| 何 | v4 | v5 |
|---|---|---|
| header checksum | 見ていなかった | 検算する |
| PAX（`x` / `g`） | **中身をファイルとして拾っていた** | 拾わない。**上書き指示にも従わない** |
| `..` / 絶対パス / `\` | そのまま登録していた | 止まる |
| symlink / hardlink | ファイルとして扱っていた | 読み飛ばす |
| entry 数・サイズ・パス長・総量 | 上限が無かった | 上限を超えたら止まる |
| `fetch` | timeout が無かった | 60 秒 |

**PAX の `path=` を honor しないのは意図的である。**従うと、checksum を通った名前とは
別の名前で登録できてしまう。実物の GitHub tarball は `pax_global_header` を 1 個持つだけで、
ファイル名の上書きには使っていない（実測）。

### 上限は実物を測ってから決めた

```
実物 v0.5.2  gz 9.76 MB → tar 15.09 MB（1.5 倍）
             entry 268（ファイル 246 / ディレクトリ 21 / pax global 1）
             最大 entry 1.33 MB ／ 最長パス 95 文字
上限         entry 5,000 ／ 1 entry 8 MB ／ 総量 256 MB ／ パス 1,024 文字（実測の 6〜20 倍）
```

**「実測より広い」と「無限に広くはない」の両方をテストで固定した。**
片側だけだと、上限を巨大にして通すことができてしまう。

### 塞ぎすぎていないことの確認方法

```
合成した正常な tar                    → 通る（entry 2 件が読める）
gzip をかけても                       → 通る
**実物の v0.5.2 tarball**             → 通る（ファイル 246 件・先頭階層の剥がしも同じ）
上限のすぐ内側（パス 800 文字）        → 通る
CLI の end-to-end（--source src.tar.gz）→ missingInSource 0 件
```

**合成だけで確かめない。**実物の tarball は PAX を含むので、合成材料では踏まない形がある。

### 材料の側にも空振りがあった

`res-long-path` は素の USTAR ヘッダに長いパスを書いていた。
**`name` 欄は 100 バイトなので切り捨てられ、上限を試験できていなかった**（`READ` で通っていた）。
GNU long name 経由へ直して `ARCHIVE_INVALID` になることを確認した。
**parser の試験を書いて初めて、材料の穴に気づいた。**

## 4. `ARCHIVE_INVALID` の分離 — **そちらの実装への影響**

v4 まで、次の 2 つは**どちらも `SOURCE_UNAVAILABLE`** だった。

```
source を取れなかった              （無い・繋がらない・応答しない）
source は取れたが archive が壊れている（checksum 不正・敵対的な entry・上限超過）
```

**記録を保存しても、通信の問題なのか改竄なのかを読み分けられない。**v5 で分けた。

| status | 意味 | exit |
|---|---|---:|
| `OK` | 全件一致 | 0 |
| `MISMATCH` | 読めたが記録と合わない | 1 |
| **`ARCHIVE_INVALID`** | **取れたが安全に読めない。中身を見ていない** | 2 |
| `SOURCE_UNAVAILABLE` | 取れなかった。検証していない | 2 |
| `MANIFEST_UNAVAILABLE` | manifest を読めなかった | 2 |
| `NOTHING_TO_VERIFY` | 入力 0 件で何も見ていない | 2 |

**`exit code` は 2 のままなので、exit code で見ている実装は影響を受けない。**
**`status` で分岐している実装だけ**、`ARCHIVE_INVALID` を足すこと。
`SOURCE_UNAVAILABLE` だけ見ていると、**壊れた archive を素通りする。**

**`ARCHIVE_INVALID` を「不一致」と読まないこと。**中身を見ていない。
理由は `reason` に文字列で入る（`detail` に補足）。**安定した ID は付けていない**ので、
機械で分岐するなら `status` までにすること。
