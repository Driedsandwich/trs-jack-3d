## 1. **v0.6.17 の attestation に欠陥がありました。公開した直後に自分で見つけました**

前回この場で「attestation を新設した」と報告しました。その attestation が、
**配った索引とは別のものを指していました。**

添付を検算する手順（前回そちらへ渡した手順そのもの）を自分で回して見つけました。

```
v0.6.17 の attestation が名乗る 3 つの digest を、添付の実物と突き合わせる
  testCountsSha256         一致
  validationResultsSha256  一致
  releaseIndexSha256       **不一致**

  名乗り  e9c72e2412fa6e21…  ← **repo 側**の索引（releaseTag: null）
  実物    a014768129b56e18…  ← 受け手が計算する値
```

**「ほとんど合ってしまう」のが、いちばん危ないところでした。**

`test_counts.json` と `validation-results.json` は配布時に**そのまま写す**ので、
repo 側を測っても同じ値になります。**索引だけが写しではありません**
——`releaseTag` と `releaseCommit` を配布時に書き込むためです。

つまり **3 つのうち 2 つは一致し、ずれるのは受け手が最初に引く 1 つだけ**でした。
2/3 が合っていると「概ね正しい」に見えます。**そこで止めずに 3 つとも突き合わせたから見つかりました。**

原因は、attestation を書く工程が `resolve(ROOT, …)` を測っていたことです。
**「検証した物と出荷した物を別にしない」の再発**で、この repo で繰り返している型です。

公開済みの v0.6.17 の asset は**上書きしていません**（`docs/ERRATA.md` §23）。

## 2. **v0.6.18 の公開物で 3/3 一致を確かめました**

測る先を `OUT`（配布物の側）へ直しました。**直ったことを、公開物そのもので検算しています。**

```
v0.6.18 の添付で attestation の 3 digest を突き合わせる
  testCountsSha256         5079b51c1296ba2a…  一致
  validationResultsSha256  d329b9b3bfb95f45…  一致
  releaseIndexSha256       dcb0ee72ddbbbdb7…  **一致**   ← v0.6.17 ではここだけ不一致だった
対照  別ファイルの digest と比べると不一致を検出
```

検査も入れました。**値の一致だけを見ると、写しである 2 つで通ってしまう**ので、
「`resolve(ROOT,` を含まないこと」を名指しで見ます。
変異対照: `resolve(ROOT, …)` へ戻すと**その検査だけが落ちます**（他 8 件は緑のまま）。

**上げていない根拠（すべて実測）:**

## 4. 分離の基準を repo へ入れました。**最初の基準には穴がありました**

「変えていない」はそれ自体では確かめられないので、**分離の前に**基準を取りました。

```
scripts/cliOutputBaseline.mjs
test/fixtures/cli-output-baseline.v1.json   10 経路
  takenFromCommit dab485c2260c（分離前）/ toolSha256 b208399106bb1d97…（分離前）
npm run check:cli-output   CI にも段として入れた
```

**基準そのものを repo へ入れたのは、報告した証拠を受け手も再現できるようにするためです。**
`JSON.parse` して比べず **byte で比べます**——キーの順序が変われば受け手の差分も変わるためです。

### 最初の基準は live な artifact に依存していました

`OK` 経路を `--source .`（作業ツリー）で測っていたので、
**証拠を作り直した時点で `OK` 経路だけが不一致**になりました。

**取り直す前に、原因を切り分けました。**

```
同じ（再生成後の）artifact に対して
  分離前の道具  6deeb0c4090efdbb…
  分離後の道具  6deeb0c4090efdbb…   → 一致。**分離は出力を変えていない**
基準（再生成前の artifact 時点）  c04a4d80d12d7fc8…
  → 差は artifact の再生成によるもので、道具ではない
```

**「一致しなかった」で取り直すと、基準の意味が消えます。**
原因が入力側だと分かったので、`OK` 経路を**固定 fixture**（`test/fixtures/ok-source/`）へ移し、
**分離前の道具へ戻してから**取り直しました。

```
実測  artifacts/ を丸ごと退避しても、fixture 経路の出力は byte 一致
      （＝本番の生成物を読んでいない）
```

## 5. `SOURCE_ARCHIVE_MISSING` を実経路として踏みました

前回 `race-defensive`（到達しうるが決定的には踏めない）と宣言した code です。
**踏めました。**「決定的には踏めない」は**踏む試験を書いていなかっただけ**でした
——v0.6.15 で `SOURCE_HTTP_ERROR` などを取り違えたのと同じ形です。

```
loadFromDir      existsSync(abs)  … 通る
                 lstatSync(abs)   … ディレクトリでない → loadFromArchive へ
loadFromArchive  existsSync(abs)  … **ここで消えていればこの code**
```

**同じ path に対する 2 回目の `existsSync`** だけ false にすれば踏めます。
`node:fs` を差し替えて注入します——**道具は 1 バイトも変えません**
（`globalThis.fetch` の差し替えと同じ形）。

```
catalog  race-defensive → **cli-route**
         82 種類 = corpus 45 / cli-route 34 / defensive-invariant 3
両方向照合  この run で出た 79 種類・到達しないと宣言した 3 種類（実測と一致）
```

### ⚠️ **`io` へ fs を足したことは、この経路には効いていません**

```
同じ注入（node:fs の差し替え）を当てる
  io に fs が無い版  → SOURCE_ARCHIVE_MISSING
  io に fs を足した版 → SOURCE_ARCHIVE_MISSING
```

`node:fs` の差し替えは **ESM の named import にも効く**ので、
`io` を経由してもしなくても同じように踏めます。
**この経路のために `io` へ fs を足す必要はありませんでした。**

残した理由は先の話です——`main(args, io)` を抽出したあとは
global を差し替えずに注入できます。**いまは土台であって、いま効いているわけではありません。**
効いていないものを効いていると書かないでおきます。

## 6. **途中で 4 回止まりました。どれも原因を測ってから進めました**

```
① 基準が実行ごとに変わった
   一時ディレクトリ名（mkdtemp）が reason に出るため。置き場を固定パスへ

② 固定した途端、並行実行で消し合った
   単独では通り、同じ表を使う 3 ファイルを同時に走らせると 2 件落ちる。
   各試験ファイルの afterAll が固定パスを消していた
   → **固定した瞬間、そこは共有物になる**

③ 契約を変えない版で検査が落ちた
   「準備中の版には必ず migration の記録がある」と決め打っていた。
   v0.6.18 は schema を 1 本も変えないので記録は 0 件

④ ③ の直しが片方の枝だけだった
   tag を打つ前は通り、**打った直後の CI で落ちた**
   ——同じ決め打ちが tagExists 側にも書いてあった
```

**④ が今回いちばん恥ずかしい形です。**「同じ問いの答えを 2 か所に書いていた」——
この repo で繰り返し直してきた型そのものを、**その型を直している最中にやりました。**
記録の有無で先に分ける形にし、3 通り（tag 有×記録 2 件／tag 有×記録 0 件／tag 無×記録 0 件）で
通ること、各枝が変異で落ちることを実測しています。

これは **v0.6.16 で schema の母集団に `--others` を足したのと同じ穴**が、

> 対照を一度作り損ねました——日本語のファイル名で試したら検出せず、
> 検出器が `[A-Za-z0-9_]` 始まりしか拾わないためでした。**対照の作り方が悪かっただけ**で、
> ASCII 名で取り直して検出を確認しています。「検出しない」と読み違えるところでした。

## 8. 次は `main(args, io)` の抽出そのものです

**この版でやったのは、接点を 1 か所に集めたところまで**です。
`done()` はまだ `io.exit` を叩きます。戻り値だけで完結する形にするのは次です。

```
やる     main(args, io) が { code, stdout, stderr } を返す形へ
         CLI 側が受け取って exit する
検証     同じ基準（10 経路）で byte 一致を確かめる。1 バイトでも動いたら止める
やらない ファイル分割・判定ロジックへの変更
```

抽出が済んだら、**global を差し替えずに fs を注入できる**ようになります
（§5 で足した `io` の fs が、そこで初めて効きます）。
