# 検算ツール `verifyReleaseSourceInputs.mjs` を v8 にしました（受け手向け）

対象: 配布物に同梱している `verifyReleaseSourceInputs.mjs`
出力の `toolVersion` が **7 → 8** になります。

v7（v0.6.2）の続きです。**v7 で塞いだつもりだった穴が 3 つ残っていました。**
外部監査（2026-08-06）が反例を出し、**こちらで再現してから**直しています。

## 3 つとも同じ形の欠陥です

**「検算が見た source の中身」と「ふつうに tar で展開してできる中身」が食い違う。**

`shasum` を通しても意味がなくなる形なので、どれも P0 です。

### 1. PAX の上書き指示に「従わない」だけで、止めてもいなかった

v7 は PAX（`x` / `g`）entry を**中身をファイルとして拾わない**ようにしていました。
しかし **PAX は後続 entry の意味を変えられます。**

```
ヘッダの名前 root/file.txt ／ PAX path=root/other.txt ／ 中身 EXPECTED
  v7 の検算 : file.txt = EXPECTED を「source にあった」と言う   status OK
  実際の展開: root/other.txt ができる。root/file.txt は存在しない

ヘッダの size 8 ／ PAX size=4 ／ 中身 ABCDEFGH
  v7 の検算 : file.txt = ABCDEFGH (8 バイト)                    status OK
  実際の展開: root/file.txt = ABCD (4 バイト)
```

**拾わないことと、無かったことにするのは別です。**

v8 は PAX のレコードを読み、**後続の意味を変える鍵があれば止めます。**

```
止める鍵   path / linkpath / size / GNU.sparse.* / SCHILY.* / RHT.*
通す例     comment / mtime など、ファイルの見え方を変えないもの
```

読めない形式（長さの区切りが無い・改行で終わらない・`=` が無い）も止めます。
**読めないものを黙って飛ばすと、そこに何が書いてあっても通ってしまう**ためです。

> **PAX を完全に実装する道は採りませんでした。**sparse や `linkpath` まで正しく扱う面積は、
> この道具が引き受けるべき量を超えます。**意味を変える鍵があったら止める**ほうを選びました。
> 実物の GitHub tarball は `pax_global_header`（`comment` のみ）を 1 個持つだけなので、通ります。

### 2. 読み飛ばす entry に、正規化の検査をかけていなかった

v7 は「リンクやディレクトリの**名前も覚える**」ようにしましたが、
**正規化の検査（`.` を含む・空のパス要素など）は通常ファイルにしかかけていませんでした。**
そのため、リンクの名前を別の綴りにするだけで衝突検査をすり抜けられました。

```
regular root/file.txt        = FIRST         ← 検算はこちらを見る
symlink root/./file.txt -> target.txt        ← 別の綴りなので衝突しない扱いだった
regular root/target.txt      = SECOND
  v7 の検算 : file.txt = FIRST    status OK
  実際の展開: root/file.txt は symlink になり、辿ると SECOND
```

v8 は**すべての entry 型に、同じパス検査を先にかけます。**
ディレクトリの末尾スラッシュだけは tar の表記なので剥がしてから見ます。

### 3. パスの前後の空白が消えていた

v7 はヘッダの文字列を読むとき、数値欄と同じく `.trim()` していました。

```
ヘッダの名前 "root/file.txt␠"（末尾に空白）
  v7 の検算 : root/file.txt を検証         status OK
  実際の展開: "root/file.txt␠" という別のファイルができる
```

v8 は**数値欄とパス欄で読み方を分けます。**数値欄は実装によって空白で詰められるので
`trim` が要りますが、パス欄では NUL 終端を落とすだけにし、
**パス要素の前後に空白があれば止めます**（途中の空白は許します——`my file.txt` は正当な名前です）。

## どうやって見つけたか（受け手にも同じことができます）

**期待値を手で書くのをやめました。**

これまでの試験は「PAX ヘッダをファイルとして拾っていないか」のように、
**人が決めた基準**で合否を出していました。その基準がコードと同じ思い違いを共有していると、
材料があっても素通りします。実際、`pax-x-path` という材料は**前から corpus にあり**、
「拾っていないので合格」と判定されていました。

v0.6.3 では、**同じ tar を `tar` コマンドで実際に展開して、できた木と比べます。**

```
要件はひとつだけ
  検算器が読めたなら、その各キーは、展開してできた通常ファイルとして
  同じ中身で存在しなければならない。
  止まった（ARCHIVE_INVALID）なら、食い違いは起こりえないので合格。
```

**何を拒むべきかを人が決めなくてよい**のが要点です。参照実装との差分がそのまま欠陥になります。
`test/tarExtractionOracle.test.ts` にあります。

## 塞ぎすぎていないこと

- 実物の GitHub tarball が通る（**v0.5.2 で 246 ファイル・v0.6.2 で 284 ファイル**。どちらも `pax_global_header` を含む）
- 26 個・6 種類の壊れた tar は、`pax-x-path` / `pax-x-size-override` の 2 件が
  `safe` → `ARCHIVE_INVALID` へ変わったほかは v7 と同じ結末
- 正常な tar・gzip・ディレクトリ entry を含む tar は今までどおり

## 変わらないこと

- **read-only** です。書き込み API を使わず、tar は展開せずメモリ上で読みます
- network は既定で使いません（`--fetch github` を明示したときだけ）
- `status` の種類は増えていません。`ARCHIVE_INVALID` は v5 のままで、
  v1 の自己申告 schema では表現できないままです（既知）
