# v0.6.2 — **schema は 1 本も上げていません。下流はどこでも止まりません**

## ⚠ 先に読むところ

### 1. **検算ツールが `OK` と言いながら別のものを渡せた**（`toolVersion` 7）

**これがこの版でいちばん重い修正です。**受け手を直接誤らせる欠陥でした。

v0.6.1 の検算ツールは、tar の中の**同じ場所を指す別の綴り**を別ファイルとして受理していました。

```
root/file.txt    = FIRST      ← 検算はこちらを「source にあった」と言う
root/./file.txt  = SECOND     ← ふつうの tar で展開するとこちらが残る
  → status OK / matched 1
```

```
regular root/file.txt  = FIRST      ← 検算はこちらを見る
symlink root/file.txt -> target.txt ← 展開すると file.txt はこのリンクになる
regular root/target.txt = SECOND    ← 辿った先はこちら
  → status OK
```

**検算が見た中身と、ふつうに展開してできる中身が食い違います。**
「合っている」と言いながら別のものを渡せるので、checksum を通す意味そのものが無くなります。

v7 で直したこと。

| | v7 |
|---|---|
| `.` を含むパス | `ARCHIVE_INVALID` |
| 空のパス要素（`//`・末尾 `/`） | `ARCHIVE_INVALID` |
| 制御文字を含むパス | `ARCHIVE_INVALID` |
| 読み飛ばす entry（symlink / hardlink / ディレクトリ）と同名のファイル | `ARCHIVE_INVALID` |

**正規化して受け入れるのではなく拒みます。**畳んだ先が衝突したときにどちらを採るかを
新たに決めることになるためで、正しい source archive にこの綴りは出てきません。

**塞ぎすぎていないことも同じテストで見ています。**実物の GitHub tarball は
**246 ファイルのまま**通り、26 個・6 種類の壊れた tar は v6 と同じ結末です。

### 2. **`profileId` が「何を入力にして作ったか」を指していませんでした**

v0.6.1 まで、生成器が `import` している実行コードの一部が入力に入っていませんでした。

```
scripts/measurementGate.mjs を書き換える
  → profile の中身は変わる（physicalVerificationRef に出る）
  → profileId    38b692a12af6 のまま
  → inputDigest  変わらない
  → 受け手の検算 status=OK / 30 of 30 / 未記録 0 件
```

**中身が変わったのに ID が同じなら、受け手は ID で区別できません。**

直したあと（実測）。

```
profileId 6df4546829d9 → aec8c7ea85c5 ／ 検算 MISMATCH 31/32
```

`scripts/contractMigration.mjs` と `scripts/measurementGate.mjs` を入力へ入れました。
入力は **30 → 32 件**です。

個別のファイル名を並べるだけだと次に足した `import` で同じ穴が空くので、
**`import` を実際に辿って宣言と突き合わせるテスト**を入れてあります。

### 3. `profileId` が変わりました。**lock を作り直してください**

```
v0.6.1  trs-jack-3d:TRS|JACK-TRS:38b692a12af6
v0.6.2  trs-jack-3d:TRS|JACK-TRS:0661012b839d

v0.6.1  trs-jack-3d:TRS|JACK-TRRS:eaccc9119c92
v0.6.2  trs-jack-3d:TRS|JACK-TRRS:1628038f74bf
```

**報告文から転記せず、同梱の `trs-jack-3d-release-index.v1.json` から引いてください。**

**ID が動いたのは入力の集合が変わったからで、モデルの数値は変わっていません。**
それがこの版の目的そのものです（実行コードを変えても ID が動かない状態を直しました）。
区間・event の数も接点位置も同じです。

### 4. **契約は変わっていません**

```
v0.6.1 の schema 22 本 → v0.6.2
  HOLD 22 / HOLD_RECORD 0 / **BUMP 0**
新設 0 本
```

`source-input-scope.v1` を上げずに済ませるため、生成器ごとの依存欄を作らず
`commonInputs` に置きました。判定器で実測したところ、欄を足すと `BUMP` になり
下流の lock が止まります。**入れすぎ（関係ない生成器の ID まで動く）と
入れ忘れ（変えても ID が動かない）なら、入れすぎのほうが安全側**です。

## そのほか直したもの

### 検証器が「予測が無いから true でよい」と読み替えていた

`validate:profiles` は plain node なのでモデル（TypeScript）を読めません。
v0.6.1 まではそのため空の予測で判定を呼び、
**「予測が渡されていない」を「まだ `true` を名乗ってよい」と読み替えていました。**

実測: モデルの予測 2.14 mm と **1.45 mm 食い違う記録**が台帳にあっても、
手で `verifiedPhysical: true` にした profile をこの規則では拒めませんでした。

配布物だけから予測を組み直すようにしました。

| 観測点 | どこから出すか |
|---|---|
| `RING_BREAK_OPEN_DEPTH_MM` / `TIP_BREAK_OPEN_DEPTH_MM` | profile 自身の event 列 |
| `L_FIRST_CONTACT_SHOULDER_GAP_MM` | `real_jack_comparison.json` の `testerPredictions.assumed.L` |

**組み直せない観測点は満たせません**（fail closed）。空で呼ぶのと同じにはしません。
生成器は自分の計算値がこれと一致することを確かめてから書くので、2 つの経路が黙ってずれません。

### ディレクトリ入力に資源上限が無かった

`--source <ディレクトリ>` は、**検証に使わないファイルまで全部メモリへ読んで**いました。

```
scope 対象 6 バイト + scope 外 70 MB
  v0.6.1  最大 RSS 114.8 MB（status は OK）
  v0.6.2  最大 RSS  43.6 MB（ARCHIVE_INVALID で止まる）
```

上限は archive と同じ値を使います——片方だけ緩いと、緩いほうから入られます。

### 空振りしていたテストを直した

パス長の境界試験が、**上限 1024 のすぐ内側ではなく 100 文字の壊れたパスを試していました。**
素の USTAR の name 欄が 100 バイトしかないためです。GNU long name 経由に組み直しました。

  `status` の種類は増えていません。
