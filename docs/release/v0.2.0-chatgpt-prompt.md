## 1. 何が壊れるか — 3 か所を実際に特定した

`half-plug-emulator v0.4.3` の `integrations/trs-jack-3d/` を読んで、止まる場所を名指しで出した。

| # | 場所 | 止まり方 |
|---|---|---|
| 1 | `release-verifier.mjs:127` `profile.schemaVersion !== 1` | **停止**（`Unsupported profile schemaVersion: 2`） |
| 2 | `topology-adapter.mjs:102` `TOPOLOGY_MAP` に該当なし | **停止**（`Unsupported electrical topology: all-expected-functions-match`） |
| 3 | `topology-adapter.mjs:106` `topologyClass === 'fully-seated'` | **沈黙**（下記） |

**1 と 2 で止まるのは意図した設計。**v0.1.0 → v0.1.1 では enum を非互換に変えたのに
`schemaVersion` を据え置き、そちらの adapter が**エラーも警告も出さないまま**
汚染検出を素通りさせた。沈黙より停止のほうが安全なので、今回は版を上げた。

### ⚠ 3 が本題 — 1 と 2 を直しても、3 は直らない

```js
// topology-adapter.mjs:106
if (topologyClass === 'fully-seated' && interval.nominalStartMm < profile.fullInsertionDepthMm) {
  warnings.push('ELECTRICALLY_NORMAL_BEFORE_MECHANICAL_FULL_INSERTION');
}
```

`TOPOLOGY_MAP` に `all-expected-functions-match` を足すと 2 は消える。
**そのとき 106 行目は旧名のままなので、この警告が黙って出なくなる。**
エラーも警告も出ない。v0.1.1 で踏んだのと同じ型である。

この警告のもとになる数字は profile 側に持たせた。条件式ではなくこちらを使うほうがよい。

```
mechanicalInsertion: {
  completeAtMm               14.00   ← プラグ肩が当たる深さ
  firstAllFunctionsMatchAtMm 13.52   ← 電気的に全機能が揃う深さ (TRS×TRRS)
  gapMm                       0.48
}
```

TRS×TRS では `gapMm` が **1.66**（12.34 → 14.00）。**variant で違う。**定数にしないこと。

## 2. `contractMigration` の読み方

profile の直下にある。**旧語彙で読んでいる箇所を機械的に洗い出すための表**である。

```json
{
  "fromSchemaVersion": 1,
  "toSchemaVersion": 2,
  "breaking": true,
  "schemaId": "half-plug-topology-profile.v2",
  "previousSchemaId": "half-plug-topology-profile.v1",
  "renamedEnumValues": [ { "field": ..., "from": ..., "to": ..., "introducedIn": ..., "reason": ... } ],
  "addedFields":       [ { "field": ..., "introducedIn": ... } ],
  "consumerAction": "...",
  "versionSelectionEvidence": "..."
}
```

使い方は 2 つ。

1. **`renamedEnumValues[].from` を自分のコードに grep する。** 当たった箇所が直す対象。
   `topology-adapter.mjs:106` はこれで見つかる。
2. **`introducedIn` を見る。**`spreadStatus` の 3 件は
   `"v0.1.1 (schemaVersion 1 のまま変えてしまった)"` と書いてある。
   **こちらの過去の失敗を表に残してある。**同じ判断がまた通らないようにするため。

`versionSelectionEvidence` には、なぜ `contractRevision` ではなく `schemaVersion` を上げたかが入っている。
**両方を実際に import させて決めた。**

| 方式 | そちらの `release-verifier.mjs` の反応 |
|---|---|
| `schemaVersion` を 2 にする | `Unsupported profile schemaVersion: 2` で**停止** |
| `contractRevision` を足すだけ | **PASS**（どこも読んでいない） |

## 3. `release-lock` の `filename` を直す必要がある

**profile のファイル名が変わった。**

```
旧  half_plug_topology_profile.v1.trs_jack_trrs.json
新  half_plug_topology_profile.v2.trs_jack_trrs.json
```

名前も契約の一部にした。そちらの `release-lock-v0.1.1.json` は
`profiles[variantId].filename` でファイルを引くので、**名前が同じまま中身の契約だけ変わると、
lock が同じ名前で非互換な内容を指すことになる。**それを避けた。

## 4. 同梱した 3 つの evidence で何が検算できるか

v0.1.1 では**そちらが確かめられないこと**が 3 つあった。どれも
「こちらは知っているが渡していない」だけだったので、渡す。

### `validation-results.json`

こちらで意味規則が通っているか。**判定は `scripts/validateProfiles.mjs` と同一実装**で、
CLI と同じ関数を呼んでいる（別実装にすると「コマンドは通るのに evidence は古い」がいつか起きる）。

```
targetsTotal 8 / targetsPassed 8 / allPassed true
generatedFromCommit 0a0e124b0399
```

各 target の `schemaErrors` / `semanticErrors` は**件数だけでなく本文も入っている**（0 件なら空配列）。
**ただしこれは生成時点のこちらでの判定にすぎない。**同梱の schema で自分で検証すること。

### `source-input-manifest.json`

`provenance.inputFiles[].sha256` を **tag source と独立に検算する**ための一覧。

```
inputFilesTotal 28 / inconsistentAcrossArtifacts 0 / mismatchedWithWorkingTreeAtBuild 0
```

`inconsistentAcrossArtifacts` は「同じパスが artifact 間で違う sha256 で現れた数」。
0 でなければ、どれかの artifact が古い入力から作られている。

**この manifest 自身は証明ではない。**検算の手順は `verificationRecipe` に書いてある。
GitHub の tag source archive を取って、`inputFiles[].path` の sha256 を自分で計算して突き合わせること。

### `test_counts.json`

**tag 時点の件数。**v0.1.1 では同梱しておらず、こちらが報告した 260 件が
tag の値なのか main の値なのか判別できなかった。

## 5. テスト件数は **363** — これは tag の値

```
v0.1.0 tag  249
v0.1.1 tag  258
v0.2.0 tag  363   ← 今回。skipped 0 / 14 ファイル
```

**363 は同梱の `test_counts.json` の値そのもの。**main の値ではない。

v0.1.1 のとき、こちらは引き継ぎ文に **260 件**と書いた。それは tag ではなく
**その後の main** の値で、tag は 258 件だった。**tag と main を混ぜて数えた誤り**である。
そちらの §7.3 の指摘が正しかった。今回は同梱してあるので、報告文ではなくファイルを見ればよい。
