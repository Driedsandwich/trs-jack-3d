## 条文を作りました

[`docs/SCHEMA_VERSIONING_POLICY.md`](../SCHEMA_VERSIONING_POLICY.md)

> 新 schema が受け入れる値の集合が、旧 schema のそれに**収まらないなら版を上げる。**
> 判定は**新旧 2 つの schema だけ**で行い、**artifact の中身は見ない。**

最初は「旧 schema を pin した consumer が**今の artifact**を拒むか」で書いていました。
**これは使えませんでした。**同じ schema 変更でも artifact 次第で答えが反転します。

```
v0.3.0 schema × 現物（role に input-scope を使う）            → 拒む   → 「上げる」
v0.3.0 schema × role を input-scope から戻した同じ artifact   → 受ける → 「据え置き可」
                                              （書き換えたのは 1 項目だけ）
```

enum に値を足しても、その版の artifact がまだ使っていなければ据え置きが許され、
**使い始めた版で突然止まります。**記録が「いつ壊したか」ではなく「いつ使い始めたか」になります。

### `additionalProperties: false` は維持します

schema 20 本すべてが `additionalProperties: false` です。この書き方では
**optional な項目の追加も、pin した consumer は拒みます。**
なので条文には「**項目の追加はすべて版を上げる**」と正直に書きました。
「optional なら据え置き可」とは書いていません（この project では成り立たないため）。

### 条文が判別力を持つことを確かめました

「常に上げる」と言うだけの壊れた判定器でも、過去 9 件には 9/9 で当たります。
それだけでは何も確かめたことになりません。

| 検査 | 結果 |
|---|---|
| 答えが分かっている合成 16 件 | **16/16 一致・うち 7 件は BUMP 以外** |
| 過去へ当てる | **9/9 で「上げるべきだった」** |
| 対照（中身が変わらない schema） | **7 件すべて HOLD**（何にでも鳴らない） |

## 記録が実物とずれないようにしました

`contractMigration` は手で書くと必ず腐ります。実際に腐っていました。

```
"field": "provenance.inputFiles[].role に \"input-scope\" を追加"   ← 項目名の欄に日本語の文
"introducedIn": "v0.1.2 (追加のみ)"                                 ← 存在しない tag
```

v0.5.0 では、記録に **schema への JSON Pointer** と **判定器が出した効果**を持たせ、
4 つの機械検査で突き合わせます。

| | 内容 |
|---|---|
| ① pointer 実在 | `changes[].schemaPointer` が新旧いずれかの schema に実在する |
| ② 判定の一致 | その 2 つの schema へ判定器を当て、`policyVerdict` と `effect` が記録と一致する |
| ③ 網羅 | 判定器が出した差分のうち記録に無いものがあれば落ちる。**全 tag 対を走査**して据え置き違反の取りこぼしも見る |
| ④ 据置きゼロ | v0.5.0 以降に `versionWasHeld: true` が現れたら落ちる |

変異は**検査の外側**からも入れています。記録側を叩くだけでなく、
**schema を書き換えて記録が追随しないこと**も確かめました（8 件すべてで落ちることを実測）。

## オフラインの受け手のための写しを入れました

v0.4.1 で受け手はネットワークが無く `SOURCE_UNAVAILABLE` になりました。
判定としては正しいのですが、**完全にオフラインだと独立検算に着手できません。**

`artifacts/source-snapshot.v1.json`（**77 ファイル / 1.05 MB**）を同梱します。
入力 30 件・生成器・schema が入っています。

**これは producer の申告であって、受け手の独立検証を置き換えません。**
artifact 自身に書いてあります。

```
isSelfConsistencyOnly          true
replacesRecipientVerification  false
isSourceOfTruthForInputDigest  false
```

**通信がある受け手は、写しではなく tag source を使ってください（循環しません）。**

```bash
curl -sL -o src.tar.gz \
  https://github.com/Driedsandwich/trs-jack-3d/archive/refs/tags/v0.5.0.tar.gz
node verifyReleaseSourceInputs.mjs --manifest source-input-manifest.json \
  --source src.tar.gz --scope source-input-scope.v1.json
```

release ページの "Source code (tar.gz)"（GitHub が tag から自動生成）でも同じです。

### なぜ tag source をそのまま添付しないのか

実測しました。

| | 実サイズ |
|---|---:|
| 入力 30 件だけ | 0.45 MB |
| **入力 + `scripts/` + `schemas/`（採用）** | **1.05 MB** |
| tag source archive まるごと | **8.94 MB** |

8.94 MB の増えるぶんは `docs/screenshots/*.png`（1 枚 0.6〜0.7 MB）と
`artifacts/contact_sweep.json`（1.3 MB）で、**どれも受け手の検証には使われません。**

`tar.gz` ではなく JSON にしたのは、**tar.gz が同じ入力から作っても毎回ハッシュが変わる**
（mtime が入る。実測で不一致）ためです。asset は sha256 で固定するので、再現しない形式は使えません。
