## Q1. なぜ `verifiedPhysical` を `true` にできないのか

**実物で確かめていないからです。**それだけです。

| 根拠 | 場所 | 値 |
|---|---|---|
| 実測の有無 | `modelLimitations.verifiedPhysical` | `false` |
| 導通 | `jackBasis.detail.electricalContinuityValidation` | **未実施** |
| 音響 | `jackBasis.detail.acousticValidation` | **未実施** |

昇格させる経路をコードに持たせていません。`test/halfPlugProfile.test.ts` の項目 7 が
`scripts/exportHalfPlugProfile.ts` に `verifiedPhysical: true` という文字列が
現れないことを検査しています。

**何があれば `true` にできるか**は `docs/VERIFICATION_PLAN.md` に手順が書いてあります。
順序は「導通でトポロジーを確かめる → そのあと音響」です。音を先に測っても、
どのトポロジーの音か分からないためです。

> **「実在部品ベース」と「実測された」は別**です。4極ジャックは Lumberg 1503 28 の
> 図面から端子位置を採っていますが、それは接点位置の実測ではありません。

## Q2. PS000001 と Lumberg のどちらを採るべきか

**こちらでは決められません。**両方を持ったまま渡しています。

| 資料 | Tip 接点 | 左右差分の区間 | 性格 |
|---|---|---|---|
| pro-SIGNAL PS000001 | 12.75 mm | **0 件** | 唯一入手できた**断面図**（接点そのものが描かれている） |
| Lumberg 1503 28 | 11.30 mm | 1 件 | **端子**位置。接点位置ではない |

### どちらにも弱点があります

**PS000001 の弱点**: 1 件の製品の図面です。代表性を主張できません
（`referencePart.representativeness` に明記）。

**Lumberg の弱点**: 端子位置を接点位置として使ってよい保証がありません。
`lumbergTerminalScenario.caveat` にこう書いてあります。

> 端子位置を接点位置として使ってよい保証は無い。実在の 4極品には
> 端子の並びが接点の並びと逆のものがある（Cliff FC68125）

### 現在の扱い

モデルは Lumberg 側（端子位置に拘束された仮定）を採り、**PS000001 は採用していません**
（`decision.chosen: "compare-only"`）。ただし比較結果は artifact に残し、
テストで「戻したら落ちる」ようにしてあります。

`result.verdict` の文言:

> 図面値では左右差分の区間が消える。看板の結論は、この 1 件の実在図面には支持されていない

**決着させるには実測が要ります。**`docs/VERIFICATION_PLAN.md` §2-2 に、
どちらが正しいかを 1 回の測定で切り分けるための対抗予測（役割ごとの肩からの隙間）が
表になっています。

## Q3. `inputDigest` はどう再計算するのか

**`provenance.inputDigestScope` に作り方が書いてあります。**

> `inputFiles` を path の昇順に並べ、`"<sha256>  <path>"` を改行で連結した文字列の sha256。
> variant は含まない（`profileId` 側が持つ）。**生成される artifact 自身は含まない。**

`provenance.inputFiles[]` は **22 件**で、それぞれ `path` / `sha256` / `role` を持ちます。

```
role の内訳 (v0.1.0 の実測)
  schema             1   schemas/half-plug-topology-profile.v1.schema.json
  generator          2   scripts/exportHalfPlugProfile.ts / scripts/provenance.ts
  model-data         9   src/data/**
  model-code         8   src/model/**
  lockfile           1   package-lock.json
  sensitivity-input  1   artifacts/sensitivity.json
                    ──
                    22
```

### 再計算する（この 1 行で再現できます）

```bash
jq -j '.provenance.inputFiles | sort_by(.path) | map("\(.sha256)  \(.path)") | join("\n")' \
  half_plug_topology_profile.v1.trs_jack_trrs.json | shasum -a 256
```

**実測で確認済みです。**v0.1.0 の profile に対して実行し、
`provenance.inputDigest` と一致することを確かめました。

```
再計算: bba0e6dc73a4273c7178ede2eaeb40cb518fcf6c9c0c7679d24f15a9a6d821a0
記録値: bba0e6dc73a4273c7178ede2eaeb40cb518fcf6c9c0c7679d24f15a9a6d821a0
```

つまずきやすい点:

- 区切りは **sha256 と path のあいだに半角スペース 2 つ**（`shasum` の出力形式と同じ）
- 行の連結は `join("\n")`。**末尾に改行を付けません**（`jq -r` だと末尾に改行が入るので `-j`）
- `role` は digest に**含めません**（`path` と `sha256` だけ）
- 並び順は `path` の昇順

> **`inputFiles` の件数は版によって変わります。**上の内訳は v0.1.0 のものです。
> 常に artifact の `inputFiles` そのものを使ってください。

## Q4. `spreadMm` が `null` の事象をどう扱うか

**「動かない」と読まないでください。**`spreadStatus` を見てください。

v0.1.0 の TRS×TRRS profile での内訳:

| `spreadStatus` | 件数 | 意味 | 扱い |
|---|---:|---|---|
| `MEASURED` | **7** | その事象そのものを測った幅 | 使えます |
| `NOT_EVENT_SPECIFIC` | **29** | `kind` 単位の集計しか無い | **その事象の幅としては使えません** |
| `NOT_MEASURED` | 0 | 測っていない | 使えません |

`sensitivitySummary.notes` にも書いてあります。

> `spreadMm` が `null` の事象は「測っていない」であって「動かない」ではない。

### `NOT_EVENT_SPECIFIC` の幅が知りたい場合

`sensitivitySummary.aggregateSpreadByKind` に `kind` 単位の集計が残っています。
**ただし個々の事象へ当てはめないでください。**`STATE_CHANGE` の集計は
全接点・全遷移をまたいだ和集合で、事実上「挿入ストローク全域」になります。

### 事象ごとの幅が要る場合

**測り直しが要ります。**現在の感度解析は `kind` 単位でしか記録していません。
`eventId` 単位で測るよう感度解析側を変える必要があり、v0.1.0 には入っていません。
必要なら次の版で対応します。
