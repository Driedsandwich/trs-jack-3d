## 2. 個別対応をやめて **allowlist** にした

`oneOf` を直した直後に同じ形が 3 つ出た。**1 つずつ塞ぐ形では、列挙漏れがそのまま危険側の穴になる。**

> 判定器が正しく扱えると宣言した keyword の集合 `HANDLED_KEYWORDS` を決め、
> **宣言外の keyword が「在る」だけで**（かつその節が新旧で変わっていれば）`UNDEC` へ倒す。

**「変わったら倒す」ではない。「在ったら倒す」である。**
変わっていない keyword が他の keyword の意味を変えるからで、`patternProperties` がまさにこれである
（`properties` から項目を消しても `patternProperties` が拾い続ける／拾わなくなる）。
差分検出を入口にする限り、この型は永久に見えない。

### 宣言集合は機械で数えて決めた

現行 21 schema を走査して、実際に使われている keyword を数えた。

```
使用 keyword 23 種
  type 1507 / description 460 / additionalProperties 257 / properties 218 / required 215
  items 212 / minimum 155 / minItems 133 / pattern 118 / const 116 / enum 75 / $ref 51
  minLength 38 / $schema 21 / $id 21 / title 21 / exclusiveMinimum 19 / minProperties 13
  maximum 12 / maxItems 10 / definitions 8 / oneOf 8 / uniqueItems 5

HANDLED_KEYWORDS 32 種（23 種をすべて含む）
```

テストは 2 方向で縛ってある。

| | 内容 |
|---|---|
| 覆っていること | **現行 schema が使う keyword が宣言集合に無ければ落ちる**（＝宣言外が現れたら落ちる） |
| 全部入りでないこと | 宣言集合が「何でも受ける」なら allowlist ではない。**弾かれる keyword が実在すること**も見る |

下の 13 種は**意図的に宣言外**である。現れたら `UNDEC` へ倒れる。

```
patternProperties  dependencies  dependentSchemas  dependentRequired
if  then  else  not  propertyNames  contains
unevaluatedProperties  unevaluatedItems  prefixItems
```

`format` / `multipleOf` / `deprecated` / `readOnly` / `writeOnly` も入れていない。

## 3. 実装中に 4 件目を見つけた — **節は同じまま参照先だけ変わる**

3 件を直す過程で、どちらの網にもかからない形に気づいた。

```
properties: { x: { $ref: '#/definitions/g', description: '...' } }   ← 節は新旧で完全に同じ
definitions: { g: { type: 'string' } }  →  { g: { type: 'number' } } ← 参照先だけ変わる
```

- allowlist ゲートは「**その節が変わっていれば**」倒す → 節が同じなので鳴らない
- `deref()` は `$ref` が単独キーのときしか辿らない → sibling があるので辿らない

**`HOLD` になっていた。**両側が同じ `$ref` を持つときに参照先同士を比較する経路を足して直した。
回帰試験は 3 件（差分が `/$ref` 位置に出ること・同一 schema 同士は `HOLD` のまま・live に実在すること）。

これはそちらの指摘ではなく、こちらが直す過程で見つけた。**指摘の 3 件だけ塞いでいたら残っていた。**

## 6. `anyOf` / `allOf` を倒さなかった判断は維持している

v0.5.1 でそちらから「`anyOf` / `allOf` も包含を証明できる限定ケース以外は `UNDEC`」と言われて採らなかった。
**allowlist へ変えた今も採っていない。**

`anyOf` は和、`allOf` は積なので、**枝ごとの言語が狭まれば全体も狭まる（単調）。**
枝ごとの再帰比較で健全である。`oneOf`（ちょうど 1 枝）だけが単調でないので、そこは無条件 `UNDEC` にしてある。

ここまで倒すと、狭めただけの変更まで版上げになり、
**条文の判別力（据え置き可を据え置き可と言える能力）が落ちる。**
判別力が無い条文は「全部 BUMP」と同じで、守る意味がない。

現行 21 schema での使用実績:

```
oneOf   8 か所 / 5 本
anyOf   0 か所
allOf   0 か所
```

**`anyOf` / `allOf` は現時点で 1 か所も使っていない。**
つまりこの判断は、いま何かを通しているのではなく、**将来の判別力のための予約**である。
反例があるなら出してほしい。**単調性を破る具体例が 1 つあれば、こちらは倒す。**
