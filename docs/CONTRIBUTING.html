数えた結果 — 構文で洗うのは筋が悪い

test/ 全体（当時 217 件）を機械で洗うと、候補は 142 か所ありました。 1 件ずつ見ると、本当に偽の合格になるのは 7 か所でした（誤検出 95 %）。

for..of（空集合で素通り）870空になるのはモデルが壊れたときで、それは他の数十件が先に捕まえる

検査コマンドそのものが空振りすることもある

2026-08-03、型検査を 3 セッションにわたって「何も検査しない形」で回していました。

$ npx tsc --noEmit -p tsconfig.json    # ← rc=0。しかし 1 ファイルも見ていない
$ npm run typecheck                    # ← tsc -b。こちらが本物
scripts/provenance.ts(31,19): error TS6133: 'relative' is declared but its value is never read.
scripts/searchTopology.ts(210,10): error TS2304: Cannot find name 'classifyFromEvaluation'.

tsconfig.json は "files": [] と references だけを持つ振り分け専用です。 -p で直接指定すると「対象 0 件」で正常終了します。-b（build mode）でないと 参照先（tsconfig.app / node / scripts）へ降りません。

そのあいだ、テストもビルドも通っていました。vitest も vite も型検査をしません。 実際、未定義の関数を呼ぶコードが 1 コミット分すり抜けています （npm run search:topology を実行して初めて ReferenceError で落ちました）。

検査は必ず package.json の script 名で呼んでください。 npx で直接叩くと、引数の違いで黙って対象が空になります。

たまに落ちる検査は、落ちない検査より悪い

2026-08-03、npm run test が 3 回に 1 回落ちる状態を自分で作りました。

test/trrs.test.ts の「どの組み合わせでも、Tip 導体を含む橋絡は起きない」が、 単独では 606 ms、全体では 5463 ms かかっており、vitest の既定 timeout 5000 ms を またいでいました。原因は同日に足した test/sensitivityVariant.test.ts が npx vite-node の子プロセスを並列に起こし、他のワーカーを遅くすることです。

このテストだけが、重いのに明示 timeout を持っていませんでした（近隣は 30_000）。

vitest.config.ts に testTimeout: 30_000 を置いて解消しました。

ここの timeout は性能を測っていません。ハングしたときに永久に止まらないための

保険です。負荷でばらつく値を合否に使うと、「たまに落ちるけど気にしないテスト」が

1 つ生まれます。それは空振りと同じ害です — どちらも検査を信用できなくします。

vite.config.ts ではなく vitest.config.ts が本物です （間違えて vite.config.ts に書き、型検査を壊しました）。

書くときの規則

  1. 成果物の有無で分岐しない。artifacts/ は git 管理下です。existsSync は使いません。 読めなければ落ちるべきです。
  2. ?? [] / ?? null で「引けなかった」を隠さない。 0 件と「引けなかった」が同じ値になる関数を書かない。test/_must.ts の mustFind を使えば、何を探して何があったかがメッセージに残ります。
  3. 列挙した識別子は、実在を先に検査する。 ```ts for (const kind of KINDS) // ← まず実在を見る expect({ kind, inArtifact: a.major.some((e) => e.kind === kind) }) .toEqual({ kind, inArtifact: true }) for (const kind of KINDS) { /* ここで値を比べる */ } ```
  4. 「n 件を検査した」という主張そのものを検査する。 axesUsedPerVariant が {} になると、「振った軸が効く」を 0 回検査したまま通ります。 前提が空でないことを mustBeNonEmpty で見ます。
  5. .find(...)! を機械的に置き換えない。41 か所ありますが、あれは落ちます。 全部書き換えても守りは増えず、差分だけが増えます。

機械が確かめること — npm run check:vacuity

構文を洗い続けるのはやめました。結果の側を見ます。 空振りは形がばらばらでも、必ず次のどちらかで現れます。

  • テストが skip される
  • テストの 件数が減る（ファイルが読めない／動的生成が 0 件になる／消された）

8. やってはいけないこと

  • artifact の数字を書き換えてテストを通す。artifact はモデルの出力です。 文書側を直すか、モデルを直してください。
  • 「確認済み」「検証済み」と単独で書く。何をどう検証したかを添えてください （静的検査／単体テスト／実ブラウザ／実機はすべて別のものです）。
  • 解決した項目を「まだ仮定です」と言い続ける。逆向きも嘘です（→ §1 (c)）。
  • 合成量に、強いほうの入力の区分を付ける。弱いほうに合わせてください（→ §1 (d)）。
  • 語句をそのままテストで固定する。モデルが進んだときに、テストが古い主張を守る側に回ります。 実際に halfPlugProfile.test.ts が「接点位置を含めて全て仮定」を固定し続け、 4極ジャックを実在部品ベースへ組み直したあとも公開 artifact に旧主張が残りました（→ §7・§9）。 固定するのは語句ではなく構造（強い根拠と弱い根拠が分けて書かれていること）にしてください。
  • 成果物の有無でテストを分岐させる。artifacts/ は git 管理下です（→ §7）。
