作成 2026-08-05 ／ 更新 2026-08-06 ／ 状態: 計画のみ。実装していません。

対象は 3 つです。

§1実測が来たとき 1 発で閉じる形にしておく（verifiedPhysical / IV028）

0. 前提 — 実測は募集する。必須にはしない

docs/VERIFICATION_PLAN.md の 2026-08-02 方針をそのまま維持します。この計画で変えません。

メンテナ自身は実測を行いません。（略）

モデルは「未実測のまま」で完結させます。実測は精度を上げますが、

無いと成立しない設計にはしていません。

❌ やらないこと    部品の発注 ／ 自分での測定 ／ 実測値を待つこと
✅ 受け入れること  実測データの提供 ／ 図面や一次資料の情報提供 ／ 手順の誤りの指摘

したがって §1 は「測る」計画ではありません。「測ってくださる方が現れた日に、 記録を 1 枚もらうだけで閉じる状態にしておく」計画です。

実測を待たずに閉じないものは 2 つだけ

1. verifiedPhysical を実物の記録で true にする
2. IV028 の 13.30–13.52 mm を実測値に置き換える

この 2 つ以外は、方針を維持したまま全部終わります（→ §3）。 ゲートの条文も判定器も受け皿も、合成の記録で作って試験できます。

募集の側でできること

部品を買うのはこちらではありませんが、募集の質は上げられます。

  • [AI] 4極ジャックの候補を、データシートに端子配列が載っているものに絞って型番で出す
  • [AI] 「どの 1 点なら特別な計測技能なしで測れるか」を示す（→ V060_MEASUREMENT_DECISION §0）
  • [AI] 記入するだけで済む測定シートを先に用意する（→ §1-6）
  • [AI] 期待値を測る前に公開しておく（後出しで結論に合わせられないことの担保）

候補の型番は V060_MEASUREMENT_DECISION §2 にあります。

協力してくださる方が型番から探さずに済むようにするためのもので、

こちらの発注予定ではありません。

1. 実測の受け皿 — 来たら 1 枚で閉じる形にする

1-1. verifiedPhysical を true にする条件が、いま定義されていません ← 最初にやること

これが最大の発見です。記録が来る前に決めておかないと、来た日に判断が要ります。 そして判断が要る形にしておくと、たいてい甘い方へ倒れます。

schemas/half-plug-topology-profile.v3.schema.json
  verifiedPhysical:
    "実物と突き合わせて検証済みか。未実測の profile では必ず false。
     true にできるのは実測記録が伴う場合のみ"

scripts/exportHalfPlugProfile.ts:612
  verifiedPhysical: false,        ← リテラル

「実測記録が伴う場合」としか書いていません。何を何点測れば足りるのかが無いので、 現状の true は「誰かがリテラルを書き換えたら true」になります。それは検証ではありません。

しかも profile 全体は、そう簡単には埋まりません（2026-08-05 実測）。

TRS profile の evidenceGradeASSUMPTION 93 / DERIVED 1
TRRS profile の evidenceGradeASSUMPTION 151 / DERIVED 1
台帳全体（artifacts/verification_summary.json）FACT 53 / DERIVED 28 / ASSUMPTION 54 / UNKNOWN 0
UNKNOWNS.md の小見出し21 件 / うち解決 4 件 / 未解決 17 件

いま最も効く測定（VERIFICATION_PLAN.md §2-2）が閉じるのは、このうち §5-2 の 1 件だけです。 「1 件測ったから verifiedPhysical: true」は明らかに言い過ぎで、 かといって「ASSUMPTION 0 件になるまで false」だと永久に false です。

  • [AI] verifiedPhysical の合格条件を条文として書く（何を・何点・どの許容差で・誰の記録で）
  • [AI] 条件を機械判定にする（docs/measurements/ の記録を読んで真偽を出す。リテラルをやめる）
  • [AI] 判定器を変異試験にかける（記録を 1 件消したら false へ落ちること・記録が無いのに true にできないこと）
  • [人間] 「この条件で true と名乗ってよいか」を最後に判断する（対外的な主張なので）

中間の語彙を作るほうが正直かもしれません。verifiedPhysical は真偽 2 値ですが、

実態は「1 点だけ実測が入った」「看板の結論だけ実測で裏が取れた」「全部埋まった」が別物です。

[AI] 2 値のままにするか、段階を持つ別項目を足すかの設計案を 2 つ出す。

1-2. 測ったものを置く区分がありません

evidenceGrade の語彙は 4 つだけです（schemas/half-plug-topology-profile.v3.schema.json の definitions/grade）。

FACT       メーカーデータシートに数値として直接記載されている
DERIVED    FACT からの演算
ASSUMPTION 仮定
UNKNOWN    不明

実物を測った値は、このどれでもありません。FACT はデータシート記載の意味で使っているので、 自分で測った値をそこへ入れると FACT の定義が壊れます。

区分を足すのは enum の値追加＝言語が広がる変更なので、条文（docs/SCHEMA_VERSIONING_POLICY.md）に照らすと BUMPです。profile は v3 → v4 になり、下流は止まります。

  • [AI] MEASURED（仮）を足す案と、FACT の定義を「一次情報」に広げる案を、条文の判定つきで比較する
  • [AI] どちらでも scripts/schemaLanguageDiff.mjs に当てて BUMP / HOLD を実測してから決める
  • [AI] 版を上げるなら contract-migration.v1.json へ移行記録を書く（v0.5.0 で作った仕組みをそのまま使う）
  • [人間] 下流を止めるタイミングを決める（v0.6.0 でまとめて止めるか、他の破壊的変更と束ねるか）

記録が来るまで区分を足さない、という選択もあります。ただしその場合、

記録が来た日に「版を上げる」という重い作業が挟まります。

来るか分からないものを待つ形にはしない（→ §0）ので、先に決めておくほうが方針と整合します。

語彙は 2026-08-03 に一度直しています。spreadStatus が MEASURED という名前で

「モデルの走査結果」を指していて、実物測定と誤読されるので MODEL_SWEEP_* へ改名しました。

同じ名前を今度は本物の意味で使うことになるので、改名の記録と衝突しないか確認が要ります。

1-3. 何を測ってもらうと何が閉じるか — 手順は既に公開済みです

docs/VERIFICATION_PLAN.md に手順・判定基準・期待値が測る前に公開済みです。 後出しで結論に合わせられない形になっているので、この計画では対応関係を確認するだけにします。

順測定要るもの閉じるもの
1§1-1 プラグ外径（30 秒）プラグ 1 個 + ノギスUNKNOWNS §4-1b（3極の結論の土台）
2§2-2 4極ジャックの接点位置4極ジャック + 4極プラグ + テスター + ノギスUNKNOWNS §5-2（最も重い）・IV028
3§1-2 橋絡の決着実験LED 回路 + CR2032どちらのモデルが正しいか
4§2 深さの確認テスター接点ばねの軸位置

2 番目が本命です。看板の結論（3極プラグを 4極ジャックへ半挿しにすると左右差分が残る）が そこに丸ごと乗っていて、IV028 もそこから出ています。

  • [AI] 測定シートを事前に埋めておく（型番・端子番号・期待値・記入欄。測る方は数字を入れるだけ）
  • [AI] 記録から接点位置を逆算する計算を用意する（fit:contacts の 4極版は未実装）
  • [AI] 提供があったら profile へ流し込み、再生成して差分を出す
  • 提供が無ければ何もしません。待ちません（→ §0）

1-4. IV028 の 13.30–13.52 mm は詰まるか — 位置は決まる。幅は測ってみないと分からない

IV028 は TRRS profile の区間で（IV000 始まりなので 30 区間中の 29 番目）、接点はすべて ASSUMPTION です。

IV028  nominalStartMm 13.3  /  nominalEndMm 13.52   幅 0.22 mm

位置は決まります。§2-2 の測定は、対立する 2 つの予測を直接分離できます。

端子本モデルの予測（肩とジャック前面のすき間）実在部品 PS000001 から計算差
MIC12.02 mm11.99 mm0.03
GND8.33 mm8.67 mm0.34
R5.57 mm5.52 mm0.05
L2.14 mm0.69 mm1.45

L の 1 点だけで決着します。差 1.45 mm はノギスの分解能 0.01 mm の 145 倍で、 IV028 の幅 0.22 mm よりも大きいので、どちらが正しいかで IV028 は動きます。

この表を検算していて、既存文書の数値誤りが 2 件見つかりました（2026-08-05・同日に訂正済み）。

VERIFICATION_PLAN.md §2-2 が「L だけが 1.35 mm」「他の 3 点は 0.2 mm 以内」と書いていましたが、

同 artifact の contactPositions.deltaMm は Tip = 1.45 / Ring2 = -0.34 です。

REAL_JACK_COMPARISON.md §3-1 の「Tip 接点が 1.35 mm 奥へ」も同じ誤りでした。

どちらも、すぐ上に正しい表があるのに、まとめの一文だけがずれていました。

[AI] 文中の数値を artifact と機械照合する検査を足す（→ §3 と同じ型の空振り防止）。

幅が縮むかは別の話です。幅 0.22 mm はモデルの出力で、実測に置き換えたときの幅は 3 回測定のばらつきで決まります。ばらつきが 0.22 mm より小さいかは測る前には言えません。

  • [AI] 「ばらつきが幅より小さいか」を測定シートの中で自動判定する欄を作る（測った直後に分かる形にする）
  • [AI] 実測が入ったときに IV028 がどう動くかを、両予測で先に計算して公開しておく（後出し防止）
  • [AI] 募集文に「L の 1 点だけでよい」と書く（次点は GND の 0.34 mm。MIC と R は 0.05 mm 以内で差がつかない）

合わなかった結果も同じ価値があります。大きくずれたら、仮定が間違っていた証拠として記録します。

これは既に VERIFICATION_PLAN.md に書いてあるので、この計画で変えることはありません。

1-5. 提供された記録が弱くならないようにする

方針が「自分で測らない」理由は、知見が無いまま測ると根拠の弱い数値が台帳へ入ることでした。 同じ危険は、提供された記録にもあります。こちらは測る人を選べません。 気をつけるでは防げないので、シート側で構造的に潰します。

  • [AI] 測定シートに分解能と 3 回の生値を必須欄にする（結論だけ書けない形にする）
  • [AI] ばらつきが閾値を超えたらシートが不合格を出すようにする（人間が判断しない）
  • [AI] 期待値をシートに先に印字しておく（予測と一致したかを人間が後から決められない）
  • [AI] 測定値と profile の突き合わせを機械にやらせる（目視で「だいたい合っている」と言わせない）
  • [AI] 提供者がやるのは「測る・数字を書き写す」だけで済む形にする（判断を渡さない）
  • [AI] 測定手順を通しで 1 回リハーサルできる形にする（何をどの順に持ち替えるかを 1 枚に）
  • [AI] 記録に測った人・部品の型番とロット・日付を必須で残す（誰の記録かを追えるようにする）

1-6. 受け皿の実装

  • [AI] docs/measurements/ の記録形式を schema 化する（今は TEMPLATE.md だけで機械が読めない）
  • [AI] 記録を validate:profiles の検証対象に足す（13 件 → 14 件）
  • [AI] 記録から verifiedPhysical を決める判定器を書く（→ §1-1）
  • [AI] 記録が無い状態で判定器が true を返さないことを変異試験で確かめる

2. P1 / P2 — v0.6.0 の本体はこちら

外部監査の指摘はすべて妥当だと判断しています。ただし現在の配布経路では踏みません。

内容v0.6.0 でやるか
P1tar parser の頑健化（PAX・GNU long name・header checksum・path traversal・symlink）やる（下記の順）
P1verifier の資源上限（fetch timeout・圧縮/展開サイズ・entry 数・1 entry サイズ・path 長）やる
P1SOURCE_UNAVAILABLE / ARCHIVE_INVALID / MISMATCH の分離やる（一番安い）
P2read-only CI（full commit SHA pin・permissions: contents: read・publish しない）やる
P2SECURITY.mdやる

実測を待たない以上、v0.6.0 で実際に手を動かす量はここが一番多くなります。 P1 が踏まれるのは「第三者が任意の archive を渡す運用」で、その運用はまだ存在しません （配布経路は GitHub の tarball 固定）。踏まないうちに直す作業です。

不確実性そのものは verifiedPhysical の側が大きい（false のままで、モデルの主張が実測で変わりえます）。

ただしそれは待っても縮まりません。縮められるのは提供が来たときだけなので、

こちらの手番は P1 / P2 と §3 です。

  • [AI] SOURCE_UNAVAILABLE / ARCHIVE_INVALID / MISMATCH を分ける（今は一括で失敗になる）
  • [AI] 資源上限を入れる。上限を超える入力を実際に作って、止まることを実測する
  • [AI] tar parser を PAX / GNU long name / checksum 不正 / path traversal / symlink の 5 種で試験する
  • [AI] 壊れた archive を生成するテスト用ヘルパーを書く（手で作った 1 個だけで通さない）
  • [AI] read-only CI を入れる。action は full commit SHA で固定する（tag 参照は書き換わる）
  • [AI] CI が publish 権限を持たないことを、permissions の実値で確認する
  • [AI] SECURITY.md を書く（報告先・対象範囲・このプロジェクトが保証しないこと）
  • [人間] SECURITY.md に載せる連絡先を決める（個人アドレスを公開するかの判断）

連絡先は判断が要ります。過去に別リポジトリで、公開ファイルに個人アドレスが

平文で入っていたことがあります。**GitHub の private vulnerability reporting を使えば

アドレスを書かずに済みます。 [AI] その設定手順を調べて出す。[人間]** 有効化する。

3. allowlist の宣言 32 種 — 「覆っている」しか測っていません

v0.5.2 で入れた HANDLED_KEYWORDS は 32 種です。テストが見ているのは 2 つだけです。

✓ 現行 schema が使う keyword 23 種が、宣言集合に入っている（覆っている）
✓ 宣言集合が「全部入り」ではない（弾かれる keyword が実在する）

✗ 宣言した 32 種を、判定器が本当に正しく扱えるか   ← 測っていない

oneOf は「扱える」と思っていて実は扱えていませんでした。同じことが残り 31 種で 起きていないという根拠は、いまのところありません。

3-1. 何を証明すれば足りるか

keyword ごとに「判定器の答え」と「言語の包含関係の真値」が一致すればよい。 真値は ajv で決められます。新旧 2 つの schema と、値の集合があれば機械で出せます。

判定器      diffSchemaObjects(old, new).verdict ∈ {HOLD, HOLD_RECORD, BUMP}
真値        ajv で old / new をコンパイルし、値の集合で valid / invalid を突き合わせる
            新だけが通す値がある → 広がっている → BUMP でなければ**危険側の誤り**

必要なのは「危険側が無いこと」です。安全側（本当は据え置けるのに BUMP）は 判別力が落ちるだけで、契約は壊れません。

3-2. どうやるか — 3 段で登る

  • [AI] 手書きペア: 32 種それぞれに広げる変更・狭める変更・変えない変更を 1 組ずつ作る（96 ペア）
  • [AI] 各ペアで ajv の真値と判定器の答えを突き合わせ、危険側が 0 件であることを実測する
  • [AI] 組み合わせ: keyword を 2 つ重ねたときに壊れないか（enum × additionalProperties など）を試す
  • [AI] 自動生成: 小さな schema をランダム生成し、ajv の真値と判定器を突き合わせ続ける（property-based）
  • [AI] 生成器が現行 schema に無い形（深いネスト・$ref の連鎖）も作ることを、対照つきで確かめる
  • [AI] 反例が出たら、直す前に回帰テストへ入れる（v0.5.1 / v0.5.2 と同じ順序）

値の集合をどう作るかが肝です。「新だけが通す値」を見つけられなければ、

反例があっても検出できません。[AI] keyword ごとに境界値の作り方を決めてから書く

（minimum なら境界の前後、pattern ならマッチする最短文字列、など）。

3-3. どこで止めるか

全数証明はできません。JSON Schema の言語包含は一般には決定不能な方向へ行きます。

  • [AI] 条文の「限界」節へ、何を測って何を測っていないかを書く（v0.5.1 で足した節の続き）
  • [AI] 「宣言したものを正しく扱えることは、96 ペア + 自動生成 N 件で反例が出なかったところまで」と書く
  • [AI] 「起きない」とは書かない（v0.5.0 でその嘘を書いて v0.5.1 で訂正している）

4. 順序 — 実測を待つ枝はありません

既定（＝これだけ）
  [AI] §1-1 verifiedPhysical のゲートを条文にする
  [AI] §1-2 区分の設計（版を上げるかの判断材料まで）
  [AI] §1-6 受け皿（記録の schema・判定器・変異試験・測定シート）
  [AI] §2   P1 / P2 を全部
  [AI] §3   allowlist の 96 ペア + 自動生成
        ↓
  ここまでで、**実測が来たとき記録 1 枚で閉じる**状態になる

もし実測データの提供があったら（**待たない**）
  [AI] 記録を受け皿へ入れる → 判定器が verifiedPhysical を決める → 再生成 → 差分を出す

[人間] §1-2 の版上げタイミングを決める
[人間] §2  SECURITY.md の連絡先を決める
[人間] §1-1 の合格条件で true と名乗ってよいか判断する
[人間] release の公開ボタン

実測の到着は工程に入れません。方針どおり「待たない」ので、 来なければ来ないまま、上の既定だけで v0.6.0 は完結します。

人間にしか渡していないのは 4 行です（版上げ判断・連絡先判断・合格条件の是非・公開）。 発注も測定も入っていません。

5. この計画でやらないこと

  • 測定値の捏造・推定での穴埋め。測っていないものは ASSUMPTION のままにします。
  • verifiedPhysical のリテラル書き換え。判定器が記録から決める形にしてからにします。
  • anyOf / allOf を予防的に UNDEC へ倒すこと。単調性を破る反例が出たらやります（→ v0.5.2 §6）。
  • 公開済み asset の上書き。v0.1.0 〜 v0.5.2 の 181 件は触りません。
  • 実測を待つこと。方針の ❌ にあるとおりです。来なければ来ないまま完結させます。
  • 実測を前提にした記述を成果物へ入れること。「測れば分かる」は募集文であって、 モデルの主張の根拠にはしません。verifiedPhysical は記録が来るまで false です。
