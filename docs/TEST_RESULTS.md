## 1. 寸法検証（仕様 §17）— 16 件

### 設計値とモデル測定値の差

| 項目 | 設計値 | モデル | 差 |
|---|---|---|---|
| プラグ軸径 | 3.5 ±0.05 mm | 3.5 mm | 0 |
| プラグ指部長 | 14.0 mm | 14.0 mm | 0 |
| 第2絶縁帯幅 | 0.7 mm | 0.700 mm | 0 |
| 挿入穴径 | 3.6 mm | 3.6 mm | 0 |
| 完全挿入深度 | 14.0 mm | 14.0 mm | 0 |
| ジャック全長 | 17.6 mm | 17.6 mm | 0 |

**許容差外の箇所はありません。**

### 確認した内容

- 軸径が Ring / Sleeve 区間の全域で φ3.5±0.05 の公差内に収まる
- セグメントが隙間なく連続し、合計が指部長 14.0 mm にちょうど一致する
- **絶縁帯が幅ゼロではない**（仕様 §4.2）。2 本ともちょうど 0.7 mm
- 記載寸法チェーンと整合する（14 − 8.5 = 5.5 が Ring 前端、14 − 5 = 9.0 が Sleeve 前端）
- Tip 導体が Ring / Sleeve より細いという図面実測の特徴が保たれている（先端側の円錐終端 φ3.02、後端でも φ3.20。Ring / Sleeve は φ3.5）。**この 0.15 mm の段差が、第1絶縁帯で橋絡が起きない理由になる**
- ジャック外形寸法が記載値どおり（3.5 + 14.1 = 17.6 の整合を含む）
- 挿入穴 φ3.6 とプラグ φ3.5 の片側隙間が 0.05 mm
- 端子の軸位置が「基板レイアウト図の値 + ナット長 3.5」と一致する（5 端子すべて）
- 完全挿入時、**各接点のパッド全幅が対応する導体区間の内側に収まる**
- 接点の根元が接触点より奥にある（前方へ伸びる片持ち梁として成立する）
- 自由半径がプラグ半径より小さい（押付が生じる）

> 描画を CPU で行うため、他のアプリと CPU を奪い合うからです。実際、同じコードで
> 静止時 **97.1 / 114.2 / 118.9 / 123.4 / 198.9 / 222.7 ms** をすべて観測しています。

>

> 併記しています。上の値は負荷 15.6 のときの測定です。
> 負荷の記録が無いまま数値だけ比べると、混んでいただけの回を「性能が劣化した」と
> 読み違えます。

ポリゴン数は 2026-07-31 に 6,228 から 5,460 へ減りました。プラグ外形から

1. **CPU 側が重くない** — 毎フレーム全接点を再評価する挿抜アニメ中でも、静止時より悪化しない

   （空いているときの測定では 2.9 分の 1 でした。CPU が混むと塗り以外の固定費の割合が上がり、比が縮みます）

## 5. 性能 — 実 GPU（仕様 §17）

`npm run perf`（Playwright + **headed Google Chrome**）で測定。
測定日 2026-07-30、macOS 26.5.2 / **Apple M5** / Metal 4。
GL 実装は `ANGLE (Apple, ANGLE Metal Renderer: Apple M5)` で、**ソフトウェアラスタではありません**。

**全条件で fps 59.9 に達しています。** 16.7 ms はディスプレイのリフレッシュレート（60 Hz）による
上限なので、これは「上限に達している」という意味です。

**フレーム落ちはありませんでした。** 全条件の最大フレーム時間が 19.40 ms 以下で、
1 vsync 分の 2 倍（33 ms）を超えたフレームは **6 条件合計で 0 件**です。

> **測定時のマシン負荷を artifact に記録するようにしました。** この回は load average 10.66 でした。
> 以前 p95 が 18.5〜18.7 ms と出た回がありましたが、それは負荷が高かったときの値です。
> vsync がある以上、中央値と fps は負荷にほとんど影響されませんが、p95 と最大値は動きます。
> `artifacts/perf_real_gpu.json` の `loadAverage1min` と `host` を見て解釈してください。

### 1 フレームの実コスト

vsync がある限り rAF 間隔は 16.7 ms に張り付くため、そこからは余裕の有無しか分かりません。
そこで `gl.render()` の直後に `glFinish()` を入れて GPU の完了を待ち、描画そのものの時間を取り出しました
（`performance.now()` は 0.1 ms 単位に丸められるので、40 回まとめて描いてから割っています）。

| ビューポート | 通常品質 | 低負荷モード |
|---|---:|---:|
| 1440×900 @2x | **0.095 ms**（3.48 Mpx） | 0.097 ms（0.87 Mpx） |
| 1920×1080 @2x | **0.080 ms**（6.20 Mpx） | 0.087 ms（1.55 Mpx） |

**16.7 ms の予算に対して 0.5〜0.6 % しか使っていません。**

### 低負荷モードの効果 — 数値での結論

| 環境 | 通常品質 | 低負荷モード | 効果 |
|---|---:|---:|---|
| ソフトウェアラスタ（弱い GPU の代役） | 97.1〜222.7 ms | 33.6〜112.1 ms | **2〜3 倍速** |
| Apple M5（実 GPU） | 0.095 ms | 0.097 ms | **差なし** |

**Apple M5 では低負荷モードに効果がありません。** 画素数を 4 分の 1 にしても描画コストが変わらないためです。
つまりこの GPU では塗り面積が律速になっておらず、コマンド送出側で既に頭打ちになっています。

一方、ソフトウェアラスタでは 2〜2.9 倍速くなりました（倍率は CPU の混み具合で動きます）。
**低負荷モードは「フィルレートが足りない環境で効く機能」であり、その環境では実際に効くことを確認しました。**
高速な GPU で差が出ないのは、そもそも削る必要が無いからです。

> 測定はディスプレイ 60 Hz の環境です。120 Hz（ProMotion）環境では上限が 8.3 ms になりますが、
> 実コストが 0.1 ms 未満なので余裕は十分あると考えられます。ただし **120 Hz 環境では未測定です。**

### 6-3. この検証で見つけて直した不具合

**ピンチの 1 本目の指がプラグに乗ると、ズームがまったく効かなかった。**

原因は、プラグのドラッグを開始したときに `OrbitControls.enabled = false` にしていたことです。
これだと OrbitControls が 1 本目の指を登録しないため、あとから 2 本目が触れても
「2 本指ジェスチャ」として認識されず、ピンチが成立しませんでした。
プラグの上でピンチしようとすると、ズームせずにプラグが動くという挙動になります。

修正: `enabled` ではなく **`enableRotate` と `enablePan` だけを止める**ようにしました。
OrbitControls は指を数え続けるので、2 本目が触れた瞬間にズームへ移れます。
あわせて、2 本目の指が触れたらプラグのドラッグは中止してカメラ操作に譲るようにしました。

修正前後で、上表の「プラグの上から始める 2 本指ピンチ」が FAIL → PASS に変わっています。
マウス操作側（デスクトップ 27 件）に退行がないことも再実行で確認済みです。

## 8. この検証で担保していないこと

- **実物の部品との突き合わせをしていません**（現物を持っていないため）。
  ここで確認しているのは「モデルが自分の定義どおりに動くこと」と「データシート記載値と矛盾しないこと」です。
- 図面実測は 2 通りの独立した方法で一致を確認しましたが、どちらも同じ 1 つの図面を読んでいるので、
  **図面自体の誤りは検出できません**。
- **物理的な iPhone / iPad では未検証です。** iOS Safari の確認は iOS 26.4 シミュレータで行いました。
  ブラウザエンジンは実機と同じ WebKit ですが、実機固有の要素 (実際の指の接触面積、Safari の
  ツールバー挙動、実機 GPU の性能、低電力モードなど) は確認できていません。
- 実 GPU での測定は Apple M5 / 60 Hz ディスプレイ 1 台のみです。他の GPU、120 Hz 環境、実際の低性能端末では未測定です。
- 詳細は [UNKNOWNS.md](../UNKNOWNS.md) を参照してください。
