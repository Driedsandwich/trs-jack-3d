## 1. 寸法検証（仕様 §17）— 16 件

### 設計値とモデル測定値の差

| 項目 | 設計値 | モデル | 差 |
|---|---|---|---|
| プラグ軸径 | 3.5 ±0.05 mm | 3.5 mm | 0 |
| プラグ指部長 | 14.0 mm | 14.0 mm | 0 |
| 第2絶縁帯幅 | 0.7 mm | 0.700 mm | 0 |
| 挿入穴径 | 3.6 mm | 3.6 mm | 0 |
| 完全挿入深度 | 14.0 mm | 14.0 mm | 0 |
| ジャック全長 | 17.6 mm | 17.6 mm | 0 |

**許容差外の箇所はありません。**

### 確認した内容

- 軸径が Ring / Sleeve 区間の全域で φ3.5±0.05 の公差内に収まる
- セグメントが隙間なく連続し、合計が指部長 14.0 mm にちょうど一致する
- **絶縁帯が幅ゼロではない**（仕様 §4.2）。2 本ともちょうど 0.7 mm
- 記載寸法チェーンと整合する（14 − 8.5 = 5.5 が Ring 前端、14 − 5 = 9.0 が Sleeve 前端）
- Tip 導体が Ring / Sleeve より細いという図面実測の特徴が保たれている（先端側の円錐終端 φ3.02、後端でも φ3.20。Ring / Sleeve は φ3.5）。**この 0.15 mm の段差が、第1絶縁帯で橋絡が起きない理由になる**
- ジャック外形寸法が記載値どおり（3.5 + 14.1 = 17.6 の整合を含む）
- 挿入穴 φ3.6 とプラグ φ3.5 の片側隙間が 0.05 mm
- 端子の軸位置が「基板レイアウト図の値 + ナット長 3.5」と一致する（5 端子すべて）
- 完全挿入時、**各接点のパッド全幅が対応する導体区間の内側に収まる**
- 接点の根元が接触点より奥にある（前方へ伸びる片持ち梁として成立する）
- 自由半径がプラグ半径より小さい（押付が生じる）

### 2-1. この結論が乗っている土台（留保）

上の「第1絶縁帯では橋絡しない」は、**Tip 導体が Ring より 0.15 mm 低い**ことだけに乗っています。
その 0.15 mm は `plug.bodyRadius`（1.750）と `plug.insulatorRadius`（1.600）の差ですが、
**両端とも幅を持つ量**です。

| | 区分 | 幅 |
|---|---|---|
| `plug.bodyRadius` | FACT | 図面公差 φ3.5±0.05 → 半径 ±0.025 |
| `plug.insulatorRadius` | **DERIVED** | 図面実測 φ3.20〜3.22 → 半径 1.60〜1.61 |

両方を悪い側へ振った最悪コーナーでも結論は保たれますが、**余裕は 3.08 倍から 2.38 倍へ落ちます**
（[SENSITIVITY.md](SENSITIVITY.md) §6-1、[UNKNOWNS.md](../UNKNOWNS.md) §4-1b）。
つまり上の表が示すのは **「公称寸法のモデルでは出ない」**であって、
「実物の 3.5 mm プラグでは出ない」ではありません。実物は測っていません。

### 参考: ヘッドレス（ソフトウェアラスタ）での測定

上記の Playwright 実行はヘッドレス Chromium で、GL 実装は
`ANGLE (Google, Vulkan / SwiftShader)` = **ソフトウェアラスタ**でした。
したがってこの環境の fps は実機 GPU の値ではありません。ここで確認できるのは次の 2 点だけです。

| 測定 | 値 |
|---|---|
| ポリゴン数 | 5,460 三角形 / 44 draw call |
| 静止時のフレーム時間 | 123.4 ms（3.5 Mpx） |
| 挿抜アニメ中 | 138.5 ms（3.5 Mpx） |
| 低負荷モード（dpr=1・AA 無し） | 42.0 ms（0.9 Mpx） |

> **フレーム時間の 3 つは測定時のマシンの混み具合で大きく動きます。** ソフトウェアラスタは
> 描画を CPU で行うため、他のアプリと CPU を奪い合うからです。実際、同じコードで
> 静止時 **97.1 / 114.2 / 118.9 / 123.4 / 198.9 / 222.7 ms** をすべて観測しています。
> **絶対値を性能の指標として読まないでください。** 実 GPU の測定は次項です。
>
> このため `artifacts/ui_verification.json` には測定時の 1 分平均負荷（`loadAverage1min`）を
> 併記しています。上の値は負荷 15.6 のときの測定です。
> 負荷の記録が無いまま数値だけ比べると、混んでいただけの回を「性能が劣化した」と
> 読み違えます。

ポリゴン数は 2026-07-31 に 6,228 から 5,460 へ減りました。プラグ外形から
存在しない面取り（[UNKNOWNS.md](../UNKNOWNS.md) §4-4）を削除したためです。
減った 768 三角形は `6 点 × 64 分割 × 2 三角形` とちょうど一致します。

1. **CPU 側が重くない** — 毎フレーム全接点を再評価する挿抜アニメ中でも、静止時より悪化しない
2. **塗り面積に効く** — 画素数を 4 分の 1 にするとフレーム時間が約 2 分の 1 になる
   （空いているときの測定では 2.9 分の 1 でした。CPU が混むと塗り以外の固定費の割合が上がり、比が縮みます）

| 1440×900 @2x（3.48 Mpx） | 静止（完全挿入） | 16.70 ms | **59.9** | 17.50 ms | 19.40 ms | **0** |
| 1440×900 @2x（3.48 Mpx） | 挿抜アニメ中 | 16.70 ms | **59.9** | 17.50 ms | 18.30 ms | **0** |
| 1440×900 @2x（0.87 Mpx） | 低負荷モード | 16.70 ms | **59.9** | 17.60 ms | 18.60 ms | **0** |
| 1920×1080 @2x（6.20 Mpx） | 静止（完全挿入） | 16.70 ms | **59.9** | 17.80 ms | 18.20 ms | **0** |
| 1920×1080 @2x（6.20 Mpx） | 挿抜アニメ中 | 16.70 ms | **59.9** | 17.50 ms | 18.00 ms | **0** |
| 1920×1080 @2x（1.55 Mpx） | 低負荷モード | 16.70 ms | **59.9** | 17.40 ms | 17.90 ms | **0** |

**全条件で fps 59.9 に達しています。** 16.7 ms はディスプレイのリフレッシュレート（60 Hz）による
上限なので、これは「上限に達している」という意味です。

**フレーム落ちはありませんでした。** 全条件の最大フレーム時間が 19.40 ms 以下で、
1 vsync 分の 2 倍（33 ms）を超えたフレームは **6 条件合計で 0 件**です。

> **測定時のマシン負荷を artifact に記録するようにしました。** この回は load average 10.66 でした。
> 以前 p95 が 18.5〜18.7 ms と出た回がありましたが、それは負荷が高かったときの値です。
> vsync がある以上、中央値と fps は負荷にほとんど影響されませんが、p95 と最大値は動きます。
> `artifacts/perf_real_gpu.json` の `loadAverage1min` と `host` を見て解釈してください。

### 1 フレームの実コスト

vsync がある限り rAF 間隔は 16.7 ms に張り付くため、そこからは余裕の有無しか分かりません。
そこで `gl.render()` の直後に `glFinish()` を入れて GPU の完了を待ち、描画そのものの時間を取り出しました
（`performance.now()` は 0.1 ms 単位に丸められるので、40 回まとめて描いてから割っています）。

| ビューポート | 通常品質 | 低負荷モード |
|---|---:|---:|
| 1440×900 @2x | **0.0875 ms**（3.48 Mpx） | 0.0800 ms（0.87 Mpx） |
| 1920×1080 @2x | **0.0725 ms**（6.20 Mpx） | 0.0775 ms（1.55 Mpx） |

**16.7 ms の予算に対して 0.43〜0.52 % しか使っていません。**

> 2026-08-01 まで、ここには 0.095 / 0.097 / 0.080 / 0.087 と書いていました。
> **4 値とも `artifacts/perf_real_gpu.json` のどの値とも一致しません。**
> 同じ §5 のフレームレート表だけが 07-31 の再測定で更新され、
> **このコスト表が取り残されていた**ものです。上は artifact の実値です。

### 低負荷モードの効果 — 数値での結論

| 環境 | 通常品質 | 低負荷モード | 効果 |
|---|---:|---:|---|
| ソフトウェアラスタ（弱い GPU の代役） | 97.1〜222.7 ms | 33.6〜112.1 ms | **2〜3 倍速** |
| Apple M5（実 GPU） | 0.0875 ms | 0.0800 ms | **差なし** |

**Apple M5 では低負荷モードに効果がありません。** 画素数を 4 分の 1 にしても描画コストが変わらないためです。
実測は 1440 では低負荷が僅かに速く（0.0875 → 0.0800）、1920 では僅かに遅い（0.0725 → 0.0775）。
**ビューポートによって符号が入れ替わる程度＝測定ノイズの範囲**で、効果と呼べる差ではありません。
つまりこの GPU では塗り面積が律速になっておらず、コマンド送出側で既に頭打ちになっています。

一方、ソフトウェアラスタでは 2〜2.9 倍速くなりました（倍率は CPU の混み具合で動きます）。
**低負荷モードは「フィルレートが足りない環境で効く機能」であり、その環境では実際に効くことを確認しました。**
高速な GPU で差が出ないのは、そもそも削る必要が無いからです。

> 測定はディスプレイ 60 Hz の環境です。120 Hz（ProMotion）環境では上限が 8.3 ms になりますが、
> 実コストが 0.1 ms 未満なので余裕は十分あると考えられます。ただし **120 Hz 環境では未測定です。**

### 6-3. この検証で見つけて直した不具合

**ピンチの 1 本目の指がプラグに乗ると、ズームがまったく効かなかった。**

原因は、プラグのドラッグを開始したときに `OrbitControls.enabled = false` にしていたことです。
これだと OrbitControls が 1 本目の指を登録しないため、あとから 2 本目が触れても
「2 本指ジェスチャ」として認識されず、ピンチが成立しませんでした。
プラグの上でピンチしようとすると、ズームせずにプラグが動くという挙動になります。

修正: `enabled` ではなく **`enableRotate` と `enablePan` だけを止める**ようにしました。
OrbitControls は指を数え続けるので、2 本目が触れた瞬間にズームへ移れます。
あわせて、2 本目の指が触れたらプラグのドラッグは中止してカメラ操作に譲るようにしました。

修正前後で、上表の「プラグの上から始める 2 本指ピンチ」が FAIL → PASS に変わっています。
マウス操作側（デスクトップ 27 件）に退行がないことも再実行で確認済みです。

## 7.5. 文書の数字が生成物と一致しているか — 65 件

**この節は 2026-08-01 に新設しました。** 文書の数字が古くなっていることを、
人間の見直しではなく機械で捕まえるためです（`test/docs.test.ts`）。

きっかけは、同日の監査で**文書と生成物のズレが 4 件**見つかったことです。
いずれも人力で気づいたもので、放っておけば次も人力頼みになります。

| 見つかったズレ | どこ |
|---|---|
| **どの生成物にも存在しない 8.22 mm** が看板の表に載っていた | README / REPORT |
| 描画コスト 4 値が artifact のどの値とも一致しなかった | §5 |
| 測定日が artifact の `generatedAt` と 1 日ずれていた | §5 |
| 節見出しのテスト件数が、総数だけ直されて放置されていた | §2 / §3 |

> **件数の読み方に注意してください。** 64 件のうち大半は `CLAIMS` 配列からの
> **ループ生成**で、人が書いた `it()` ブロックは 15 個です。
> 表明の数で数えると、モデル検証 202 に対して文書照合は 26 で、**約 11 %** です。
> 「テスト件数の半分が文書照合」に見えるのは数え方の錯覚なので、
> モデル検証 75 件と文書照合 64 件は**分けて示しています**。

### 3 方向から見ています

| 方向 | 何を見るか | 件数 |
|---|---|---:|
| **A. 深さ表** | 「半挿しで何が起きるか」の表の全 14 数値が `events.json` に存在するか。2 文書の表が互いに一致しているか | 8 |
| **B. 転記値** | 転記していると分かっている値が、指定した文書に**その表記で**載っているか | 51 |
| **C. 逆向き** | artifact にあるのに文書が拾っていない項目が無いか | 6 |

**B が押さえている生成物**: `verification_summary`（根拠区分の内訳・押付力）、
`force_curve`（挿抜ピーク）、`perf_real_gpu`（測定日・三角形数・fps・描画コスト 4 値）、
`ui_verification` / `touch_verification`（件数）、`sensitivity`（基準の橋絡深さ・
Tip 橋絡しきい値・**公差の箱 15 マス全部**・余裕の倍率・破綻線・同時振りの幅・
力の幅・校正係数の 3 点）、`SOURCES.md` が絶縁帯を「幅」として記録していること。

> **丸めた浮動小数を文字列で比較しない。** 力の片振り表だけは数値照合にしています。
> artifact が 3 桁に丸めた値をさらに 2 桁へ丸めると、真値からの丸めと食い違うことが
> あるためです（4.2551… → artifact 4.255 → 再度丸めて 4.25。しかし真値からは 4.26）。

### 総当たりにしなかった理由

「artifact の全数値を文書から探す」も試しましたが、**使い物になりません**。
`0` や `14` や `2` はどの文書にも偶然出てくるので、**9 割が誤検出**になります（実測）。
そこで**転記していると分かっているものだけを明示的に並べる**方式にしました。

### C（逆向き）の設計

文書は 27 件 / 20 件を逐語で並べず要約しています。全数を逐語で要求すると
**文書が機械の吐き出しになって読めなくなる**ので、2 段にしました。

2. 逐語で載せないものは、**理由つきで明示的に除外する**

## 8. この検証で担保していないこと

- **実物の部品との突き合わせをしていません**（現物を持っていないため）。
  ここで確認しているのは「モデルが自分の定義どおりに動くこと」と「データシート記載値と矛盾しないこと」です。
- 図面実測は 2 通りの独立した方法で一致を確認しましたが、どちらも同じ 1 つの図面を読んでいるので、
  **図面自体の誤りは検出できません**。
- **物理的な iPhone / iPad では未検証です。** iOS Safari の確認は iOS 26.4 シミュレータで行いました。
  ブラウザエンジンは実機と同じ WebKit ですが、実機固有の要素 (実際の指の接触面積、Safari の
  ツールバー挙動、実機 GPU の性能、低電力モードなど) は確認できていません。
- 実 GPU での測定は Apple M5 / 60 Hz ディスプレイ 1 台のみです。他の GPU、120 Hz 環境、実際の低性能端末では未測定です。
- **中心的な結論は「公称寸法のモデルでの結果」です。** 「第1絶縁帯で橋絡しない」の土台である
  0.15 mm 段差は、片端が DERIVED（図面実測 φ3.20〜3.22）で、もう片端も公差 ±0.05 を持ちます。
  **実物のプラグ外径は測っていません。** 決着はノギス 1 本・30 秒で、手順は
  [VERIFICATION_PLAN.md](VERIFICATION_PLAN.md) §1-1 です（→ §2-1）。
- 仮定を振ったときに何が動くかは [SENSITIVITY.md](SENSITIVITY.md) にまとめました。
  **これも実物の検証ではありません。**モデルの内部で仮定をどう選び直しても結論が変わらない
  ことを確かめただけです。
- 詳細は [UNKNOWNS.md](../UNKNOWNS.md) を参照してください。
