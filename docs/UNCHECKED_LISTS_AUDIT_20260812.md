# 検査されていない列挙・件数の棚卸し（2026-08-12）

v0.6.11 で「**同じ境界を、検査されない一覧がもう 1 つ持っている**」欠陥が 3 件出た。
そのうち 1 件は**配布物の中**にあり、受け手に古い一覧を渡していた。

同じ形がほかにも在るかを全面で数えた記録である。
**「無い」と言うために作った文書ではない。**どこを見て、何が残っているかを書く。

---

## 0. 直した 3 件（変異対照の前後つき）

各件とも、**直す前に「嘘の一覧でも緑のままか」を実測**してから直した。

| | 直す前の変異 | 落ちた試験 | 直したあとの同じ変異 |
|---|---|---:|---|
| corpus の `ok` 旗 | `pax-linkpath-long` を `true`→`false` | **0 件** | 期待値を 1 件嘘にする → **2 件** ／ 種類の既定を消す → **5 件** |
| 手順書の status 一覧 | 5 語 → 2 語 | 2 件（※） | 偽の `TOTALLY_FAKE(9)` を足す → **2 件** |
| 同上（実際の欠陥と同じ形） | 5 語を残し偽の語を 1 つ足す | **0 件** | 新しい status を 1 つ落とす → **2 件** ／ 終了コードだけ嘘にする → **2 件** |

※ この 2 件は**一覧の正しさを見ていない**。片方は artifact の digest が変わったことを、
もう片方は `SOURCE_UNAVAILABLE` という**1 語がべた書きで残っているか**を見ていただけで、
**足りない側も、偽の値も捕まえられなかった。**

### 直し方

```
corpus の ok 旗        消した。判定は test/_tarExpectations.mjs の期待値表 1 本から引く
                       引けない材料は expectedOutcome が投げる（黙って「通る」側へ落とさない）
status の一覧          scripts/verifyReleaseSourceInputs.mjs の CLI_STATUS_EXIT を正本にした
                       配布物の手順書はそこから生成する。終了コードも同じ表が持つ
自己申告 schema の範囲  scripts/selfReportStatus.mjs へ切り出し、schema の enum を正本にした
                       関門は投げる関数なので、試験が実際に踏める（v0.6.11 までは
                       ソースを正規表現で読み、process.exit(1) という文字列を探していた）
```

## 1. 文書に書いた数（宣言照合の対象かどうか）

`npm run check:doc-numbers` の**宣言照合**が唯一の機械照合である。

```
                              数を含む行   v0.6.11 の宣言   v0.6.12 の宣言
SECURITY.md                       23           0              3
README.md                         18           0              2
docs/TEST_RESULTS.md              52           0              2
docs/VERIFICATION_PLAN.md         24           6              6
docs/REAL_JACK_COMPARISON.md      35           1              1
                                 ---
合計                             152          15             23
```

**v0.6.11 の時点で、SECURITY.md / README.md / TEST_RESULTS.md は 1 件も入っていなかった。**
実測したところ **5 件が古いまま**だった。

| 文書 | 書いてあった値 | 実測 | いつからずれていたか |
|---|---|---|---|
| SECURITY.md | 直近の release は `v0.6.8` | `v0.6.11` | 3 版ぶん |
| SECURITY.md | corpus は `26 個・6 種類` | `182 個・19 種類` | v0.6.6 以降 |
| SECURITY.md | 通す材料 `66 個` | `72 個` | **旗から数えた誤り**（本件そのもの） |
| docs/TEST_RESULTS.md | 単体テスト `1215 件` | `1218 件` | この修正で動いた |
| docs/TEST_RESULTS.md | 入力 `29 件` | `32 件` | v0.6.6 以降 |

**5 件とも直し、宣言に入れた。**変異対照で 5 件とも検出されることを確認している
（1 ずらす／版数を 1 つ戻す、いずれも `check:doc-numbers` が exit 1）。

さらに、正しかったが未検査だった 3 件も宣言に入れた（`ASSUMPTION 54 件`・
`寸法 135 件のうち 54 件`・`仮定は全体で 54 件`）。**同じ数を 3 つの文書が別々に書いている。**

## 2. まだ宣言照合に入っていない数（152 − 23 = 129 行）

**全部を入れるべきではない。**入るべきものと、入りようがないものを分ける。

### 2-1. artifact から引けるのに、まだ入っていないもの

数えた範囲では**見つからなかった**。宣言に入れた 23 件のほかに、
`artifacts/` の値と 1 対 1 で対応する主張は残っていない。

> **これは「探して見つからなかった」であって、「無い」ではない。**
> 判定は「その数が artifact のどれかと対応づけられるか」を人が見て決めており、
> 機械で網羅した結果ではない。

### 2-2. artifact に対応する値が無いもの（入りようがない）

| 種類 | 例 | なぜ入らないか |
|---|---|---|
| 実機の性能測定 | `fps 59.9` / `16.70 ms` / `フレーム落ち 0` | `npm run perf` の実行結果で、artifact に固定していない |
| 仕様の節ごとの件数 | `接点検証（仕様 §17）— 41 件` | 仕様書の項目数。artifact ではなく文書構造 |
| 履歴の記述 | `2026-08-03 まで「DERIVED 39 件」と書いていました` | **過去にそう書いた**という事実。追いかけてはいけない |
| 実物の入手状況 | `断面図は 1 件だけ` | 外形の事実。測り直す先が無い |
| 公開済み notes | `docs/release/v0.6.*-notes.md` | **凍結値**として別に管理（公開本文は編集しない方針） |

**履歴の記述を宣言に入れてはいけない。**入れると、artifact が動くたびに
「昔こう書いていた」という記録のほうが書き換わる。

## 3. 配布物・schema に載る列挙

受け手が機械で読む列挙は次の 3 か所にある。

```
scripts/verifyReleaseSourceInputs.mjs  CLI_STATUS_EXIT      ← 権威（8 種類 + 終了コード）
schemas/source-verifier-cli-result.v1  properties.status.enum  試験が CLI_STATUSES と一致を assert
artifacts/source-verification-result   howToVerifyYourself     **v0.6.12 から権威から生成**
```

`schemas/` の `description` に列挙を書いている欄は、**enum と description の両方を持つ 15 欄**。
機械で突き合わせると 13 欄が「ずれ」と出たが、**読むと 13 件とも誤検出だった。**

| 見かけのずれ | 実際 |
|---|---|
| `spreadStatus` に enum に無い 3 語 | **2026-08-03 まで使っていた旧名**を「改めた」と説明している文 |
| `source-verifier-cli-result` の `INTERNAL_ERROR` | **入れていない理由**を書いた文。専用の試験がある |
| `source-verification-result` の `ARCHIVE_INVALID` | **表現できない**と書いた文。専用の試験がある |
| `topologyClass` を description が列挙していない | 列挙する義務は無い。enum が正本 |

**検出器のほうが粗い。**「大文字語が enum に無い」だけでは、
説明文が正当に触れている語と、古い一覧を見分けられない。
**この 13 件を「欠陥 13 件」と報告するのは誤りである。**

残る観点としては、**description が「これで全部」と読める書き方をしているのに
enum と食い違う**場合が危ない。今回はその形は見つからなかった。

## 4. 残っている構造的な弱さ

1. **宣言照合は allowlist である。**宣言していない数がいくらずれても「不一致 0 件」になる。
   `check:doc-numbers` はこれを自覚していて、**裏の取れなかった mm 値の件数**を常に出す。
   だが件数系（`N 件`・`N 個`）にはその安全網が無い。
2. **公開済み notes の凍結値は 4 件だけ。**tag が 21 本あるのに、凍結しているのは v0.6.0 のみ。
   ほかの notes は**照合も凍結もされていない**。
3. **`README.md` の性能表と `TEST_RESULTS.md` の性能表が同じ数を別々に持っている。**
   同じ境界の 2 つ目の一覧だが、artifact が無いので今の枠組みでは縛れない。
   `npm run perf` の出力を artifact にすれば縛れる。**まだやっていない。**

---

## 5. この棚卸し自体の限界

- 数を含む行の抽出は `(\d+\s*(件|個|本|種類|か所))|(\*\*\d+\*\*)` という正規表現で、
  **表の中の裸の数字や、日本語で書いた数（「3 つ」）は拾えていない。**
- 「artifact から引けるか」の判定は人が見て決めた。**網羅の証明は無い。**
- schema の description は 488 件あり、そのうち**列挙または件数を含むと判定した 24 件**しか読んでいない。
