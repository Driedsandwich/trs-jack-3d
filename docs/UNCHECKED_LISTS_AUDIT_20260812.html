検査されていない列挙・件数の棚卸し（2026-08-12）

v0.6.11 で「同じ境界を、検査されない一覧がもう 1 つ持っている」欠陥が 3 件出た。 そのうち 1 件は配布物の中にあり、受け手に古い一覧を渡していた。

同じ形がほかにも在るかを全面で数えた記録である。 「無い」と言うために作った文書ではない。どこを見て、何が残っているかを書く。

3. 配布物・schema に載る列挙

受け手が機械で読む列挙は次の 3 か所にある。

scripts/verifyReleaseSourceInputs.mjs  CLI_STATUS_EXIT      ← 権威（8 種類 + 終了コード）
schemas/source-verifier-cli-result.v1  properties.status.enum  試験が CLI_STATUSES と一致を assert
artifacts/source-verification-result   howToVerifyYourself     **v0.6.12 から権威から生成**

schemas/ の description に列挙を書いている欄は、enum と description の両方を持つ 15 欄。 機械で突き合わせると 13 欄が「ずれ」と出たが、読むと 13 件とも誤検出だった。

見かけのずれ実際
spreadStatus に enum に無い 3 語2026-08-03 まで使っていた旧名を「改めた」と説明している文
source-verifier-cli-result の INTERNAL_ERROR入れていない理由を書いた文。専用の試験がある
source-verification-result の ARCHIVE_INVALID表現できないと書いた文。専用の試験がある
topologyClass を description が列挙していない列挙する義務は無い。enum が正本

検出器のほうが粗い。「大文字語が enum に無い」だけでは、 説明文が正当に触れている語と、古い一覧を見分けられない。 この 13 件を「欠陥 13 件」と報告するのは誤りである。

残る観点としては、description が「これで全部」と読める書き方をしているのに enum と食い違う場合が危ない。今回はその形は見つからなかった。

4. 残っている構造的な弱さ

  1. 宣言照合は allowlist である。宣言していない数がいくらずれても「不一致 0 件」になる。 check:doc-numbers はこれを自覚していて、裏の取れなかった mm 値の件数を常に出す。 だが件数系（N 件・N 個）にはその安全網が無い。
  2. 公開済み notes の凍結値は 4 件だけ。tag が 21 本あるのに、凍結しているのは v0.6.0 のみ。 ほかの notes は照合も凍結もされていない。
  3. README.md の性能表と TEST_RESULTS.md の性能表が同じ数を別々に持っている。 同じ境界の 2 つ目の一覧だが、artifact が無いので今の枠組みでは縛れない。 npm run perf の出力を artifact にすれば縛れる。まだやっていない。

5. この棚卸し自体の限界

  • 数を含む行の抽出は (\d+\s*(件|個|本|種類|か所))|(\*\*\d+\*\*) という正規表現で、 表の中の裸の数字や、日本語で書いた数（「3 つ」）は拾えていない。
  • 「artifact から引けるか」の判定は人が見て決めた。網羅の証明は無い。
  • schema の description は 488 件あり、そのうち列挙または件数を含むと判定した 24 件しか読んでいない。
