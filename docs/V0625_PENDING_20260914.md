## 2. BusyBox を 3 つ目の oracle に足した

### なぜ

`test/tarExtractionOracle.test.ts` の `EVIDENCE_ELSEWHERE` は、
「GNU tar 1.35 / BusyBox 1.37 の実測にもとづく判断だが、こちらの環境には
GNU tar も BusyBox も無いので再現していない」と書いていた。
GNU tar は CI の ubuntu で走るようになったが、**BusyBox はどこでも走っていない。**
手元で走らない実装は、根拠ではなく引用である。

### 何を足したか

```
busyboxDisagreement()      tar / python が一致したあと、BusyBox の木とも比べる
extractWithBusyBoxTree()   busybox tar -xf … -C … で展開し、**walkTree**（同じ物差し）で木にする
BUSYBOX                    可用性の判定。busybox は引数なしで exit 1 なので、
                           **終了コードではなく「起動できたか」**で見る
busyboxSkipped             スキップした回数。0 件のまま「スキップした」と言えないようにする
```

**python3 とは扱いを分けた。**

| oracle | 無いとき |
|---|---|
| `tar` / `python3` | **必須。**「確かめていない」＝不合格に倒す（v0.6.8 からの規則） |
| `busybox` | **任意。**スキップして、スキップしたと出す（受け手に BusyBox を要求する筋合いが無い） |

ただし**在るなら、割れたら止める。**「表示するだけ」にすると門にならない。

### この開発機での結果（スキップ）

```
BusyBox oracle: **無い（ENOENT）→ この run では照合をスキップする**
BusyBox 照合: スキップ / この run でスキップした材料 76 件

test/tarExtractionOracle.test.ts + test/ciWorkflow.test.ts   347 件すべて通る   exit 0
```

### 経路が本当に動くことの確認（偽の `busybox` を置いた）

**BusyBox 本体は入れていない。**PATH の先頭に置いた使い捨ての shim で、3 つの状態を測った。

```
(a) 本物の tar へ委譲する shim    309 件すべて通る  exit 0  「実走 / スキップ 0 件」
(b) わざと 1 ファイル増やす shim   **76 件が落ちる** exit 1
    メッセージ: 3 つ目の oracle（BusyBox）が違う木を作る: BusyBox のみ file zz-extra-from-busybox.txt #…
(c) shim なし（本来の状態）        347 件すべて通る  exit 0  「スキップ / 76 件」
```

(b) を最初に走らせたとき、差分が**空文字**で出た——「tar にあって BusyBox に無い行」だけを
見ていたので、**BusyBox が余分に作った物が報告されなかった。**両方向の差を出す形へ直してある。

### まだ測っていないこと

- **BusyBox 本体の挙動。**上の (a)(b) が確かめたのは呼び出し経路と門の噛み方だけで、
  実物の BusyBox tar が corpus の何を拒み、何を違う木にするかは**CI の run が初めて測る。**
  corpus には「通す」材料が 72 個あるので、**CI が赤くなる可能性がある**
  ——それは欠陥の発見であって、この変更の失敗ではない。
- `EVIDENCE_ELSEWHERE` の `on` は `bsdtar` / `gnu-tar` / `none` の 3 値のままである。
  BusyBox で根拠が取れる行を `on: 'busybox'` へ動かすには、**BusyBox が実際に走った run の
  出力**が要る（件数を固定した試験も一緒に直すことになる）。

## 4. CI の最初の run（2026-10-18）

この作業ブランチを PR にして、**BusyBox が初めて CI で走った。**

```
ubuntu   BusyBox v1.36.1（Ubuntu の apt）  照合: 実走 / スキップ 0 件
macOS    入らなかった                       照合: スキップ / 76 件
```

### BusyBox だけが展開を拒む材料が 3 個あった

検算器が受理し、tar と python が**同じ木を作る**のに、BusyBox だけが exit 1 で止まった。

```
rawField/raw-cksum-signed                    tar: invalid tar header checksum
headerFormat/format-v7-no-prefix             tar: invalid tar magic
headerFormat/format-unknown-magic-no-prefix  tar: invalid tar magic
```

3 個とも、過去の外部監査で**受理すると決めた形**である
（signed checksum は v0.6.8 の P1-C、V7 と未知 magic は v0.6.9 の P0-A）。
**違う木を作った材料は 0 個。**§2 の「CI が赤くなる可能性がある」はこの形で起きた。

**検算器は変えていない。**試験の側で「拒む」と「違う木を作る」を分けた。

| BusyBox が | 扱い |
|---|---|
| 違う木を作る | **止める**（変えていない） |
| 展開を拒む・表に無い | **止める**（変えていない） |
| 展開を拒む・`BUSYBOX_REFUSES` に載っていて理由の文も合う | 通す |
| `BUSYBOX_REFUSES` に載っているのに展開した | **止める**（表が古い） |

表は `test/tarExtractionOracle.test.ts` の `BUSYBOX_REFUSES`（3 件）で、件数も試験で固定した。
開発機では偽の `busybox` を PATH の先頭に置いて 2 通り測った。

```
magic と unsigned checksum を見て拒む偽物   311 件すべて通る  「表のとおりに拒まれた 3 件」
何でも tar へ任せる偽物                    5 件が落ちる      表の 3 件が「表が古い」で名指しされる
期待する理由の文を 1 件だけ変えた変異        2 件が落ちる      理由の照合が効いている
```

**受理の範囲を BusyBox に合わせて狭める道は採らなかった。**それは検算器の判定を変える
（版を上げる・外部監査の結論を戻す）話で、この作業の範囲の外にある。

### macOS では入れないことにした

Homebrew に busybox の formula が無かった（`No available formula with the name "busybox"`）。
導入の step は `continue-on-error` なので CI は止まらなかったが、毎回必ず失敗する step を残すと
失敗の注記が本当の失敗を埋もれさせる。**導入は ubuntu だけ**にした（`test/ciWorkflow.test.ts` で固定）。

版を記録する行も直した。`busybox | head -1 || echo …` は pipefail の無い bash では
パイプの終了コードが head の 0 になり、無いときに代わりの文が出ず `command not found` だけが残っていた。
